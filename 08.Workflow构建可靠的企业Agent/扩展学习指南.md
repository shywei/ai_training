## 主题一：工业级持久化执行引擎（Durable Execution）原理对比：Temporal 与 Restate 架构解析

### 1. Why 为什么值得深潜（生产触发场景）
在课堂上，我们的 `AgentRuntime` 是运行在 JVM 进程内存中的循环。这在短平快的实时交互中运行良好，但在企业复杂任务场景下：
- **场景 1（进程重启导致任务腰斩）**：Agent 执行一个长达 15 步的企业采购审查流程。在执行到第 8 步时，Kubernetes 触发了 Pod 滚动发布，或者 JVM 发生了 FullGC / OOM。单机内存中的状态全部蒸发，导致整个任务永久丢失。
- **场景 2（重试导致外部副作用重复执行）**：如果简单地把整个任务从第 1 步重新跑一遍，前面已经执行成功的“扣除客户预算”、“发送供应商邮件”等操作会被再次重复执行，引发严重的业务灾难与资产损失。
- **核心诉求**：我们需要一种能力——**让代码在物理进程挂掉、服务器断电甚至跨天挂起等待人工审批后，能在新进程中从容“苏醒”，精准从上次中断的断点继续向下执行，且绝对不重复触发已完成的外部物理调用**。这就是**持久化执行（Durable Execution）**的精髓。

### 2. Where 权威一手资料（核心信源与链接）
- **工业级持久化执行事实标准：Temporal**：
  - Temporal 官方核心概念文档（Workflow Execution, Activities, Event History & Replay）：  
    [Temporal 官方文档站](https://docs.temporal.io/workflows)
  - Maxim Fateev（AWS SQS/SWF 与 Cadence/Temporal 创始人）技术演讲与长文：*"Durable Execution: A New Paradigm for Cloud Applications"*：  
    [Temporal Durable Execution 范式解析](https://temporal.io/blog/durable-execution)
- **新一代云原生轻量执行引擎：Restate**：
  - Restate 官方架构规范（针对无状态服务与 AI Agent 步进执行的状态日志协议）：  
    [Restate 官方文档站](https://docs.restate.dev/)

### 3. What 高效阅读指引（核心看点与避坑）
- **Event Sourcing（事件溯源）与 Replay（确定性重放）底层机制**：
  - **核心看点**：仔细阅读 Temporal 关于 **Workflow History** 与 **Replay** 的时序图。在 Durable Execution 中，工作流代码被划分为两部分：
    1. **Workflow Definition（编排逻辑）**：必须是**严格确定性（Deterministic）**的纯代码。严禁在 Workflow 代码中直接调用系统当前时间（`System.currentTimeMillis()`）、生成随机数（`UUID.randomUUID()`）或发起原生 HTTP/RPC 请求。所有非确定性操作必须委托给 Activity。
    2. **Activity（外部副作用单元）**：负责具体的 LLM 调用、数据库写入或 RPC 请求。每次 Activity 执行成功后，其返回结果会被持久化为一条 `ActivityTaskCompleted` 事件写入事件历史日志。
  - **重放苏醒机制**：当 Pod 挂掉重启时，Temporal 引擎重新执行你的 Java 工作流方法。当代码再次执行到第 1 步的 `llmClient.call()` 时，引擎拦截该调用，检测到历史事件日志中已有该步骤的完成记录，**直接从日志中反序列化出当年的结果返回，完全不发起实际网络请求**！直到代码重放到尚未执行的第 9 步，才真正发起网络调用。这种机制使得开发者可以用写普通单机顺序代码的方式，写出天然抵御进程崩溃的韧性程序。
- **Temporal vs Restate 架构选型对比**：
  - **Temporal**：重型工业级标杆。由独立的 Temporal Cluster（基于 Cassandra/PostgreSQL + History/Matching/Frontend 角色）调度。适合数月级超长业务流、高吞吐企业主核心流程；但架构偏重，本地联调与运维门槛较高。
  - **Restate**：云原生轻量级。基于 Kafka 或轻量嵌入式存储，提供 RPC 风格的无状态挂起与恢复（Durable Promise / Virtual Objects）。针对 AI Agent 步进式执行（Step-by-step Execution）更加轻量敏捷。
- **Java 避坑要点**：
  - **版本兼容性陷阱（Workflow Versioning）**：生产环境中修改已有运行实例的 Java Workflow 代码逻辑时，若改变了事件流转顺序，会导致重放校验抛出 `NonDeterministicWorkflowError`。必须使用 `Workflow.getVersion()` API 进行版本分支管理。

## 主题二：复杂工作流中的分布式事务：Saga 模式（正向幂等重试与逆向补偿）

### 1. Why 为什么值得深潜（生产触发场景）
传统企业业务流程是硬编码的，每个步骤的逆向补偿非常明确。而在 Agentic Workflow 中：
- Agent 的行动链是**由 LLM 根据中间观察结果动态规划与决策的**。
- **痛点场景（跨系统长事务部分失败）**：导购 Agent 为用户办理采购：第 1 步成功扣减了用户积分；第 2 步成功锁定了供应商库存；但在第 3 步生成财务发票时，发票服务由于网络异常彻底不可用。
- 此时分布式 2PC（两阶段提交 / XA 事务）完全不可行（微服务跨多团队、持有长周期锁会导致数据库雪崩）。如果系统没有设计完善的 **Saga 分布式事务与逆向补偿机制**，积分被白白扣除、库存永久挂起，引发严重客诉与账目不平。

### 2. Where 权威一手资料（核心信源与链接）
- **微服务架构经典论著**：
  - Richardson, Chris. *"Microservices Patterns: With examples in Java."* Manning Publications.（重点精读第 4 章：*Managing transactions with sagas*）。  
    [Microservices.io: Saga 模式在线权威专栏](https://microservices.io/patterns/data/saga.html)
- **Temporal 官方 Saga 实现参考**：
  - Temporal Java SDK Saga 框架与补偿链设计：  
    [Temporal Saga Pattern 官方指南](https://docs.temporal.io/encyclopedia/saga-pattern)

### 3. What 高效阅读指引（核心看点与避坑）
- **Saga 三大事务分类与设计铁律**：
  - 精读 Chris Richardson 论著中关于事务类型的界定：
    1. **可补偿性事务（Compensatable Transactions）**：有可能会失败的普通业务步骤，但必须预先定义其逆向补偿操作（如：`扣积分` $\leftrightarrow$ 补偿 `退还积分`；`锁库存` $\leftrightarrow$ 补偿 `释放库存`）。
    2. **支点事务（Pivot Transaction）**：**整个工作流成败的分水岭！** 一旦支点事务成功执行，后续所有步骤**绝对不允许失败回滚**；如果支点事务失败，则触发前序所有可补偿事务的逆向回滚。在电商中，*“订单支付扣款成功”* 通常就是支点事务。
    3. **可重试事务（Retriable Transactions）**：在支点事务之后的步骤（如“异步发送订单确认通知短信”、“生成离线报表”）。这些步骤即使下游暂时宕机，也不需要向前回滚订单，只需借助消息队列或重试引擎不断重试，直至最终必定成功（保证最终一致性）。
- **Orchestration（编排式）vs Choreography（协同式）在 Agent 中的选型**：
  - 在 AI Agent 场景下，**坚决采用编排式（Orchestration）Saga**。协同式（事件广播）在微观动态推理中极难还原因果树状链路。由 `AgentRuntime` 或工作流引擎集中记录一个 `SagaDefinition`，在执行每个 Tool Call 时，将对应的逆向补偿 Lambda（如 `saga.addCompensation(orderService::cancelOrder, orderId)`）压入补偿栈（LIFO 栈结构）。一旦任何中间检查点失败，逆向弹出执行补偿。
- **Agent 动态推理中的非确定性补偿陷阱**：
  - **避坑红线**：补偿动作自身必须是**严格幂等（Idempotent）**的！因为补偿动作本身在弱网下也可能重试。如果“退还积分”接口本身不带防重流水号，补偿重试会导致用户积分反而被多退，造成资损。

## 主题三：确定性规划与动态推理融合：FSM、DAG（LangGraph Pregel）与 GOAP 取舍

### 1. Why 为什么值得深潜（生产触发场景）
当前 AI 社区存在两种极端的架构倾向：
- **极端一（纯动态 LLM 循环）**：完全指望大模型通过 ReAct / 自主 Plan 进行任务流转。在稍微复杂的 10 步业务中，模型跑着跑着就出现“死循环调用同一个工具”、“遗忘关键前置检查”或“擅自跳过支付直接给用户承诺已发货”。
- **极端二（死板硬编码流程）**：用硬编码写死所有 if-else，大模型仅充当文本润色工具，完全丧失了面对模糊需求时动态调整策略的智能特性。
- 企业级架构师的核心功力，在于**根据业务严谨度与灵活性要求，在有限状态机（FSM）、有向无环图（DAG / LangGraph Pregel 模型）与目标导向行动规划（GOAP）之间找到最佳融合平衡点**。

### 2. Where 权威一手资料（核心信源与链接）
- **图状态机与分布式图计算基础**：
  - Malewicz, G., et al. *"Pregel: A System for Large-Scale Graph Processing."* ACM SIGMOD 2010.（LangGraph 底层核心计算模型来源）。  
    [ACM Digital Library: Google Pregel 经典论文](https://dl.acm.org/doi/10.1145/1807167.1807184)
  - LangGraph 官方底层概念深度指南（StateGraph, Reducer, Checkpointer & Supersteps）：  
    [LangGraph Core Concepts 官方文档](https://langchain-ai.github.io/langgraph/concepts/low_level/)
- **目标导向规划（GOAP）与工业级混合架构**：
  - Orkin, Jeff. *"Three States and a Plan: The A.I. of F.E.A.R."* GDC 2006（游戏 AI 领域 GOAP 奠基性论文）。  
    [Jeff Orkin GOAP 原始论文与资源站](http://alumni.media.mit.edu/~jorkin/goap.html)
  - Embabel 开源框架（面向企业级 Java/Kotlin 的目标驱动 Agent 规划引擎）：  
    [Embabel GitHub 仓库](https://github.com/embabel/embabel)

### 3. What 高效阅读指引（核心看点与避坑）
- **三大主流规划模型的工程特性全景矩阵**：

| 维度 | 有限状态机（FSM） | 有向无环图 / 环图（LangGraph Pregel） | 目标导向规划（GOAP） |
| :--- | :--- | :--- | :--- |
| **拓扑定义方式** | 显式预定义有限 State 集合与转移条件（如第 8 课手搓的 7 状态机） | 节点（Nodes）为处理函数，边（Edges）为路由逻辑，支持条件分支与循环 | 定义当前世界状态（World State）、目标状态（Goal）与 Action 集合（Preconditions & Effects） |
| **执行引擎机制** | 当前状态转移驱动，易于状态持久化 | 基于 Pregel **超步（Superstep）** 并发步进：各节点计算后发送消息，Reducer 函数合并 State | 采用 **A* 启发式搜索算法** 从目标向初始状态反向逆推最优行动路径链 |
| **容错与审计性** | **最高**。每一步都在白名单状态内，绝不可能跑飞 | **中高**。通过 Checkpoint 快照持久化，支持时间旅行（Time Travel）与回滚 | **中等**。规划路径是动态搜索生成的，依赖前置条件的严密性 |
| **生产适用场景** | 强监管、高严谨金融交易、订单核心主链路 | 研报撰写、多角色协作审查、跨部门数据治理流水线 | 开放环境资源调度、多变组合配置寻优、游戏 NPC 自主交互 |

- **LangGraph Pregel 核心看点**：
  - 重点阅读其 **State Reducer（状态归约函数）** 与 **Superstep 机制**。在 Pregel 模型中，多个并行 Node 输出的数据通过预定义的 Reducer（如 `(current_list, new_elements) -> current_list.addAll(new_elements)`）安全合并进全局 State，从拓扑层面杜绝了多线程并发修改共享状态的脏写冲突。
- **架构融合设计模式建议**：
  - 采用 **“外层确定性状态机（FSM/DAG 围栏）+ 内层微观动态推理（LLM ReAct Loop）”** 的分层设计。外层 FSM 牢牢锁死企业业务大关卡（如：必须先通过风控审查，才能进入支付确认）；内层将复杂的信息提取、用户意图辨析交给 LLM 在特定节点内部自由发挥，既保证了企业合规底线，又保留了大模型的灵活性。

## 主题四：智能体运行时可观测性标准：OpenTelemetry GenAI Semantic Conventions

### 1. Why 为什么值得深潜（生产触发场景）
传统 APM 监控（如针对 HTTP 请求耗时、数据库 SQL 执行时间的 Spring Actuator / SkyWalking）在面对 AI Agent 时完全力不从心：
- **无法定位的性能瓶颈**：一个请求耗时 8 秒，传统监控只显示 `POST /api/chat` 执行了 8 秒，根本无法透视中间是 LLM 首字延迟（TTFT）慢了、还是第 3 次工具调用的数据库连接池被占满、抑或是 ReAct 状态机循环了 5 轮才停下。
- **账单暴涨无处问责**：月末大模型 Token 账单翻倍，研发团队无法统计到底是哪个具体的 Agent 角色、哪个下游业务环节、哪次恶意的超长 Prompt 吞噬了资金。
- **敏感数据合规雷区**：为了排查问题，初级开发将完整的 Prompt 和大模型回复全部用 `log.info()` 打印进日志。结果用户的银行卡号、手机号等 PII（个人敏感信息）直接泄露进明文日志采集器，违反企业数据合规安全红线。
- 掌握 **OpenTelemetry GenAI 统一标准规范**，是将 Agent 从玩具推向生产可观测体系的最后一块关键拼图。

### 2. Where 权威一手资料（核心信源与链接）
- **官方行业标准定义**：
  - OpenTelemetry 官方 GenAI Semantic Conventions（语义约定标准，定义了 `gen_ai.*` 的完整属性集）：  
    [OpenTelemetry GenAI 官方规范文档](https://opentelemetry.io/docs/specs/semconv/gen-ai/)
- **工业界开源实现标杆**：
  - OpenInference（Arize AI 发起、被业界广泛采纳的 GenAI 语义可观测性开源协议）：  
    [OpenInference GitHub 仓库](https://github.com/Arize-ai/openinference)
  - Langfuse（专为 LLM 应用与 Agent 打造的现代化开源可观测性与 Prompt 追踪平台）：  
    [Langfuse 官方文档与架构指南](https://langfuse.com/docs)

### 3. What 高效阅读指引（核心看点与避坑）
- **核心 Span 属性规范速查表（重点记忆与配置）**：

| 属性名称 (Attribute Key) | 数据类型 | 典型示例 | 业务工程意义 |
| :--- | :--- | :--- | :--- |
| `gen_ai.system` | String | `"openai"`, `"anthropic"`, `"ollama"` | 标识大模型供应商标识符 |
| `gen_ai.request.model` | String | `"qwen-plus"`, `"gpt-4o"` | 请求指定的目标模型名称 |
| `gen_ai.response.model` | String | `"qwen-plus-2024-11-25"` | 服务端实际完成推理的具体底层权重版本 |
| `gen_ai.usage.input_tokens` | Int | `1240` | 单次调用的输入 Prompt Token 消耗量（计费核心） |
| `gen_ai.usage.output_tokens` | Int | `312` | 单次推理生成的 Completion Token 消耗量（计费核心） |
| `gen_ai.client.operation.name` | String | `"chat"`, `"embeddings"`, `"execute_tool"` | 当前 Span 的操作原语 |
| `gen_ai.request.temperature` | Float | `0.7` | 推理超参数，便于关联分析幻觉与发散度 |

- **层级化 Trace 树状拓扑设计**：
  - 生产中必须将 Agent 调用组织为清晰的三级 Span 树：
    
    ```
    Root Span: agent.session.execute (Session ID, User ID)
    ├── Child Span 1: agent.planner.think (gen_ai.system, Tokens: 520)
    ├── Child Span 2: agent.tool.execute (tool.name="queryStock", duration=120ms)
    ├── Child Span 3: agent.planner.think (gen_ai.system, Tokens: 680)
    └── Child Span 4: agent.confirmation.wait (HITL 状态挂起, duration=15s)
    ```

- **敏感数据脱敏与采样策略（Java 落地避坑）**：
  - **默认禁用全文采集**：在生产环境中，`gen_ai.prompt` 与 `gen_ai.completion` 的原始报文默认**必须关闭采集**，或者配置正则掩码器（Masking Filter）对手机号、身份证、密钥等字段执行 `****` 替换。
  - **OTLP 标准直连导出**：利用 Spring Boot 3 的 `Micrometer Tracing` 配合 OpenTelemetry OTLP Exporter，直接将追踪数据流式推送给内网的 OTel Collector。避免与特定 SaaS 厂商深度绑定，随时可以平滑分流至 Langfuse、Jaeger 或 Datadog。

## 配套自测思考题（Self-Check）

在学完以上一手资料后，请尝试独立回答以下 3 道架构级自测题，检验对生产级 Agent 流程控制与治理体系的掌握情况：

### 思考题 1：长周期工作流持久化执行（Durable Execution）中的重放幂等陷阱
**场景**：某采购 Agent 编排了一个审批流程。第 1 步调用 LLM 生成了采购合同草案；第 2 步调用邮件服务向供应商发送了确认邮件；随后工作流挂起等待供应商邮件点击确认（耗时预计 2 天）。
在挂起第 2 天上午，运维团队对执行该任务的 Kubernetes 集群执行了节点滚动重启。新容器启动后，基于 Temporal 重启该工作流。
如果负责发送邮件的开发人员将发邮件代码直接写在 Workflow 编排方法中（而不是封装在 Activity 中），工作流重启后会发生什么严重后果？其底层的重放机制是怎样运作的？
> **参考思路**：
> 1. **严重后果**：由于发邮件逻辑直接写在 Workflow 主方法中，重放引擎在恢复工作流时，会从代码第 1 行重新执行。引擎无法判断该原生 Java 代码是否已经产生过外部副作用，导致供应商再次收到一封一模一样的采购邮件！如果期间发生多次崩溃重启，供应商甚至会被邮件轰炸。
> 2. **底层机理与正规设计**：
>    - Temporal 的重放是基于**事件历史记录（History Event Log）**的。只有封装在 Activity 中的调用，其完成状态和输出结果才会作为 `ActivityTaskCompleted` 事件持久化进日志。
>    - 正规设计必须将发邮件逻辑抽离到专门的 `EmailActivity` 中。重放时，引擎执行到 `emailActivity.sendConfirmationEmail()`，发现事件历史中已存在该 Activity 执行成功的记录，会直接跳过实际网络调用，静默返回历史结果，工作流瞬间恢复至挂起等待点，确保外部副作用严格只执行一次。

### 思考题 2：Saga 事务模式下 LLM 自主决策的补偿一致性设计
**场景**：用户指示导购 Agent：“*帮我买 2 台笔记本，总预算 2 万元以内；如果联想有现货就买联想，没现货就买戴尔*”。
Agent 在第 1 步锁定了联想的 2 台库存；但在第 2 步扣减公司采购账户资金时发现余额不足（仅剩 1.5 万元）。此时 Agent 经过 LLM 自主推理，认为“既然总预算不够，那我改买 1 台联想笔记本吧”，于是没有回滚第 1 步的库存，而是继续执行了新的扣款。
请分析：这种由 LLM 在长事务中途擅自变更业务参数的行为，破坏了传统 Saga 事务的什么核心设计假设？在生产架构中应如何对 LLM 的自主补偿与分支做“围栏约束（Guardrailing）”？
> **参考思路**：
> 1. **破坏的核心假设**：破坏了传统 Saga 的**原子目标一致性与事务隔离性**。Saga 模式假定整个事务的最终目标（Goal）是确定的，前序步骤失败时，逆向补偿必须严格执行前序动作的逆向反向操作（锁 2 台 $\rightarrow$ 释放 2 台），将系统恢复至事务发生前的干净状态。LLM 擅自在事务中途修改了业务目标（从买 2 台变为买 1 台），导致前面的资源预占与后续的扣减不匹配，产生幽灵资源悬空。
> 2. **生产围栏设计**：
>    - **Saga 状态机不可篡改原则**：当步骤抛出不可恢复的业务异常（如余额不足）时，控制权必须强制移交给确定性状态机，立即触发已注册的逆向补偿链（释放联想 2 台库存），彻底终结当前失败事务。
>    - **失败后的二次规划机制**：在原事务彻底干净回滚并返回 `FAILED` 状态后，系统将失败原因装配回上下文，允许 LLM 在新一轮完整的交互中提出新建议：“*您的预算不足以购买 2 台，是否改为购买 1 台？*”，经由用户明确授权后，重新开启一个全新的独立 Saga 事务。

### 思考题 3：OpenTelemetry GenAI 标准下的企业级链路成本分析与异常拦截
**场景**：某企业上线了客服任务 Agent。监控大盘显示，某日系统发生了严重的 API 欠费告警，但当天的总请求用户数并没有明显增加。
请基于 OpenTelemetry GenAI Semantic Conventions 的属性集合，设计一套自动化的日志/链路告警规则，精确定位是哪一个链路环节导致的 Token 异常暴涨，并指出应该监控哪些具体的 Span 属性指标。
> **参考思路**：
> 1. **核心 Span 监控指标切片**：
>    - 聚合分析 `gen_ai.system` 与 `gen_ai.request.model` 维度的 `gen_ai.usage.input_tokens` 和 `gen_ai.usage.output_tokens`；
>    - 统计单次 Root Trace 内的 **Child Span 深度与数量（ReAct 迭代轮数）**；
>    - 监控每一个 Tool Call Span（`execute_tool`）的耗时与返回数据长度。
> 2. **异常归因排查时序**：
>    - **排查维度 A（是否陷入死循环）**：检查单个 Trace 包含的 `gen_ai.client.operation.name = "chat"` 子 Span 数量。如果数量触碰到了上限（如配置的 `MAX_ITERATIONS = 10`），说明任务规划器在特定复杂意图下无法收敛，循环疯狂消耗 Token。
>    - **排查维度 B（上下文雪崩膨胀）**：对比第 1 轮与第 10 轮的 `gen_ai.usage.input_tokens` 增长曲线。如果每一轮以指数级或数万 Token 级暴增，说明工具返回的超大 HTML/数据未做截断直接全量拼进了对话上下文。
> 3. **企业级自动断路防护**：
>    - 在 OTel 拦截器中设置“单会话 Token 熔断阈值”：当单次 Trace 累积 `input_tokens + output_tokens > 50,000` 时，立即强制中断当前 Agent 任务执行，抛出 `TokenQuotaExceededException`，并触发安全降级响应，向研发大盘发送高危告警。
