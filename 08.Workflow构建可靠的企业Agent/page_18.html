CHAPTER 06

Human-in-the-loop — AI 的安全边界

为什么需要人工确认
LLM 可能误判意图——用户说"帮我看看"，LLM 理解成"下单"。
LLM 可能过度自信——用户还没确认，就直接调了下单接口。
LLM 可能被注入——恶意用户通过提示词诱导 Agent 执行危险操作。

AI 不应该对所有操作都有执行权。
哪些操作需要确认
下单 退款 删除 修改价格 支付
Demo 已覆盖：ConfirmationService.java 完整确认/取消流程。
仅 PPT 讲解：确认超时、并发控制、CSRF 防护、多级审批。
工作流程与持久化挂起
① Agent 决策调用高危 Tool（如 place_order 资金支付）
② 拦截与 Checkpoint 持久化：工作流置入 CONFIRMING，快照落盘 DB/Redis
③ 抛出待确认事件，前端渲染人机审批确认弹窗
④a 用户确认 → Process Rehydration：反序列化 Checkpoint 重建上下文，断点恢复执行
④b 用户取消/超时拒绝 → 状态流转为终态 CANCELLED
API 端点与跨进程恢复
POST /api/agent/workflow/confirm?traceId=trace-xxx&confirmed=true&sessionId=default
Durable Execution 支撑：人工确认往往跨越数分钟甚至数天。依赖 Checkpoint 持久化与 Rehydration，即使后台 Pod 重启或漂移，用户点击确认依然能准确定位快照恢复推进，杜绝任务遗失。
