## Slide Objective
讲清 Demo 到生产的具体差距——每个差距的问题、后果、做法。诚实面对不完美。

## Suggested Presentation
左边三个差距。第一个：持久化 Checkpoint。问题——状态在内存，重启丢失。后果——Agent 执行到一半挂了，用户从头来。我在测试中遇到过：Agent 执行到第 3 步时我重启了服务，回来后 Trace 丢了，workflow 也找不到了。做法——状态序列化到 Redis 或 MySQL。工程上不难，但需要定义"存什么"——WorkflowState、conversationHistory、Tool 执行结果都要序列化。

第二个：分布式 Tracing。问题——Trace 存在内存，重启丢失。后果——多实例部署时，A 实例的 Trace 在 B 实例查不到。做法——接 OpenTelemetry，Trace 数据写入 Jaeger。这不是 Demo 的核心目标，但生产环境必须做——否则出了问题无法回溯。

第三个：SSE 真正流式。问题——Demo 执行完才逐字返回。效果像流式，但不是真正的 LLM streaming。后果——用户体验差，等 5-10 秒空白。做法——LLM 调用改 stream=true + reactive 管道 + Flux<ServerSentEvent>。这是体验优化，不影响功能正确性。

右边三个差距。第一个：确认超时 + 并发控制。问题——确认无超时，单线程无并发。后果——工作流永远挂起；多人同时买最后一件会超卖。做法——5 分钟自动取消 + 乐观锁。乐观锁是在数据库层面加版本号，更新时检查版本号是否变化。

第二个：LLM 成本控制。问题——每次规划/思考都调 LLM，token 费用高。后果——用户量上来后成本爆炸。做法——语义缓存（同样 query 不重复调 LLM）、规划缓存（同样任务不重复规划）、小模型做简单任务。这些是第十一课"AI Gateway 成本治理"的内容。

第三个：超时分级 + 熔断恢复探测。问题——写死 15s 超时；熔断后不探测恢复。后果——简单查询等太久；恢复后又触发熔断。做法——按操作类型分级超时（查询 5s、下单 15s）+ 熔断半开状态探测（先放一个请求试探）。

## Key Emphasis
每个差距都有"问题→后果→做法"的结构。不要只说"缺什么"，要说"缺了会怎样"和"怎么补"。

这页是为架构师准备的——他们需要知道"Demo 到生产还要做什么"。

## Optional Extension
**学员问：这些差距里哪个最优先？**
答：按优先级排：① 确认超时（安全问题）② 持久化 Checkpoint（可靠性）③ 并发控制（正确性）④ SSE 流式（体验）⑤ 成本控制（运营）⑥ 熔断探测（运维）。安全和可靠性优先。

**学员问：乐观锁怎么做？**
答：数据库表加一个 version 字段。更新库存时：UPDATE stock SET stock = stock - 1, version = version + 1 WHERE id = ? AND version = ?。如果 version 变了（被别人改了），更新失败，返回"库存不足"。这就是乐观锁——不需要加锁，靠版本号检测冲突。

## Take Away
Demo 不能解决所有问题，但架构是正确的。诚实面对差距，才能持续改进。
