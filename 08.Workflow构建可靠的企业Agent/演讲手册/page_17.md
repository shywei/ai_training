# page_17 · 三级容错③ 降级 — 触发条件 · 兜底取值 · 失败模式

## Slide Objective
讲透降级的三格：三条触发路径（熔断命中返回 `getDegradationMessage()`、重试耗尽返回 null 后强制收敛、TaskPlanner 失败降级为单步）、兜底取值（降级消息模板、空答案兜底句、脱敏与 trace 留痕）、失败模式（LLM 编造、降级无标记的假成功、故障被降级吞掉）。对应 Demo 的 `ErrorRecovery.getDegradationMessage()` 与 `AgentRuntime.executeToolCall()` / `execute()` 的两条降级分支。

## Suggested Presentation
先纠正一个常见误解：降级不是"报个错"，是**换一条更弱但更稳的路径把请求走完**。Demo 里降级有三条路径，触发点不同、收敛方式不同，必须分开认。

**路径 A · 熔断命中**：`executeToolCall()` 入口查到 `isCircuitBroken()`，直接返回 `errorRecovery.getDegradationMessage(toolName)`——注意返回值不是 null，它会被上层当作"工具结果"塞进对话历史，下一轮 THINK 里 LLM 看到"[系统提示: 工具 X 当前不可用（连续失败 N 次），请基于已有信息回答用户。"自己决定怎么答。**循环不中断**，这是软降级。**路径 B · 重试耗尽**：`executeToolCall()` 返回 null，上层把这个 null 读作降级信号——打 warn 日志、`trace.recordEvent("…降级…")`，然后直接 `buildFinalAnswerPrompt()` 强制收敛出最终回答，循环 break。**路径 C · 规划失败**：TaskPlanner 挂了返回空步骤列表，Runtime 降级为单步执行——任务变糙但流程不断。

兜底取值就三样东西：**降级消息模板**（工具名 + 连续失败次数 + "请基于已有信息回答"）、**空答案兜底句**（"抱歉，处理过程中遇到了问题……"）、**输出仍走 `guardrails.sanitize()` 脱敏**。降级目标写在设计决策里："有回答总比报错好"——但这句话要补后半句：**有标记的弱回答**。

失败模式是这页的重点。第一，**编造**：降级提示词只说"基于已有信息"，没说"不许编"，LLM 拿不到价格就可能编一个价格——对导购场景这是资损级错误。第二，**假成功**：降级回答和正常回答在用户界面上长得一样，用户拿它当真数据用。第三，**故障被降级吞掉**：全链路看起来 200 成功，降级率没人统计，故障在监控里"不存在"。这三条的生产解法一起给：分级降级（缓存兜底 → 简化回答 → 明确报错三档，别一上来就自由发挥）、输出校验（价格/库存字段必须来自工具结果，第四课的结构化输出就是干这个的）、响应带降级标记 + 降级率当 SLO 指标。

设计弯路一条：Demo 为了让学员看清降级逻辑，提示词和兜底都写死在代码里（`getDegradationMessage()` 一个字符串、`execute()` 里一句兜底）。真实系统里"降级说什么"是产品决策不是代码常量——谁定降级文案、降级到什么程度算可接受，这是要在评审里吵清楚的事。

## Key Emphasis
必须讲清：A/B 两条路径的区别（软降级循环继续 vs 强收敛直接出最终回答）；null 是降级信号不是异常；降级回答必须留痕（trace 事件 + 日志 ⚠️）。

不要展开：Guardrails 脱敏的实现细节（page_19/17 的事）、缓存兜底的具体选型。

## Optional Extension
**学员问：降级回答质量这么差，为什么不直接报错让用户重试？**
答：分场景——事实类查询宁可弱答也要标记，资金类操作宁可报错也不能模糊。
Demo 做法：停掉 mcp-knowledge-server 提问，页面返回基于已有信息的回答 + trace 里"降级"事件，学员能看到"弱但不断"的形态；空答案时兜底句兜住，不会白屏。
生产做法：分级降级 + 显式降级标记（响应里 `degraded=true` + 缺了哪个依赖），资金/订单类操作降级为"明确报错 + 引导重试"，绝不模糊回答；降级率、依赖可用性进 SLO 告警。取舍：分级越细代码越多，但"一刀切降级"迟早在某类业务上出事故——按操作风险分级是底线。

**学员问：怎么防止降级时 LLM 编一个价格出来？**
答：靠提示词"自觉"是防不住的，要在输出侧设卡。
Demo 做法：降级消息里明确"请基于已有信息回答"，让学员现场问一个降级中的价格问题，观察 LLM 是说"查不到"还是给数字——猜错的点就是认知缺口。
生产做法：结构化输出 + 字段级校验（第四课）：价格/库存字段必须引用工具结果里的值，校验不过就置空并标注"暂不可用"；提示词层加硬约束"工具报错就说查不到，不要编"。取舍：约束越死长尾问题灵活度越低，但事实类字段宁可呆板不可编造。

## Classroom Interaction
让学员在 Demo 里验一点：熔断触发后（page_24 ④ 的现场保留）再问一次价格，做三处对照——页面回答（有答案、含系统提示痕迹）、`GET /api/agent/workflow/trace` 的 events（"降级"事件 + step 状态）、agent-runtime 日志（⚠️ 降级标记）。让学员回答："这次降级走的是路径 A 还是 B，依据是什么？"

## Take Away
降级是换路径不是报错：软降级（系统提示注入、循环继续）和强收敛（null 信号、直接出最终回答）要分清；降级回答必须带标记、必须留痕、事实字段必须可校验——否则降级就成了故障的隐身衣。

## Why This Slide Matters
跳过这页，学员只会"返回个默认值"式降级：LLM 编造数据、用户拿弱回答当真、故障全被降级吞进 200 OK——出了事故连复盘的证据都没有。

## Transition
三级容错解决的是"工具不可靠"。还有一类问题容错管不了：工具很可靠，但**不该由 AI 自己决定执行**——高风险操作的人在回路。
