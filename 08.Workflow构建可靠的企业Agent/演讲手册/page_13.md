## Slide Objective
讲解三级容错策略——重试、熔断、降级，以及它们在生产环境中的必要性。

## Suggested Presentation
左边是三级容错策略。第一级：重试。最多 3 次，指数退避 1s→2s→4s。为什么是指数退避？因为如果 MCP Server 真的忙了，立即重试只会加重负担。1s、2s、4s 给它喘息的机会。3 次够不够？够了——大多数临时故障在 3 秒内恢复。如果 3 次都不行，大概率是真的挂了。

第二级：熔断。同一工具连续失败 5 次 → 熔断，60 秒内不再调用。为什么 5 次？因为如果是服务宕机，第 1 次失败就该重试，第 2 次可能还是失败，第 3 次基本确认挂了。但为了防止误判（比如网络抖动），等 5 次再熔断。60 秒恢复时间——大多数服务重启在 30 秒内完成。

第三级：降级。熔断后跳过工具调用，让 LLM 基于已有 context 直接回答。"有回答总比报错好"——用户问"MateBook 多少钱"，如果查价格的工具挂了，LLM 可以回答"MateBook 14 是一款轻薄商务本，具体价格请稍后再试"，而不是显示"系统错误"。

右边展示两个实际例子。第一个：MCP Server 临时超时。第 1 次调用超时，等待 1s，第 2 次超时，等待 2s，第 3 次成功。用户无感知。第二个：MCP Server 宕机。连续 5 次失败 → 熔断触发 → 60 秒内跳过该工具 → 降级回答。

底部标注 Demo 已覆盖完整的三级容错。生产还需要：分布式熔断（Redis 共享状态）、熔断恢复探测（半开状态——先放一个请求试探，成功了再全部恢复）。

## Key Emphasis
容错不是"锦上添花"，而是"生产环境的底线"。MCP Server 挂了，Agent 不能跟着一起崩。

三级容错的参数（3 次重试、5 次熔断、60 秒恢复）要解释为什么这么选——不是拍脑袋，是有原因的。

## Optional Extension
**学员问：为什么不用 Resilience4j？**
答：Demo 需要让学员看到容错的完整逻辑，不能藏在框架里。ErrorRecovery 只有 151 行，逻辑清晰。生产环境建议用 Resilience4j 或 Sentinel——它们支持更复杂的策略（限流、bulkhead、分布式熔断）。

**学员问：降级的回答质量会很差吧？**
答：会比正常回答差，但比报错好。降级时 LLM 基于已有 context（画像、记忆、对话历史）回答，可能缺少最新的商品信息。可以优化降级 Prompt——比如告诉 LLM"商品查询服务暂时不可用，基于已有知识回答，不要编造价格"。

**学员问：重试会不会重复执行副作用操作？**
答：会！这是重试的经典问题。查询操作（search_knowledge）重试没问题——幂等的。但写入操作（place_order）重试可能重复下单。Demo 没处理这个问题——生产环境需要幂等设计（请求 ID 去重）。

## Take Away
重试解决临时故障，熔断保护下游服务，降级保证用户体验。三级容错是生产环境的底线。

## Why This Slide Matters
如果跳过这页，学员以为"工具调用失败就报错"是正常的。在企业环境里，工具一定会偶尔失败——容错不是可选项，是必选项。
