# Page 8 — Agent Runtime 全貌：内存执行机制与 Durable Execution 生产演进

## Slide Objective
全面展示 Agent Runtime 的执行全景，并明确划清 **Demo 内存执行机制（单机教学基线）** 与 **Durable Execution 生产演进（高可用架构）** 的边界；系统化阐述 **“三级自动容错（重试 + 熔断降级 + 错误重规划）+ 人工接管（HITL）”** 的协同纵深防御体系。

## Suggested Presentation

### 一、架构边界明确化：Demo 内存执行 vs 生产 Durable Execution 完整概念
各位学员，第八课是可靠性工程的核心。在理解 Runtime 全景时，请务必建立清晰的工程边界意识：
- **Demo 现状（v1.5 落地）：** 采用**单机内存执行模型**。内存 7 状态机流转、基于 `ConcurrentHashMap` 记录本地 Trace、单步推进 `TaskPlanner` 结构化子任务清单。这种设计极度轻量、零外部存储依赖，非常便于学员在 IDE 里打断点单步调试；
- **生产演进（Durable Execution 完整概念体系）：**
  很多工程师容易产生一个误解：“把 Agent 当前的会话状态存进数据库，就是 Durable Execution 了。”**绝对不是！**
  必须严格厘清三层边界：
  1. **Chat History**：仅仅保存多轮对话文本记录（第 05 课 Redis/MySQL）；
  2. **Agent State Store**：保存 Agent 当前运行态变量与会话属性；
  3. **Execution Checkpointer**：真正的**可恢复任务执行检查点**。
  真正的 Durable Execution 必须包含四大核心要素：
  - **步骤与副作用持久化**：不仅保存状态变量，还必须记录已完成步骤的输入、输出以及外部工具调用的返回值；
  - **故障恢复与确定性重放（Replay）**：进程宕机后，异地节点反序列化复水恢复（Process Rehydration），重放时直接跳过已完成步骤，**坚决避免对外部系统的写操作产生重复副作用（如重复下单扣款）**；
  - **外部调用幂等控制**：外部 API 必须结合分布式唯一幂等键与 Saga 补偿机制；
  - **长任务安全休眠与唤醒**：在进入 HITL 人工审批时，任务可安全休眠数小时甚至数天，审批通过后由 Webhook 触发原位唤醒续跑。

### 二、Demo 内存执行主链路（左侧）
1. **① 请求装配与 Trace 生成：** 用户请求进入，生成本地 `traceId`，装配短期会话上下文与知识库检索结果；
2. **② TaskPlanner 结构化任务清单：** 针对复杂多步任务，通过 Prompt 将目标拆解为结构化子任务清单（线性步骤），并由确定性 FSM 校验前置条件；
3. **③ 内存 7 状态机与受控 ReAct 循环：** 严格按照 `THINK → ACT → OBSERVE` 推进，设置 10 轮安全硬上限，防范死循环与 Token 熔断；
4. **④ 最终回复与状态收敛：** 回复脱敏、沉淀记忆，将状态机收敛至不可逆终态 `COMPLETED`。

### 三、三级自动容错 + 错误重规划 + 人工接管协同防御体系（右侧）
在分布式生产环境中，单点错误绝不能仅靠简单的“重试”一招鲜吃遍天，必须构建分层协同的纵深防御体系：
1. **自动容错 ①：重试机制（Retry）— 处理瞬态网络故障**
   - **应对场景：** 网络闪断、偶发读超时等瞬态抖动；
   - **工程策略：** 最多重试 3 次，指数退避（1s → 2s → 4s）+ 随机抖动（Jitter）。严格限制仅对幂等操作重试，非幂等操作严禁重试防重复扣款。
2. **自动容错 ②：熔断机制（Circuit Breaker）— 防止故障持续扩散**
   - **应对场景：** 下游企业微服务或数据库持续宕机；
   - **工程策略：** 连续 5 次失败开启熔断 60 秒，直接阻断对下游物理冲击，半开探测，防止级联雪崩。
3. **自动容错 ③：服务降级兜底（Fallback）— 提供替代结果或保底响应**
   - **应对场景：** 服务熔断或严重不可用；
   - **工程策略：** 跳过宕机工具，使用备用轻量模型生成兜底说明或调用静态模板，保证核心主干不中断。
4. **额外任务恢复策略：错误重规划（Error Replanning）— 重新规划失败任务路径**
   - **应对场景：** 工具返回确定性业务不可用阻断（如“商品已下架”、“库存不足”）；
   - **工程策略：** 单纯重试毫无意义，Runtime 将业务错误作为观测反馈（Observation）回填大模型上下文，驱动 `TaskPlanner` 动态重排剩余子任务清单，实现业务动态自愈。
5. **终极安全防线：人工接管（Human-in-the-Loop, HITL）— 业务决策授权与高危阻断**
   - **应对场景：** 自动容错手段全部耗尽、重规划死循环或命中资金扣款等高危破坏性操作；
   - **工程策略：** 状态机安全挂起为 `CONFIRMING` 状态，派发企业工单通知人工介入审核。

---

### 四、核心分工收口
**Runtime 是操作系统的“内核调度器”**：负责状态流转、Checkpoint 恢复与容错兜底；
**LLM 是“认知推理单元”**：负责思考与决策输出，但**绝不能越权直接管理和操作执行流程**。

## Key Emphasis
1. **讲清 Demo 与生产边界**：Demo 是内存执行与线性清单，生产是 Durable Execution 持久化快照与 DAG 依赖拓扑。
2. **统一术语表达**：严格表述为“三级自动容错（重试 + 熔断降级 + 错误重规划）+ 人工接管（HITL）”。
3. **四个兜底出口不可少**：最大轮次强停、工具失败降级、LLM 返回空兜底、超轮次强制总结。

## Take Away
Runtime 是内核，LLM 是算力。内存闭环跑 Demo，Durable 快照保生产。三级自动容错解故障，人工接管托底线。
