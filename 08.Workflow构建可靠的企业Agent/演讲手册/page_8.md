## Slide Objective
展示 Agent Runtime 的完整执行流程——从用户请求到最终回复的全链路。

## Suggested Presentation
看左边的流程。用户请求进来，第一步创建 Trace（记录开始），构建 context（画像+记忆+RAG）。这一步和第七课的 MemoryManager.buildContext() 是一样的——复用了 v4.0 的代码。

第二步 TaskPlanner 判断是否需要规划。我在做 Demo 时发现一个有趣的现象：不是所有任务都需要规划。"你好"、"推荐一台笔记本"这种简单任务，一次 THINK 就能回答。只有"帮我对比 A 和 B"、"推荐几个"这种多步骤任务才需要拆步骤。TaskPlanner 用关键词判断——包含"对比""比较""帮我选"等词才规划。这个设计让简单任务不走规划，节省了一次 LLM 调用。

但要跟学员说实话：关键词永远补不全。我实测"分析一下游戏本和轻薄本的区别"就没命中——句子里没有"对比""比较"，是学员提出来我才补的"区别/差异/分析"。补丁永远打不完。所以生产的标准做法是混合路由：规则做快路径（命中就直接规划，零成本、确定性），没命中时用快模型做一次语义分类兜底（"这个任务需要多步吗？"）。规则保证速度和可测试性，LLM 保证覆盖率。反过来也要防误触发——"帮我看看价格"这种单步任务被拆成三步，白白多花两次 LLM 调用。

第三步进入 ReAct 循环。THINK→ACT→OBSERVE，最多 10 轮。为什么是 10 轮？因为我在测试中发现，超过 5 轮基本都是在死循环。10 轮是安全上限——足够完成复杂任务，又不会无限循环。

第四步输出最终回复。脱敏、保存记忆、返回用户。

右边讲循环中的异常处理。工具调用失败 → ErrorRecovery 介入，重试/熔断/降级。高风险操作 → ConfirmationService 拦截，暂停等待确认。达到最大循环次数 → 强制让 LLM 基于已有信息总结回复。LLM 返回空 → 结束循环，用已有 context 生成兜底回复。

底部的核心思想：Runtime 是 Agent 的"操作系统"——管理资源、调度任务、处理异常。LLM 是"CPU"——负责推理，但不能直接管理自己。

## Key Emphasis
四个异常处理分支都要讲——它们是"可靠"的保障。特别是"达到最大循环次数"和"LLM 返回空"这两个兜底分支——没有它们，Agent 可能永远不返回。

TaskPlanner 的触发条件要讲清楚——不是所有任务都规划，简单任务直接走 ReAct 循环。同时要讲清关键词方案的边界和生产做法（混合路由）——这是课程计划里"Demo vs 生产差距"的要求，不能让学员以为关键词就是终态。

## Optional Extension
**学员问：为什么是 10 轮不是 20 轮？**
答：实测数据。我用"帮我对比拯救者和 MacBook 的价格"测试，3 轮完成。用"帮我找一台适合剪视频的笔记本"测试，2 轮完成。超过 5 轮的基本都是死循环。10 轮是安全上限。

**学员问：TaskPlanner 规划失败怎么办？**
答：TaskPlanner.plan() 返回空列表，AgentRuntime 降级为单步执行——不规划，直接走 ReAct 循环，一次 THINK 就回答。这个降级逻辑很重要——规划失败不能让整个任务失败。

**学员问：为什么不把 ReAct 循环放在 Spring AI 的 Advisor 里？**
答：Advisor 是"增强"，不是"控制"。Advisor 可以在请求前后加逻辑，但不能控制循环次数、不能插入确认步骤、不能处理重试。ReAct 循环需要自己控制——这就是手搓的价值。

## Take Away
Runtime 是 Agent 的操作系统——管理循环、处理异常、控制行为边界。
