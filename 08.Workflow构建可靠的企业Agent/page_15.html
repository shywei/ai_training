CHAPTER 05 · 三级容错 1/3

① 重试（Retry）— 触发条件 · 参数取值 · 失败模式

■ 触发条件（什么时候重试）
· 位置：AgentRuntime.executeToolCall() 的 while(true) 循环内
· callToolDirectly() 抛异常、或返回 null（视为失败）→ 进 catch
· ErrorRecovery.shouldRetry(step)：retryCount < MAX_RETRY 才继续
· 只对瞬时故障划算（超时 / 连接失败）；参数错误重 3 次还是错
■ 参数取值（为什么是这些数）
· MAX_RETRY = 3，计数在 WorkflowStep.retryCount（每步独立）
· 退避 getRetryDelayMs() = 2^retryCount × 1000 → 1s / 2s / 4s（指数退避，给下游喘息）
· 成功即 recordSuccess() 清零；失败先 recordFailure() 记进熔断计数
· 等待是 Thread.sleep 同步阻塞——请求线程被占住
■ 失败模式（重试会怎么坏）
· 重试耗尽 → step.fail("重试耗尽")、返回 null → 上层降级为直接回答（见第 3 页）
· 重试放大：非幂等操作（place_order）重复执行 = 重复副作用；Demo 下单无幂等键，两次下单两个 ORD- 时间戳
· 退避无抖动：并发请求同时睡、同时醒 → 惊群，下游刚恢复又被打
代码锚点 — ErrorRecovery.java + AgentRuntime.executeToolCall()
// ErrorRecovery.java
static final int MAX_RETRY = 3;
public boolean shouldRetry(WorkflowStep step) {
  return step.getRetryCount() < MAX_RETRY;
}
public long getRetryDelayMs(WorkflowStep step) {
  return (long) Math.pow(2, step.getRetryCount()) * 1000; // 1s / 2s / 4s
}

✗ Demo vs 生产 · 三格
✗ 重试不配幂等与预算
问题：对写操作重试 = 重复下单 / 重复扣款；每层各自重试，总耗时按层数指数相乘。
不解决：一次"容错优化"直接造成资损，或整条链路超时雪崩。
怎么解决：读写分开——只读自动重试；写操作先有幂等键（第七课幂等页）再重试。链路 deadline 向下传递，剩余预算不足就不重试；退避加 ±随机抖动；熔断打开时重试直接短路。
取舍：幂等键要全链路传参、要存去重表；抖动牺牲一点可复现性。
