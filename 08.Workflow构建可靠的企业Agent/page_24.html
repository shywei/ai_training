CHAPTER 08

🧪 可在 Demo 验证哪些点 — 状态机 · 三级容错 · 人在回路 · 追踪

① 简单/复杂自动分档（Runtime 说了算）
POST /api/agent/workflow?message=&sessionId=&userId=： 发"推荐一台笔记本"→ mode=simple、stepCount=1； 发"帮我对比游戏本和轻薄本的区别"（命中 TaskPlanner.needsPlanning() 关键词）→ mode=workflow、stepCount≥2。 前端不判断复杂度。
② 计划先行，执行前 trace 就有全貌
复杂任务先规划后执行：GET /api/agent/workflow/trace?traceId= 里 steps 全部提前登记（recordStepCreated）， 每步带 llmThought / toolName / toolInput / toolOutput / durationMs，出问题可逐步回溯。
③ 重试与指数退避（第 1 级）
停掉 mcp-knowledge-server 再提问：日志 [ErrorRecovery] 重试等待 …ms (第 N 次重试)（getRetryDelayMs() 的 2^n×1000）； trace 事件 "Step N 重试第 N 次: …"，steps[].retryCount 递增。
④ 熔断触发（第 2 级）
连续触发 5 次失败：日志 ⚡ 工具 search_knowledge 触发熔断！暂停 60 秒； GET /api/agent/workflow/circuit-breaker → {failureCount:5, circuitBroken:true, lastError:…}， 再调用直接跳过（不发请求）。
⑤ 熔断恢复 + 手动复位（简化半开）
60 秒后再请求：日志 [ErrorRecovery] 工具 search_knowledge 熔断恢复，重新尝试，计数清零放行（无探测请求，是简化版）； POST /api/agent/workflow/circuit-breaker/reset 可立即复位。
⑥ 降级有回答 + 留痕（第 3 级）
熔断后页面仍给回答（不是报错、不是白屏）；trace events 有 "…降级…"，对应 step 为 SKIPPED / FAILED；回答里能看到系统提示 "工具 X 当前不可用…请基于已有信息回答用户"。
⑦ 人在回路 — 高风险必须确认
说"我要买拯救者"→ 响应 status=confirming / confirmRequired=true / pendingTool=place_order； POST /api/agent/workflow/confirm?traceId=&confirmed=true|false 才继续/取消，trace 事件 "Step N 等待用户确认"。
⑧ 现状自证 — 治理缺口就在眼前
重启 agent-runtime 再查 GET /api/agent/workflow/trace → not_found（Trace 是内存 ConcurrentHashMap）； 确认后执行的下单不再走重试/熔断（resumeAfterConfirm 直接 callToolDirectly）； 连点两次下单两个 ORD- 时间戳 = 无幂等键；trace 的 state 里找不到 RETRYING（声明未使用，重试只体现在 retryCount 与事件）。
