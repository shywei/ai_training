CHAPTER 05 · 三级容错 2/3

② 熔断（Circuit Breaker）— 触发条件 · 参数取值 · 失败模式

■ 触发条件（什么时候熔断）
· 每次失败 recordFailure() 按工具名计数（ConcurrentHashMap<String, ToolFailureInfo>）
· 同一工具连续失败 ≥ 5（CIRCUIT_BREAKER_THRESHOLD）→ 熔断
· 下一次调用入口 isCircuitBroken() = true → 不发请求，直接跳过
· 一次成功 recordSuccess() 整桶清零——"连续失败"语义
■ 参数取值（为什么是这些数）
· 阈值 5 次：防误判（网络抖动一两次不熔断），又不让宕机下游被持续打
· 恢复窗口 CIRCUIT_BREAKER_RECOVERY_MS = 60_000（60 秒），自最近一次失败起算
· 恢复动作在 isCircuitBroken() 里做：elapsed ≥ 60s → 日志"熔断恢复，重新尝试"、计数清零、放行
· 计数与恢复时间都在本进程内存（常量，不可配）
■ 失败模式（熔断会怎么坏）
· 半开是简化版：60 秒到点放行全部流量，没有"先放一个探测"；下游没好 → 再攒 5 次 → 开/关震荡
· 状态不共享：多实例各自熔断，宕机下游仍被其余实例打死
· 不分错误类型：参数错也计数；连续计数被一次成功清零 → 10% 慢故障永远熔不掉
代码锚点 — ErrorRecovery.java + AgentRuntime.executeToolCall() 入口
// ErrorRecovery.java
static final int CIRCUIT_BREAKER_THRESHOLD = 5;
static final long CIRCUIT_BREAKER_RECOVERY_MS = 60_000;

public boolean isCircuitBroken(String toolName) {
  if (info.failureCount < THRESHOLD) return false;
  long elapsed = now - info.lastFailureTime;
  if (elapsed >= RECOVERY_MS) { // 简化半开：到点清零放行
    info.failureCount = 0; return false;
  }
  return true;
}

// AgentRuntime.executeToolCall() — 先查熔断，再谈调用
if (errorRecovery.isCircuitBroken(toolName)) {
  step.skip("工具已熔断，降级为跳过");
  return errorRecovery.getDegradationMessage(toolName);
}
✗ Demo vs 生产 · 三格
✗ 进程内熔断 + 到点放行，无半开探测
问题：恢复点直接放大全部流量，下游没恢复就再来一轮失败；状态只在单进程，多实例不共享。
不解决：开/关震荡，下游重启窗口被反复打死；故障率统计失真。
怎么解决：显式三态 closed / open / half-open——半开只放 N 个探测请求，成功才闭合（Resilience4j CircuitBreaker / Sentinel）；滑动窗口计数 + 错误分类（超时/限流/业务错分开）；多实例状态放 Redis 共享，或每实例独立但由网关全局限流兜底。
取舍：分布式状态多一次 Redis 往返与一致性问题；探测期少量请求仍会失败——这是恢复的必要成本。
