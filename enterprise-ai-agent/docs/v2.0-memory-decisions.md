# v2.0-memory 设计决策记录

## 验证目标
第五课（Memory：让 Agent 记住用户）的所有核心技术点。

## 设计决策

### 1. Session 和 User 怎么区分？
**决策**：sessionId 管对话历史（Redis），userId 管用户画像（MySQL），两个独立维度。
**原因**：同一个用户可以有多个对话 Session，画像应该跨 Session 生效。用 sessionId 查画像会丢失跨 Session 的信息。
**PPT 影响**：必须讲清楚"Session 存什么、User 存什么"，不能混为一谈。

### 2. 上下文怎么注入 Prompt？
**决策**：`MemoryManager.buildContext(sessionId, userId)` 统一构建，一次调用返回"用户画像 + 对话历史"的合并字符串，注入 `PromptManager.buildUserPrompt()` 的 context 参数。
**原因**：第四课留的 context 扩展点在这里第一次填充。统一由 MemoryManager 构建，Controller 只调一次。
**PPT 影响**：重点讲 context 参数的演进——v1.0 null → v2.0 对话历史+画像 → v3.0 +RAG → v4.0 +Tool。

### 3. 用户画像存在哪？
**决策**：MySQL，MyBatis Plus（不用 JPA）。
**原因**：用户指定技术栈。建表用 SQL 脚本，不用 JPA 自动 DDL。
**PPT 影响**：存储选型章节要讲 MySQL vs Redis vs Vector DB 的适用场景。

### 4. 画像抽取用什么模型？
**决策**：推理模型（Qwen3-8B），从 `agent.model.extract` 配置读取。
**原因**：画像抽取需要输出严格 JSON，小模型格式经常出错。压缩用快模型（`agent.model.summary`）就够了。
**PPT 影响**：要讲清楚"不同任务用不同模型"——压缩用快模型、抽取用推理模型，不能一刀切。

### 5. 画像抽取什么时候触发？
**决策**：两种触发方式——用户主动说"记住"时立即触发，会话结束（退出/清空）时兜底触发。不用消息条数触发。
**原因**：按条数触发不自然——用户没说要记住，你就在后台分析他的对话，感觉是"偷窥"。用户主动表达意图时触发更合理，也更符合实际产品设计。会话结束时做兜底抽取，确保不遗漏。
**PPT 影响**：不要讲"每N条触发一次"，要讲"用户主动触发 + 会话结束兜底"。

### 6. 画像更新还是覆盖？
**决策**：合并更新——旧画像传给 LLM，LLM 根据新对话生成合并后的画像。空值不覆盖。
**原因**：直接覆盖会丢失历史信息。让 LLM 看到旧画像 + 新对话，自主决定保留什么、更新什么。
**PPT 影响**：要讲清楚"画像不是一次性抽取，而是持续合并演进的"。

### 7. 上下文压缩怎么触发？
**决策**：在 `MemoryManager.buildContext()` 里内联检查，消息数超过 8 条时触发。阈值从 12 改为 8，方便演示。
**原因**：实际项目中应该异步触发（不阻塞用户请求），但 Demo 里同步更直观。8 条阈值比 12 条更容易在演示中看到效果。
**PPT 影响**：要讲清楚实际项目中应该用异步定时任务，Demo 为了演示直观用了同步。

### 8. 压缩策略是什么？
**决策**：累积压缩——新摘要 = 旧摘要 + 新对话，不是每次从头压缩。压缩后保留 1 条摘要 + 4 条最近原文。
**原因**：每次从头压缩会丢失早期信息。累积压缩保证摘要越来越完整。阈值 8、保留 4 是为了演示方便，实际项目可以更大。
**PPT 影响**：要画出"12→7→12→7"的波浪式压缩过程，强调"累积不丢失"。

### 9. 用户登录怎么做？
**决策**：MySQL 用户表 + AuthController（登录/注册接口）+ 前端登录页。
**原因**：用户要求"真实一点"。纯 localStorage 的身份识别太假，有数据库支撑的登录更接近实际项目。
**PPT 影响**：可以提一句"身份识别是 Memory 的前提"，但不要花太多时间讲登录实现。

### 10. LLM 交互日志怎么分？
**决策**：分两个日志文件——`llm-chat.log`（对话）和 `llm-summary.log / llm-profile.log`（画像抽取+压缩）。
**原因**：混在一起不方便演示。分开后可以单独展示"画像抽取的完整过程"。
**PPT 影响**：演示时可以打开 `llm-summary.log / llm-profile.log`，让学生看到画像抽取的 Prompt、旧画像、对话历史、LLM 返回。

## 发现的问题

### 小模型 JSON 输出不稳定
Qwen2.5-7B 返回的 JSON 经常格式错误（值不加引号、多余逗号）。画像抽取必须用推理模型，或者给非常严格的 Prompt 模板。我们最终用推理模型 + 给空 JSON 模板让 LLM 填值。

### PromptManager 接口设计验证
第四课留的 context 扩展点（`buildUserPrompt(message, context)`）在第五课顺利填充。接口不需要改，只是 context 从 null 变成了有内容的字符串。**这个设计是正确的，后续课程继续验证。**

### Redis key 设计
Session 的 Redis key 用 `session:{sessionId}:messages`，List 结构。滑动窗口用 LPOP 裁剪。简单有效，但大量用户时需要考虑 Redis 内存。

## PPT 调整建议

基于 Demo 验证，第五课 PPT 应该调整的点：

1. **Memory Architecture 图**：重点讲 sessionId vs userId 的分离，不能混为一谈
2. **context 注入**：用实际日志展示 context 从 null 到有内容的变化
3. **画像抽取触发**：不要讲"按条数触发"，讲"用户主动 + 会话结束"
4. **模型选择**：不同任务用不同模型——压缩用快模型、抽取用推理模型
5. **压缩策略**：画出累积压缩的过程图，强调"不丢失历史"
6. **存储选型**：Redis vs MySQL vs Vector DB 的选型决策树
7. **llm-summary.log / llm-profile.log**：演示时打开日志文件，让学生看到画像抽取的完整链路
