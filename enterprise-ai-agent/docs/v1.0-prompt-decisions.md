# v1.0-prompt 设计决策记录

## 验证目标
第四课（LLM 交互工程）的所有核心技术点。

## 设计决策

### 1. 模型路由放在哪一层？
**决策**：独立的 `ModelRouter` 组件，Controller 层调用。
**原因**：路由逻辑应该和业务逻辑分离。如果放在 ChatClient 里，换框架就要重写。
**PPT 影响**：模型路由应该作为独立章节讲，不要塞在 API 调用里。

### 2. Self-Correction 放在哪一层？
**决策**：放在 Controller 层，用 try-catch 模式。
**原因**：Self-Correction 本质上是"输出不合法 → 重新调用"的重试逻辑，不是 LLM 内部的事。
**PPT 影响**：Self-Correction 应该强调是"服务端重试"，不是"LLM 自己纠错"。

### 3. Guardrails 放在哪一层？
**决策**：独立的 `GuardrailsService`，在 Controller 入口和出口都调用。
**原因**：入口防 Injection，出口防泄露。两层防护不能合并。
**PPT 影响**：Guardrails 应该讲"入口检查 + 出口过滤"两道防线。

### 4. 结构化输出用什么方案？
**决策**：先用提示词约束 JSON 格式，再用代码验证。不依赖 Spring AI 的 Structured Output（因为不是所有模型都支持）。
**原因**：提示词约束是最通用的方案，代码验证是兜底。
**PPT 影响**：应该讲两种方案——提示词约束（通用）和 API 原生 Structured Output（特定模型），以及各自的适用场景。

### 5. Prompt Template 怎么管理？
**决策**：用 Java Text Block（"""）+ 变量替换。
**原因**：v1.0 阶段够用。后续版本会升级到外部模板文件 + 版本管理。
**PPT 影响**：可以提 Text Block 的便利性，但也要指出企业级应该用外部模板。

## 发现的问题

### Spring AI 版本
Spring AI 1.0.0-M4 还是 milestone 版本，API 可能有变化。需要关注正式版发布。

### Streaming + Guardrails
流式输出时，Guardrails 不能逐 chunk 检查（会截断句子）。需要在流结束后做整体检查，或者只在首个 chunk 做 Injection 检查。

### JSON Schema 验证
手动解析 JSON 比较脆弱。后续应该引入 JSON Schema Validator 库（如 everit-json-schema）。

## PPT 调整建议

基于 Demo 验证，第四课 PPT 应该调整的点：

1. **模型路由**：从"提一下"升级为"重点讲"——这是企业成本控制的关键
2. **Self-Correction**：强调是"服务端重试模式"，不是"LLM 自动纠错"
3. **Guardrails**：讲"入口 + 出口"两道防线，不要只讲 Injection 防御
4. **Streaming**：需要讲清楚 Streaming + Guardrails 的冲突和解决方案
