# v4.0-tool 设计决策记录

## 验证目标
第七课（Tool Calling: 连接企业系统）的核心技术点：Function Calling、Tool Runtime、LLM 路由、MCP 协议、数据分层闭环。

---

## 设计决策

### 1. Function Calling 用哪种方式定义？

**决策**：`FunctionCallbackWrapper` + `java.util.function.Function`（编程式）

**原因**：
- Spring AI 1.0.0-M4 没有 `@Tool` 注解（`@Tool` 在 GA 版本才引入）
- M4 的标准做法是 `FunctionCallbackWrapper.builder(function).withName().withDescription().build()`
- 注册为 Spring Bean，ChatClient 通过 `.functions()` 引用

**对比**：
- `@Tool` 注解（1.0.0+）：声明式，更简洁，自动提取 JSON Schema
- `FunctionCallbackWrapper`（M4）：编程式，更灵活，手动控制 Schema
- Demo 用 M4 兼容方式，保持和前几课的 Spring AI 版本一致

**PPT 影响**：要讲清楚两种方式的区别，以及为什么 Demo 用编程式。

### 2. LLM 路由替代关键词过滤

**决策**：用快模型（Qwen2.5-7B）判断意图，替代第六课的关键词过滤。

**路由类型**：
- `KNOWLEDGE`：需要检索商品知识（"推荐笔记本"、"有什么手机"）
- `TOOL`：需要查价格/库存（"多少钱"、"有货吗"）
- `CHAT`：普通聊天（"你好"、"今天天气怎么样"）

**原因**：
- 关键词过滤无法理解语义（"帮我看看那个笔记本"不含"推荐"但需要检索）
- LLM 路由用语义理解判断意图，准确率更高
- 成本：每次路由多一次 LLM 调用，但用最便宜的快模型（~100 token）

**实现**：`LlmRouter.java`，独立组件，和业务逻辑分离。

**PPT 影响**：这是第七课的核心教学点——LLM 不仅能回答问题，还能判断"该做什么"。

### 3. MCP 协议统一所有数据访问

**决策**：agent-runtime 不直接访问任何数据库，所有数据操作通过 MCP 协议。

**两个 MCP Server**：

| MCP Server | 端口 | 职责 | 数据源 |
|------------|------|------|--------|
| mcp-product-server | 8081 | 商品实时数据查询 | MySQL |
| mcp-knowledge-server | 8082 | 知识检索 + 记忆读写 + 画像读取 + 知识索引 | pgvector + MySQL |

**mcp-knowledge-server 能力清单**：

| 类型 | 名称 | 说明 |
|------|------|------|
| Tool | search_knowledge | 商品知识语义检索（RAG） |
| Tool | search_memory | 用户记忆语义检索 |
| Tool | save_memory | 写入用户记忆 |
| Tool | index_knowledge | 索引商品知识库 |
| Resource | user://{userId} | 读取用户画像 |

**为什么不用本地 FunctionCallback**：
- 从 Agent 设计规范看，Tool 应该通过标准协议暴露
- MCP 是 Tool 的标准化方式，其他 Agent 也能复用
- 本地 FunctionCallback 是框架实现细节，不是架构设计
- 生产中即使 Tool 和 Agent 同进程，也应走 MCP

**教学价值**：
- 统一架构，干净清晰
- MCP Server 独立部署，体现企业微服务架构
- agent-runtime 只负责 LLM 交互和路由，不碰数据

### 4. Tool vs Resource 的分工

**决策**：动态操作用 Tool，静态上下文用 Resource。

| MCP 概念 | 用途 | Demo 中的使用 |
|----------|------|--------------|
| Tool | 搜索、写入、计算 | search_knowledge / search_memory / save_memory / index_knowledge / queryProductInfo |
| Resource | 会话级上下文数据 | user://{userId} 用户画像 |

**为什么用户画像是 Resource 不是 Tool**：
- 画像在会话开始时加载一次，不需要每次对话都调用
- 画像相对稳定，适合"读取上下文"语义
- 不需要 LLM 决策是否读取，Client 启动时自动获取

**为什么用户记忆是 Tool 不是 Resource**：
- 记忆会持续增长，全量加载不现实
- 需要语义搜索（按 query 匹配），不是简单读取
- save_memory 需要 LLM 主动决策何时写入

**PPT 影响**：Tool vs Resource 是 MCP 协议的核心概念，Demo 用具体例子讲清楚。

### 5. save_memory 跨路由注册

**决策**：save_memory 作为 FunctionCallback，在所有路由下都注册给 LLM。

**原因**：
- 用户在任何对话中都可能表达偏好（"我预算8000"、"我喜欢轻薄本"）
- 不限于 TOOL 路由，CHAT 路由下 LLM 也应该能保存记忆
- 和 queryProductInfo 不同（只在 TOOL 路由注册）

**实现**：
- McpKnowledgeClient.discoverTools() 将 save_memory 包装为 FunctionCallback
- ShoppingAgentController 中，TOOL 路由注册 product tools，所有路由都注册 knowledge tools
- PromptManager 的「记忆使用规则」引导 LLM 何时调用

**PPT 影响**：讲"Tool 不是只有 TOOL 路由才能用"——跨路由 Tool 是更灵活的设计。

### 6. Tool 注册方式

**决策**：MCP Tool 自动发现 + FunctionCallbackWrapper 包装。

**Tool 来源**：
| 来源 | 注册方式 | 路由 |
|------|---------|------|
| mcp-product-server | McpProductClient.getFunctionCallbacks() | 仅 TOOL |
| mcp-knowledge-server (save_memory) | McpKnowledgeClient.getFunctionCallbacks() | 所有路由 |

**实现**：
- MCP Client 启动时连接 Server，获取 Tool 列表
- 将 MCP Tool 转换为 FunctionCallback，注册到 ChatClient
- MCP Server 未启动时优雅降级（不影响 Agent 正常运行）

### 7. 数据分层闭环

**决策**：商品描述 → pgvector（RAG），价格/库存 → MySQL（Tool），记忆 → pgvector（MCP Tool），画像 → MySQL（MCP Resource）。

**v4.0 完整数据流**：
```
用户: "推荐一台笔记本，预算8000"
  ↓
LlmRouter → KNOWLEDGE
  ↓
context 构建：
  画像 ← MCP Resource: user://U001
  记忆 ← MCP Tool: search_memory("U001", "笔记本推荐")
  RAG  ← MCP Tool: search_knowledge("推荐笔记本")
  ↓
LLM 基于 context 推荐

用户: "多少钱？有货吗？"
  ↓
LlmRouter → TOOL
  ↓
LLM 调用 mcp_queryProductInfo("NB008")
  ↓
MCP Tool 返回: "价格 7999 元，库存 67 件，在售"
  ↓
LLM 整合回复

用户: "记住我更喜欢这个"
  ↓
LlmRouter → CHAT（但 save_memory 可用）
  ↓
LLM 调用 mcp_save_memory(user_id="U001", memory_type="preference", content="更喜欢 ThinkPad T14s")
```

### 8. context 演进

**v4.0 context 完整形态**：
```
用户画像（MCP Resource: user://{userId}）
+ 用户记忆（MCP Tool: search_memory）
+ 对话历史（Redis 工作缓冲区）
+ RAG 检索结果（MCP Tool: search_knowledge，仅 KNOWLEDGE 路由）
+ Tool 调用结果（LLM 自动调用，仅 TOOL 路由）
```

**变化**：
- 所有持久化数据统一通过 MCP 协议访问
- MemoryManager 不直接依赖任何 Mapper 或数据库组件
- RAG 不再自动注入，由 LLM 路由决定（KNOWLEDGE 才注入）
- Tool 结果由 LLM 框架自动处理（不需要手动注入 context）

### 9. 前端 Tool 调用可视化

**决策**：SSE 流中增加 `[ROUTE]` 和 `[TOOL_CALL]` 事件标记。

**原因**：
- 学员需要看到"LLM 正在调用工具"这个过程
- 后端日志可以看到，但前端可视化更直观
- `[ROUTE]` 显示意图分类，`[TOOL_CALL]` 显示调用了什么工具

**实现**：
- 后端：在 Flux.concat 中插入 `[ROUTE]` 事件
- 前端：解析 SSE 事件，显示路由标签和 Tool 调用指示器

### 10. agent-runtime 清理

**决策**：删除 agent-runtime 中所有直接数据库访问代码。

**删除的文件**：
| 文件 | 原因 |
|------|------|
| KnowledgeController | 索引 API 迁移到 MCP Tool index_knowledge |
| KnowledgeService | 空壳类 |
| RetrievalService | RAG 检索迁移到 MCP Tool search_knowledge |
| VectorStoreConfig | pgvector 数据源配置，agent-runtime 不再连接 PostgreSQL |
| UserMemoryMapper | 记忆读写迁移到 MCP Tool search_memory / save_memory |
| UserMemory | UserMemoryMapper 的实体类 |
| ProductInfo | 商品查询迁移到 MCP Tool queryProductInfo |
| ProductInfoMapper | 同上 |

**pom.xml 清理**：
- 移除 `spring-ai-pgvector-store-spring-boot-starter`
- 移除 `postgresql` 驱动
- 保留 `spring-ai-openai-spring-boot-starter`（ChatModel / ChatClient / OpenAiChatOptions）

**application.yml 清理**：
- 移除 `spring.datasource.pgvector.*`
- 移除 `spring.ai.vectorstore.pgvector.*`
- 移除 `spring.ai.openai.embedding.options.model`
- 保留 MCP 连接配置

## 发现的问题

### Spring AI 1.0.0-M4 没有 @Tool 注解
M4 版本没有 `@Tool` 和 `@ToolParam` 注解。使用 `FunctionCallbackWrapper` + `java.util.function.Function` 方式。

### MCP Java SDK 1.1.3 独立于 Spring AI
MCP Java SDK 的 Spring 集成（mcp-spring-webmvc）已移至 Spring AI 2.0+。MCP Server 使用核心 mcp 模块自带的 HttpServletSseServerTransportProvider。

### spring-ai-pgvector-store-spring-boot-starter 自动配置冲突
如果 pom.xml 中保留此依赖但没有配置 PostgreSQL 数据源，Spring Boot 启动会失败。必须在 MCP 化后移除此依赖。
