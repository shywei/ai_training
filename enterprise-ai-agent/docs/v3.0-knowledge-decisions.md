# v3.0-knowledge 设计决策记录

## 验证目标
第六课(Knowledge:企业知识系统与 RAG)的核心技术点,以及向量数据库对记忆系统的增强。

---

## 设计决策

### 1. 向量数据库选哪个?

**决策**:pgvector(PostgreSQL 扩展)

**原因**:
- 学员企业大概率已有 PostgreSQL,不引入新基础设施
- SQL 生态复用,可以用 SQL 直接查询向量
- Spring AI 有原生 `PgVectorStore` 集成
- 生产可用,不是玩具方案

**对比**:
- Chroma:最轻(pip install),但企业不用,学习价值低
- Milvus:性能最强,但需要独立部署,培训场景偏重
- Elasticsearch:企业已有,但资源重

**PPT 影响**:向量数据库选型章节要讲"为什么选 pgvector"--不是技术最先进的,而是最贴合企业现状的。

### 2. 独立数据源还是复用 MySQL?

**决策**:pgvector 用独立的 PostgreSQL 数据源,不和 MySQL 混用。

**原因**:
- 当前项目主数据库是 MySQL(用户表、画像表)
- pgvector 需要 PostgreSQL,两者不能共用一个数据源
- 独立数据源更清晰,知识库和业务数据分离

**实现**:`VectorStoreConfig.java` 手动创建 `DataSource` + `JdbcTemplate`,注入 `PgVectorStore`。

**PPT 影响**:可以讲"数据源隔离"--知识库是独立的存储,不应该和业务数据混在一起。

### 3. 商品数据用什么格式?

**决策**:JSON 文件(`products.json`),放在 classpath 下。

**原因**:
- 结构化数据,方便解析和演示
- 每个商品有完整的字段(配置、亮点、适用场景)
- 启动时自动加载,不需要手动导入

**对比**:
- Markdown:适合非结构化文档,但解析复杂
- Excel:企业常用,但需要额外依赖
- 数据库直接读:最灵活,但需要预置数据

**PPT 影响**:Data Pipeline 章节要讲"不同格式的文档怎么处理"--JSON 是最简单的,PDF/Word 是最复杂的。

### 4. Chunking 策略怎么选?

**决策**:一个商品 = 一个 Chunk(固定大小,按商品边界分块)。

**原因**:
- 商品数据天然有结构边界(每个商品是一个独立单元)
- 不需要语义分块或递归分块
- 每个 Chunk 包含完整的商品信息,检索时不会丢上下文

**Demo 局限**:
- 对于长文档(如产品手册),需要更复杂的分块策略
- Chunk Size 对检索效果影响很大,Demo 没有调优

**PPT 影响**:Chunking 章节要讲三种策略(固定/语义/递归),Demo 用的是最简单的固定分块。

### 5. Embedding 用什么模型?

**决策**:使用 Spring AI 自动配置的 Embedding 模型(基于 OpenAI 兼容接口)。

**原因**:
- 和 ChatModel 共用同一个 API Key 和 base-url
- 不需要额外配置
- SiliconFlow 支持 Embedding 模型(如 BGE、Jina)

**Demo 局限**:
- 没有对比不同 Embedding 模型的效果
- 没有做领域微调

**PPT 影响**:Embedding 章节要讲模型选型维度(成本、语言、维度、部署方式),Demo 只用了默认配置。

### 6. 检索管道做到什么程度?

**决策**:只做单路向量检索(pgvector cosine similarity),返回 Top-3。

**原因**:
- 核心教学点是"检索→注入 context→LLM 生成"的完整链路
- Top-3 对于 12 个商品的数据集足够
- 相似度阈值 0.3 过滤掉不相关的结果

**Demo 未覆盖**(仅 PPT 讲解):
- Query Rewrite(用 LLM 改写用户问题)
- Rerank(交叉编码器精排)
- 多路召回(向量 + BM25 融合)
- 语义缓存

**PPT 影响**:Retrieval Pipeline 章节要画完整的 5 步流水线图,标注哪些是 Demo 已覆盖、哪些是 PPT 讲解。

### 7. RAG 结果怎么注入 Prompt?

**决策**:在 `MemoryManager.buildContext()` 中,将 RAG 检索结果追加到对话历史和用户画像之后。

**context 的完整形态(v3.0)**:
```
用户画像(来自 Memory)
+ 对话历史(来自 Session)
+ RAG 检索结果(来自 Knowledge) ← 本课新增
```

**格式**:
```
## 参考知识(从商品库检索)
[1] ThinkPad X1 Carbon Gen12(联想)- 商务轻薄本 - 9999元
    ThinkPad X1 Carbon Gen12(联想)...
    配置:CPU=Intel Core Ultra 7 155H, RAM=32GB...
    亮点:超轻机身1.08kg、OLED屏幕色彩出色...
    适合:商务办公、出差旅行...
    总结:经典商务旗舰...

## 用户问题
推荐一台写代码的笔记本
```

**PPT 影响**:Prompt + RAG 集成章节要讲 Token 预算分配(画像 10% + 历史 30% + RAG 40% + 余量 20%)。

### 8. System Prompt 要不要改?

**决策**:加入"知识使用规则",引导 LLM 优先使用参考知识。

**新增内容**:
```
# 知识使用规则
- 如果"参考知识"中有商品知识,请优先基于这些知识回答
- 推荐商品时,引用具体的配置、价格、亮点来说明理由
- 如果参考信息中没有相关内容,可以基于常识回答,但不要编造商品信息
- 不确定的信息说"我不确定"
```

**原因**:不加这个规则,LLM 可能忽略检索结果,自己编造商品信息。

**PPT 影响**:这是 Prompt + RAG 集成的关键点--不是把检索结果塞进去就行,还要告诉 LLM 怎么用。

### 9. 启动时自动索引还是手动索引?

**决策**:启动时自动索引(`@EventListener(ApplicationReadyEvent.class)`)。

**原因**:
- 演示方便,重启后自动加载
- 12 个商品数据量小,索引很快

**生产局限**:
- 应该有增量索引机制(不是每次全量重建)
- 应该有索引状态检查
- 应该支持异步索引(不阻塞启动)

**PPT 影响**:Demo vs 生产差距章节要讲"索引管理"--生产中需要增量更新、版本控制、权限隔离。

### 10. 商品数据分层:向量库 + MySQL

**决策**:商品数据不全放向量数据库,按数据特性分层存储。

**分层方案**：
| 数据类型 | 存储 | 谁来查 | 课程 |
|---------|------|--------|------|
| 商品描述、亮点、适用场景、配置参数 | pgvector | 系统自动检索（RAG） | 第六课 |
| 价格、库存、销量、上架状态 | MySQL | LLM 通过 Tool 调用 | 第七课 |

**原因**：
- 价格会变（今天9999，明天促销8999），向量库里存旧价格会误导
- 库存实时变（卖完了要显示“缺货”），不能靠语义检索
- 查价格/库存是“做事”，属于 Tool 的范畴
- 第六课只解决“懂”（知识检索），第七课解决“做”（Tool 调用）

**v3.0 检索流程**：
1. pgvector 语义检索 → 返回商品描述（名称、配置、亮点、适用场景）
2. 注入 Prompt → LLM 基于描述推荐商品

**v4.0 增强**（第七课）：
- LLM 识别到用户问价格/库存时，调用 Tool 查询 MySQL
- Tool 返回实时数据，LLM 整合后回复用户

**教学价值**：
- 不是所有数据都适合放向量数据库
- Knowledge 和 Tool 的职责边界清晰
- 能力递进：v3.0 懂商品，v4.0 能查价格、能做事

### 11. 向量数据库增强记忆系统

**决策**:引入 pgvector 后,同时增强第五课的 Long-term Memory。

**增强内容**:
- 用户画像(preference)存入 pgvector,支持语义检索
- Session 结束时沉淀对话片段(conversation)到 pgvector
- `MemoryManager.buildContext()` 用语义检索替代 MySQL 精确查询

**原因**:
- 向量数据库是基础设施,Memory 和 Knowledge 都应该用它
- 只存结构化标签(MySQL)丢失了语义信息
- 用户说"推荐笔记本"时,能检索到"用户上次说喜欢轻薄本、预算8000"

**与第五课的关系**:
- 第五课 PPT 和演讲手册不改(概念不变)
- 第六课引入 pgvector 后,在 Demo 代码中增强记忆检索
- 体现"同一个基础设施,两个能力层都受益"

**数据模型**:
- `user_memory` 向量表:存储 preference / conversation / event 三种类型
- MySQL `user_profile` 表保留:做结构化概览
- 两者互补:UserProfile 做"这个用户是谁",UserMemory 做"和当前对话相关的记忆"

**PPT 影响**:可以展示"向量数据库的两个用途"--知识检索 + 记忆检索,加深学员对基础设施的理解。

## 发现的问题

### pgvector 需要独立数据源
Spring AI 的 pgvector 自动配置使用主数据源,但我们的主数据源是 MySQL。必须手动创建 PostgreSQL 数据源并注入 PgVectorStore。这增加了一层配置复杂度,但也体现了"数据源隔离"的设计思想。

### Spring AI 1.0.0-M4 的 PgVectorStore API
需要确认 `PgVectorStore.builder()` 的 API 是否和后续版本一致。如果不一致,需要在提纲中标注。

### Embedding 模型的维度
pgvector 表的维度需要和 Embedding 模型的输出维度一致。如果换 Embedding 模型,需要重新建表和重新索引。这是生产中常见的坑。
