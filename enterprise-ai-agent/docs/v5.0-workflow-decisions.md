# v5.0-workflow 设计决策记录

## 验证目标
第八课（Workflow:构建可靠的企业 Agent）的核心技术点：状态机、Agent Runtime、TaskPlanner、容错、人在回路、执行追踪。

---

## 设计决策

### 1. ReAct 循环由 Runtime 控制，不是 LLM 自主

**决策**：AgentRuntime 用 `while (iteration < MAX_ITERATIONS)` 控制循环，LLM 只负责"想"，Runtime 负责"管"。

**原因**：
- 纯 ReAct 模式下，LLM 自主决定循环次数，可能无限循环
- Runtime 控制循环可以：强制最大轮次、超时中断、状态机约束
- LLM 通过 Prompt 约定输出格式（`TOOL_CALL:工具名(参数)`）表达意图，Runtime 解析执行

**对比**：
- 第七课：Spring AI 框架自动处理一次 tool_call，LLM 不能控制循环
- 第八课：Runtime 手动控制循环，LLM 在每轮 THINK 中决定是否继续

**教学价值**：这是所有 Agent 框架（LangChain、LangGraph）的底层模式。手搓一遍才能理解框架帮了什么。

### 2. TaskPlanner 用 LLM 做任务规划

**决策**：用 reasoning 模型把复杂请求拆成步骤列表，输出 JSON 数组。

**原因**：
- "帮我对比拯救者和 MacBook"需要分步查询，一次性调用不够
- LLM 擅长理解意图和拆解任务
- 规划结果是 JSON 数组，可解析为 WorkflowStep 列表

**触发条件**：
- 包含"对比""比较""帮我选"等关键词
- 包含多个商品名（≥2）
- 简单任务不规划，直接走 ReAct 循环

**降级策略**：TaskPlanner 失败 → 返回空列表 → AgentRuntime 降级为单步执行

### 3. 状态机用枚举实现，不用框架

**决策**：WorkflowState 用 Java enum 实现，状态转换在 AgentRuntime 代码中硬编码。

**原因**：
- Demo 只有 7 个状态，转换逻辑简单，不需要 Spring StateMachine 等框架
- 枚举 + 代码判断更直观，学员容易理解
- 生产环境可以用状态机框架（Spring StateMachine、Temporal）

**状态设计**：
- PLANNING → EXECUTING → COMPLETED（正常流程）
- EXECUTING → CONFIRMING → EXECUTING（确认后继续）
- EXECUTING → RETRYING → EXECUTING（重试后继续）
- EXECUTING → FAILED（重试耗尽）
- CONFIRMING → CANCELLED（用户取消）

### 4. 三级容错：重试 → 熔断 → 降级

**决策**：ErrorRecovery 实现三级容错，每级有不同的触发条件和恢复策略。

**参数选择**：
- 重试：最多 3 次，指数退避 1s→2s→4s（业界标准）
- 熔断：连续失败 5 次，暂停 60 秒（适合 Demo 演示）
- 降级：跳过工具，LLM 基于已有 context 回答

**为什么不用 Resilience4j**：
- Demo 需要让学员看到容错的完整逻辑，不能藏在框架里
- ErrorRecovery 只有 151 行，逻辑清晰
- 生产环境建议用 Resilience4j 或 Sentinel

### 5. 人在回路只拦截高风险 Tool

**决策**：ConfirmationService 通过关键词匹配判断是否需要确认，不是所有 Tool 都拦截。

**高风险关键词**：order、place_order、refund、delete、支付、下单、退款

**为什么不用 LLM 判断风险**：
- LLM 判断风险不可靠，可能漏判或误判
- 高风险操作的定义应该是确定性的，不能交给非确定性的 LLM
- 关键词匹配简单可靠，生产环境可以用 RBAC 权限表

**确认流程**：
- AgentRuntime 调用 Tool 前检查 ConfirmationService
- 需要确认 → 状态变为 CONFIRMING → 返回确认请求
- 用户确认 → resumeAfterConfirm() → 继续执行
- 用户取消 → 状态变为 CANCELLED

### 6. Trace 用内存存储，不用外部系统

**决策**：TraceService 用 ConcurrentHashMap 存储 Trace，不接入 OpenTelemetry。

**原因**：
- Demo 需要让学员看到 Trace 的完整结构，不能藏在外部系统里
- 内存存储简单，API 直接查询，不需要额外部署
- 生产环境应该接入 OpenTelemetry/Jaeger

**Trace 结构**：
- TraceRecord：traceId、userMessage、state、steps、events、startTime、endTime
- WorkflowStep：stepNumber、action、toolName、toolInput、toolOutput、llmThought、status、retryCount、durationMs

### 7. 新增端点，不改原有代码

**决策**：WorkflowController 新增 `/api/agent/workflow` 端点，ShoppingAgentController 完全不动。

**原因**：
- 两条路径并存：简单问题走 `/chat`，复杂任务走 `/workflow`
- 共享 MCP Client、MemoryManager、PromptManager
- 学员可以对比两条路径的行为差异

**统一入口**：前端统一调 `/api/agent/workflow`，AgentRuntime 内部判断简单/复杂：
- 简单任务：TaskPlanner 跳过规划，一次 THINK 就回答（`mode: "simple"`）
- 复杂任务：TaskPlanner 拆步骤，多轮 ReAct 循环（`mode: "workflow"`）
- `/chat` 端点保留，仅用于需要 SSE 流式输出的场景

### 8. MCP Product Client 新增 callToolDirectly

**决策**：McpProductClient 新增 `callToolDirectly(toolName, arguments)` 方法，绕过 FunctionCallback 包装。

**原因**：
- AgentRuntime 在 THINK 阶段决定调用什么 Tool 和参数，不走 Spring AI 的 FunctionCallback 机制
- 需要直接通过 MCP 协议调用 Tool
- 原有的 `getFunctionCallbacks()` 仍保留，供 ShoppingAgentController 使用

## 发现的问题

### LLM 工具调用格式不稳定
**问题**：Prompt 约定 `TOOL_CALL:工具名(参数)` 格式，但 LLM 输出可能不严格遵守（多换行、多空格、中文标点）。
**Demo 简化**：extractToolCall() 用正则提取，支持多种格式变体。
**生产做法**：用 OpenAI 的 function_call 协议（结构化输出），不靠 Prompt 约定。

### TaskPlanner 规划质量不稳定
**问题**：LLM 规划的步骤可能太粗或太细，有时规划了但不需要（单步就能回答）。
**Demo 简化**：needsPlanning() 用关键词判断，TaskPlanner 失败则降级为单步。
**生产做法**：规划结果缓存 + 人工审核模板 + 规划质量评估。

### 确认超时未实现
**问题**：Demo 中确认请求无超时，用户不点确认，工作流永远挂起。
**生产做法**：确认请求 5 分钟自动取消，状态变为 CANCELLED。

### Trace 内存泄漏风险
**问题**：Trace 存在 ConcurrentHashMap 中，只增不减，长时间运行会 OOM。
**Demo 简化**：getRecentTraces() 只返回最近 50 条。
**生产做法**：Trace 写入外部存储（Elasticsearch/Jaeger），内存只保留最近 N 条。
