## Slide Objective
把 LLM 交互层的七项生产差距一次讲到三格粒度（是什么问题 / 不解决会怎样 / 怎么解决，含具体技术方案与取舍）：API Key 管理与轮换、Token 成本核算与配额、限流与退避、输出 PII 脱敏位置、超时与重试、模型降级、日志脱敏与留存。补上"知道做什么、不知道怎么做"的缺口——这是本课此前最弱的一环（手册里只 4 次提"生产"、具体方案仅 2 个）。

## Suggested Presentation
逐项讲。每项三格都要落地：什么问题、不解决会怎样、怎么解决（含取舍）。这一页讲完，学员应该能对着自己项目说出"我缺哪几件"。

**1 · API Key 管理与轮换。**
问题：Demo 的 Key 走 `application.yml` 的 `spring.ai.openai.api-key: ${SILICONFLOW_API_KEY}` 占位 + `.env` 注入（docker-compose.yml 里 `SILICONFLOW_API_KEY` 必填校验）。一个人一把 Key，全环境共用，没有轮换机制。
不解决会怎样：Key 一旦进 Git 历史或进 Docker 镜像层就泄露，攻击者拿你的 Key 调模型，账单和内容责任都是你的；泄露后无法快速作废——一把 Key 要停就是全停；员工离职带走 Key 无从追责。
怎么解决：三件事。① Key 不落代码不落镜像——运行时从密钥管理服务取（K8s Secret / HashiCorp Vault / 云 KMS），业务进程只拿到注入后的环境变量；② 按环境和用途拆 Key（开发/测试/生产分开，聊天/抽取分开），泄露爆炸半径小；③ 定期轮换 + 双 Key 过渡——新旧 Key 并存一个窗口期，灰度切流量，旧 Key 延迟作废。取舍：Vault 这类组件引入新的运维成本，小团队至少做到"Key 出 Git + 按环境拆分 + 可手动作废"。平台化方案见第十一课支柱三「API Key 治理」。

**2 · Token 成本核算与配额。**
问题：本课 `v1.1.1` 仅用 `System.out.println` 打印文本输出，未解析响应里的 `usage` 字段（`prompt_tokens` / `completion_tokens` / `cached_tokens`），一次调用花多少 token、折多少钱没人知道。
不解决会怎样：成本失控且无感知——改一个 Prompt 或破坏了前缀缓存让单次成本翻倍，账单月底才发现；无法按业务/用户/模型归因，预算分不下去；免费模型下架换付费模型时，没有历史数据支撑选型。
怎么解决：① 在 `callLLM()` 拿到 `ChatResponse` 后解析 usage，按模型单价折算金额，写成本明细表（时间 / 模型 / 业务线 / 用户维度）；② 设配额与告警——日/月 token 阈值，按租户或业务线限预算，超限降级或拒绝；③ 高频相似请求加语义缓存压成本（第六课提过，第十一课网关层系统化）。取舍：计量有存储和聚合开销，但没有计量就没有成本治理——这项是其他六项的"仪表盘"。

**3 · 限流与退避。**
问题：Demo 没有任何限流——每个请求直连 LLM API；被服务商限流（HTTP 429）也没有退避处理，直接报错给用户。
不解决会怎样：并发一上来触发服务商 429，全量用户报错；客户端无脑重试形成重试风暴，把下游彻底打死；开放接口会被刷，token 预算一夜烧光。
怎么解决：① 入口限流——令牌桶或滑动窗口，按用户 + 接口两个粒度（Guava RateLimiter 单机 / Resilience4j RateLimiter / Redis+Lua 分布式）；② 出口对服务商做并发上限 + 队列排队，超卖保护下游；③ 退避重试——对 429/5xx 用指数退避 + 抖动，尊重 Retry-After 头，最多 2-3 次；④ 超限返回什么要想清楚：排队提示、降级答复还是明确错误码，别让用户干等。取舍：阈值卡太紧浪费吞吐、太松失去保护，要按压测数据调；退避会拉长尾延迟，必须设最大重试次数和总超时上限。第七课讲工具侧限流，第十一课网关层做全局限流。

**4 · 输出 PII 脱敏位置。**
问题：Demo 只有 `GuardrailsService.sanitize()` 的敏感关键词替换（密码/password/token/私钥 → `***`），姓名、手机号、身份证、住址这类 PII 没有系统性识别与脱敏，而且只在出口做。
不解决会怎样：LLM 输出和日志里带出用户 PII——违反个保法/GDPR，过不了审计；用户在对话里报的手机号会被原样打进控制台或日志文件，日志系统反而成了最大的泄露面。
怎么解决：关键是确定脱敏**位置**，三个布防点。① 入口——用户输入进 Prompt 前做 PII 识别与掩码（手机号→[PHONE_1]，配映射表），模型只见到占位符，回复后再还原，模型永远拿不到真值；② 出口——LLM 返回后做一次 PII 检测与掩码（正则管手机号/身份证/卡号，NER 模型兜底人名/地址）；③ 日志——落盘前走同一套脱敏管道。取舍：入口脱敏损失语义（模型看不到真号码，涉及号码推理的任务会变差），掩码-映射表方案在"隐私"与"可用"之间折中；NER 有延迟和误报，高风险接口再叠人工审核。第十一课「PII 脱敏粒度」会展开。

**5 · 超时与重试。**
问题：Demo 的 LLM 调用本身没有超时分级、没有重试——`callLLM()` 失败直接抛异常。
不解决会怎样：上游挂起时线程和连接被占满，拖垮整个服务（一个慢上游 = 全站慢）；用户端无限等待或莫名报错；一次网络抖动就是一批用户流失。
怎么解决：① 分层超时——HTTP 连接/读超时、LLM 调用超时按场景分级（意图路由 2-3s、普通对话 30s、深度推理 60s+）、端到端总预算超时（一个请求最多活 N 秒，到点截断给兜底答复）；② 重试只对可重试错误（超时 / 429 / 5xx），前提是调用幂等（纯生成调用幂等，带回写动作的要在第七课幂等框架下做）；③ 指数退避 + 抖动，最大 2-3 次，和限流配合。取舍：超时太短误杀长推理、太长占资源——按场景分级是唯一解；重试是流量放大器，不配限流的重试比不重试更危险。

**6 · 模型降级。**
问题：Demo 的 `ModelRouter.selectModel()` 只负责按长度和关键词选出模型名；真正调模型那一步（`callLLM()`）失败就是失败，没有备选降级。
不解决会怎样：主模型超时/限流/下架时整条链路不可用——免费模型变动频繁（我们在 Demo 里就遇到过模型下架），单模型 = 单点；供应商侧故障 = 全站故障。
怎么解决：① 模型级降级链——reasoning 超时/失败 → fast 模型 → 备用供应商小模型，按错误类型触发（429 退避后换模型，5xx 直接换）；② 供应商级多活——OpenAI 兼容协议让同模型多供应商备份成为改配置（base-url + Key）而不是改代码；③ 降级要可观测——回复打标（当前是降级模型）、监控降级率并告警，降级率升高说明主模型出问题了。取舍：降级后回答质量下降，业务必须提前接受"能答 > 答得最好"，什么场景允许降级要和业务定好；多供应商增加配置面和测试面。第十一课「多模型统一接入/路由/降级」就是把这件事收进网关。

**7 · 日志脱敏与留存。**
问题：本课 `v1.1.1` 直接 `System.out.println` 明文打控制台，无脱敏、无留存策略、无访问控制。
不解决会怎样：日志成了 PII 和密钥的最大泄露出口（用户对话里什么都说，Prompt 里还有系统配置）；无限写盘把磁盘写爆；合规上两头挨打——审计要求可追溯 N 天，隐私要求不能永久存用户原文。
怎么解决：① 落盘前接出口脱敏管道（复用第 4 项那套）；② 分级留存——用量/耗时等元数据长期留（成本与审计要用），对话原文短期留（7/30 天滚动删除，logback RollingFileAppender 配保留策略，或进 ELK 带生命周期索引）；③ 敏感字段哈希或加密存储，用 traceId 关联，确需还原走受控流程；④ 日志本身收访问权限并留审计。取舍：脱敏后排查变难——留哈希/占位映射来平衡；留存越长合规成本越高，"元数据长留 + 原文短留"是通用折中。

最后一句收尾：这七项里 1/2/3/6 本质是横切工程件，Demo 手写是教学需要（看清机制），生产上用成熟件——Resilience4j（限流/退避/熔断）、Vault/KMS（Key）、LLM Gateway（计量/降级/脱敏统一收口）。第十一课的支柱一「AI 网关与成本治理」、支柱三「安全与合规防线」就是把这些平台化。本课先知道缺什么，第十一课知道怎么管。

## Key Emphasis
七项都要讲到"怎么解决"的技术方案与取舍，不能停在"要注意成本"这种正确废话。刻意不展开的：具体接入代码、各组件配置参数、依赖版本——那些是课后作业和 decisions.md 的内容。每项都要点出"配在哪一层"（配置/代码/网关/平台），这是学员做架构决策时真正要的。

## Optional Extension
**学员问：这些生产件是自己写，还是买/用现成的？**
答：分层看，别一刀切。
Demo 做法：本课 Demo 全是手写——`GuardrailsService.sanitize()` 十几行、`ModelRouter.java` 一个类，看得见机制、改得动逻辑，这是教学价值。
生产做法：优先用成熟件——Resilience4j 拿来就有令牌桶/滑动窗口/退避/熔断，Vault/KMS 管 Key 轮换，LLM Gateway（自建或云服务）把计量、限流、降级、脱敏统一收口。自己写的只剩业务语义：什么算 PII（行业不同清单不同）、什么场景允许降级、配额给谁分多少。取舍是明账：引组件有运维成本，自写有维护成本——横切件（限流/脱敏/计量）用成熟件，业务规则自己写。第十一课会把"网关收口后业务代码还剩什么"讲透。

**学员问：我是小团队/内部工具，这七项要全做吗？**
答：按风险排优先级，不做齐也要知道缺口在哪。
Demo 做法：七项在 Demo 里全缺，page_15 的验证点能让你看清"现在到底是什么行为"（比如日志里真的有完整原文）。
生产做法：最低配先做 1（Key 出 Git、能作废）、5（超时分级，防拖垮）、7（日志别存原文）——这三项不做，出事是安全事故；2/3/4/6 按业务量补：有外部用户就补 3（限流），涉及个人信息就补 4（PII），调用量大了补 2（成本），模型不稳定补 6（降级）。取舍：全做是平台能力（第十一课），单应用做到"可作废、有超时、日志干净"就能避开大部分生产事故。

## Classroom Interaction
让学员对照七项给自己现在的项目打分（有 / 无 / 半成品），写下最缺的一项和它对应的"不解决会怎样"。下课时每人带走一个明确的行动项——这比"听懂了"有用得多。

## Take Away
LLM 交互层上生产前补齐七件套——Key 可轮换、成本可核算、流量可限、PII 三处脱敏、超时分级、模型可降级、日志脱敏分级留存，每件都要落到"谁实现、配在哪一层"。

## Why This Slide Matters
跳过这页（这是本课唯一的差距页），学员学完 LLM 交互工程只知道"怎么调通"，不知道生产上要注意什么——他们会把 Demo 直接搬上线：Key 提交进仓库、无超时无重试、完整对话明文进日志。这七项每一项都对应一类真实生产事故，而且全是在上线后才炸。

## Transition
七项差距讲完，本课的知识闭环就齐了：协议打底、交互件落地、防护件兜底、生产差距标出。最后一页做总结，把今天的能力放进导购 Agent 的五步路线图里。
