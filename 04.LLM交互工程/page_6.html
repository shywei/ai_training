CHAPTER 02 · 架构解耦与演进

协议演进 vs 网关演进 — LLM API 协议与企业网关双轨解耦

🌐 轨道一：模型厂商 API 协议演进 (Provider API Evolution)
① Completion API (2020 · 早期文本补全) — 纯文本单向预测
形态：POST /v1/completions，仅输入 prompt 字符串。无 role 角色语义，历史多轮对话只能靠手工文本拼接（如 \nHuman: ...\nAI: ），极易格式漂移与提示词冲突。
② Chat Completions API (2023 · 工业基线) — 结构化对话事实标准
形态：POST /v1/chat/completions，奠定 messages: [system, user, assistant] 角色范式与 Tools/Function Calling 机制。
行业地位：最大公约数！vLLM、Ollama、硅基流动及绝大多数国产模型全量兼容，本课 Demo 全部走此基线。
③ Responses API (2025/2026 · OpenAI) — 面向 Agent 的语义超集
形态：POST /v1/responses，将文本、工具调用、思考流原生抽象为统一输出项（items），支持对话状态与推理续接。
重大变更：OpenAI 官方已弃用 Assistants API（2026 关停），能力并入 Responses API。
旁系与开放规范：Anthropic Messages API 与 Open Responses
Claude 系采用独立的 /v1/messages 协议；社区正推进开放中立的 Open Responses 标准（LiteLLM / OpenRouter 支持），力求实现跨厂商一键互操作。
🏢 轨道二：企业级 LLM 网关架构演进 (Enterprise Gateway Evolution)
阶段一：专用 SDK 点对点直连 (碎片化接入)
各业务直接引入 OpenAI / 智谱 / 通义官方 SDK。强依赖供应商特定类库，代码侵入严重，缺乏统一监控、配额管控与熔断保护，供应商锁死且运维成本极高。
阶段二：应用内统一客户端抽象 (Spring AI / LangChain)
应用层引入 ChatClient 统一接口，实现换模型不改业务代码（本课 Demo 形态）。但在多服务分布式场景下，各微服务仍独立持有 Key、独立计算配额，无法跨业务集中治理。
阶段三：企业级独立 LLM 网关 (统一流式代理与治理底座)
建立独立集中网关服务（如 OneAPI / LiteLLM / 自研网关）：
统一封装：对外暴露标准协议 ｜ 协议适配：抹平各厂商入参出参方言
流式代理：高性能 SSE 转发与长连接治理 ｜ 治理矩阵：多维路由、Token 计费与多层安全。
🚨 兼容性严正警示：OpenAI 兼容协议 ≠ 100% 完全兼容！
许多厂商虽声称“兼容 OpenAI 格式”，但在 Tool Calling 嵌套解析、JSON 严格模式（Structured Outputs）、流式思考字段（reasoning_content 命名）、多模态 Base64 格式 上存在差异！必须靠企业网关层做协议适配抹平方言。
Demo 映射：Demo 采用 Spring AI ChatClient 直连兼容端点（/v1/chat/completions），这是教学的“代码抽象样本”；生产级系统则必须挂载独立 LLM 网关以实现治理与协议适配解耦。
