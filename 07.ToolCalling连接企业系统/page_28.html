CHAPTER 07

补偿 — 失败之后，世界怎么回到一致

① 失败怎么回滚：三条路按操作性质选
不补偿：纯读、幂等写（重复无影响）——记录即可。
反向操作（补偿动作）：下单→取消订单、扣库存→回补、发券→作废。 反向操作必须成对设计：设计正向 Tool 时就定义它的补偿 Tool（`place_order` ↔ `cancel_order`）， 不要等出事再想怎么撤。
人工介入：不可逆操作（已发货、已付款已清算）——系统只能标记异常 + 告警 + 工单，靠人收尾。
判断标准：先问"能不能反向"，再问"反向的代价是否小于不一致的代价"。
② Demo 现状（v1.4）：无事前确认，也无事后补偿
本课 v1.4 的 mcp-product-server 仅暴露 3 个只读查询 Tool（queryProductInfo / queryPrice / queryStock），尚不敢开放真实下单/扣库存写接口。 下一课（第八课）将引入 ConfirmationService 对高危写操作做事前人工确认拦截，但即便有了事前确认，一旦"下单成功但后续扣库存失败"，事后回退与对账补偿仍需专门设计！
③ Saga：把"多步写操作"编排成可回退的链
编排式（集中协调）：一个协调器按序调 T1→T2→T3，任一步失败就逆序调 C3→C2→C1。 链路清晰、好调试；协调器是单点，逻辑集中容易变胖。下一课第八课 AgentRuntime 的多步执行天然像编排器—— 在每个 WorkflowStep 上挂"补偿动作"字段就是最简 Saga。
协同式（事件驱动）：每个服务做完发事件，下游监听并各自决定下一步/补偿。 解耦好、可扩展；链路分散，排查要靠 Trace/审计串起来。
取舍：步数少（≤5）、流程固定用编排式；跨团队、多系统用协同式。 两边共同前提：每一步幂等（补偿本身也会重试）。
④ 本地消息表：不用分布式事务，也要最终一致
做法：业务操作和"待发消息"在同一个本地事务里写库（订单 + outbox 消息表一起提交）， 后台任务扫表投递到 MQ / 直调下游，成功后标记已发。
为什么不用两阶段提交：跨 ERP/订单/库存的 2PC 又慢又脆（锁资源、部分场景根本不支持）。 本地消息表保证"要么都生效、要么最终补上"，代价是短暂不一致 + 投递重试。
⑤ 对账：最后一道防线
T+1（或小时级）跑对账任务：把 Agent 侧的调用/订单记录（审计表里带幂等键与下游单号）与 ERP 侧数据逐条比对， 找出孤儿单（我方有、对方无）和重复单（一幂等键多单）。 处理：自动触发补偿（取消重复单）或转人工工单。补偿解决"当下"，对账兜住"漏网"。
✗ 补偿事务与对账 ｜ 问题
写操作失败即终止，没有反向操作、没有幂等键支撑的重试、没有跨系统对账——多步任务（下单→扣库存→发通知）半途失败只留下中间态。
不解决
订单下了库存没扣（超卖/发不出货）、库存扣了单没成（货压死）、重复单无人发现——数据不一致靠客诉暴露，越晚发现代价越大。
怎么解决
正向/补偿 Tool 成对定义，Saga 编排式（≤5 步固定流程）或协同式（跨团队）执行；本地消息表保证"业务+消息"同事务、异步投递最终一致； 定时对账比对双方数据，孤儿/重复单自动补偿或转人工。取舍：没有银弹——补偿链会叠加延迟与复杂度，只给真正需要一致性的写链路用，读操作不做补偿。
