CHAPTER 07

幂等 — 重复调用是常态，不是意外

① 重复调用从哪来（四个来源）
超时后重试：调用超时 ≠ 没执行——下游可能已经下单了，重试就是第二单。
LLM 重复决策：ReAct 循环里 LLM 看到不确定的结果会再调一次；提示词注入可以让它反复调。
用户重复提交：页面卡顿用户再点一次；前端重发请求。
链路重放：消息队列重投、运维手工补单。
② Demo 现状（v1.4）：写操作没有幂等键
save_memory（真实写操作）：mcp-knowledge-server 的 MemoryService.save() 每次都直接 INSERT INTO user_memory——无幂等键，重复触发沉淀就会把同一条记忆存多次。
扩展下单 Tool（如 place_order）：若接入订单写入且不带幂等键，每次超时重试都会生成新订单号（双下单事故）。
index_knowledge 算幂等雏形：index(force) 检测到已有数据则跳过、force=true 才重建——重跑结果一致。
③ 幂等键怎么设计
键的生成（调用方）：sessionId/requestId + toolName + 业务参数哈希（第八课引入 TraceService 与 WorkflowStep 后即可升级为 traceId + stepNumber + toolName + 参数哈希）——同一笔业务重试沿用同一个键。
键的存放（Tool 端）：去重表（idempotency_key, tool, args_hash, result, created_at） 或业务表加唯一索引（如订单表 `uk_request_id`）——插入冲突即视为重复。
重复请求的返回：不重新执行，回放首次结果（含首次的 orderId）—— 调用方无感知，这才是幂等，"什么都不返回"不算。
清理：去重表设 TTL（如 24~72h），覆盖重试与补单的时间窗。
④ 读与写要分开看
查询天然幂等：`queryProductInfo` / `queryPrice` / `queryStock` 都是 SELECT， 重复调用无副作用——只做超时和限流就够。
写操作必须设计：下单、扣库存、发消息、写记忆。判断标准一句话： "这个 Tool 执行两次，世界会不会不一样？"——会，就必须有幂等键。
✗ 幂等键设计 ｜ 问题
Tool 没有幂等键，重复调用重复执行：save_memory 每次 INSERT 新行，写接口（如下单）重试即产生重复单。
不解决
用户下一单变三单（客诉+退款）、记忆库里一堆重复条目污染检索；超时重试越重试越糟——重试与幂等必须成对出现。
怎么解决
调用方生成 idempotency-key（traceId+step+tool+参数哈希）；Tool 端唯一索引/去重表挡重复，命中就回放首次结果； 读操作不加、写操作必加。取舍：去重表要容量与 TTL，跨系统键要约定归属方（谁生成谁负责），补偿动作本身也要带同一个键。
