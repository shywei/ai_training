CHAPTER 04 · 07

Agent 互操作协议全景 — 各管一段，组合而非替代

一句话分工： MCP 让模型"接得上"工具 ｜ A2A 让 Agent"连得上"Agent ｜ AG-UI 让前端"看得上"过程 ——Agent 互操作 ≠ MCP 一个协议，2026 年已三足鼎立。
MCP — Model Context Protocol
模型 ↔ 工具 / 资源 / 上下文（"USB-C 接口"）
管什么：把工具、数据源、Prompt 标准化接进模型。本课主角。
2026 演进：无状态请求模型（单 /mcp POST 传递 JSON-RPC，免除强制 initialize 握手）；现代化 server/discover 端点动态获取元数据；Tasks 解耦为独立扩展；原生支持 OAuth 2.1。
边界：只管"模型这一端怎么接"，不管 Agent 之间怎么协作、前端怎么呈现。
Demo ✓ McpProductClient / McpKnowledgeClient
A2A — Agent2Agent
Agent ↔ Agent 任务委派与信任基座
管什么：Agent 之间怎么互相发现、委派任务、跟踪进度、带回结果——能力声明（Agent Card）+ 任务生命周期 + 多轮协作。
关键事实：Google 发起，v1.0 2026-03-12；2026-08-17 捐入 Linux 基金会（LF AI & Data）——协议归中立基金会，不是某一家的私有协议。
边界：只管 Agent↔Agent，不负责 Agent 接工具（那是 MCP）。
为什么现在就要知道：一个 Agent 干不完的活要委派给别的 Agent，委派语义就跑在 A2A 上——第十课 Multi-Agent 的协议语境。
仅 PPT 讲解 · Demo 无
AG-UI
前端 ↔ Agent/模型 交互渲染（"UI 事件总线"）
管什么：把 Agent 的思考、工具调用、中间状态、流式增量，以标准事件推给前端渲染与同步——前端"看得上"过程，不是只等最终答案。
解决什么：各家 Agent 各自发明自己的流式格式，前端每接一个 Agent 重写一遍 UI 适配；AG-UI 把"过程可视化"变成标准事件（步骤/工具卡/状态更新）。
边界：只管呈现与交互回传，不负责 Agent 内部怎么决策。
为什么现在就要知道：产品要展示"Agent 正在干什么"、要让用户中途干预，第十一课企业平台的统一体验就落在这层。
仅 PPT 讲解 · Demo 无
ACP（Agent Communication Protocol）＋ 组合而非替代
ACP：另一套 Agent ↔ Agent 消息/会话互通协议，与 A2A 同处"Agent 互操作"赛道、生态不同——选型看生态与治理归属，不必都接，更不是二选一就完事。
前端 —AG-UI→ Agent A —MCP→ 工具/资源 ｜ Agent A —A2A→ Agent B —MCP→ 工具/资源
垂直接工具用 MCP、水平接 Agent 用 A2A、面向用户接前端用 AG-UI——三段各就各位，谁也吃不掉谁。
