CHAPTER 08

🧪 可在 Demo（v1.4）验证哪些点 — 动手确认，不是听完就过

① Tool 发现与握手
按知识 → 商品 → agent-runtime 顺序启动三个服务，看 agent-runtime 控制台： [MCP] 发现 3 个 Tool / [MCP] 已包装 3 个 FunctionCallback； knowledge-server 侧 4 Tool + 1 Resource（user://{userId}）。验证"Tool 是自动发现的，不用改 Client"。
② 实时数据真的来自 MySQL
问"拯救者 Y9000P 多少钱"→ 8999 元/库存 12 件；直接改 product 表的 price 再问一遍——答案跟着变。 证明走的是 ProductRepository 参数化查询，不是模型记忆。
③ 数据分层
问"推荐一台写代码的笔记本"（走 search_knowledge → pgvector 描述）和 "NB001 多少钱"（走 queryProductInfo → MySQL 实时数据），对照两段回答的来源差异。
④ 路由判定是确定性的
POST /api/agent/recommend（LlmRouter.route() 的入口）发同样内容两次， logs/llm-route.log 的 ROUTE REQUEST/RESPONSE 里 Route 与 Selected Model 完全一致（temperature=0）。
⑤ 记忆自动沉淀（系统行为）
聊满 20 条消息触发：[Memory] 消息数 20 达到阈值 20，触发自动沉淀（见 logs/llm-extract.log）； psql 查 user_memory 能看到摘要。验证 save_memory 不暴露给 LLM、由系统控制时机。
⑥ MCP Resource 读取验证（user://{userId}）
发起 GET /api/agent/chat 对话时，观察 MemoryManager.buildContext() 调用 McpKnowledgeClient.readUserProfile(userId) 通过 MCP Resource URI user://U001 读取 MySQL 用户画像并注入 context，无需 LLM 发起 tool_call。
⑦ MCP 断线重连与冷却保护验证（ensureConnected）
停掉 mcp-product-server 后提问价格，观察报错提示与 10 秒冷却重连保护（RECONNECT_COOLDOWN_MS = 10_000，防止每次请求卡死重连）； 重新启动 mcp-product-server 等待 10 秒后再提问，验证自动恢复连接并重新发现 Tool。
⑧ v1.4 治理缺口现场观察（直指第八课演进目标）
在 v1.4 现场观察四个缺口：① 单次 Function Calling 无法分步规划对比多商品；② 超时/报错无指数退避重试与熔断；③ 写操作（如 save_memory）无幂等键去重；④ 高危操作无人工确认拦截与步骤级 Trace——直指第八课 AgentRuntime 的演进目标！
