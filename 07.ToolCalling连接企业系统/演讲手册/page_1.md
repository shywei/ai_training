## Slide Objective
开场定调：从"记住用户"进入"让 Agent 连接企业系统"。建立第七课的认知框架——Agent 只能"读"是不够的。

## Suggested Presentation
上节课让导购 Agent 懂了商品知识，记住了用户偏好。RAG 检索让它能推荐商品，记忆系统让它能记住用户。但它还是只能"说"，不能"做"。

用户问"ThinkPad X1 多少钱"，Agent 只能从向量库里找到描述信息——"ThinkPad X1 Carbon Gen12，联想，笔记本电脑"。没有价格，没有库存。因为向量库存的是商品描述，不是实时数据。价格每天在变，库存每分钟在变，这些数据不应该放向量库。

用户说"记住我喜欢轻薄本"，Agent 被动等系统提取。`UserProfileExtractor` 在检测到"记住"关键词时触发，用 LLM 从对话中提取画像写入 MySQL。但这种关键词触发是 Demo 的简化——实际企业中，画像是由专门的画像系统维护的，通过批量任务（每天定时从近期对话中抽取）、事件驱动（会话结束、订单完成后触发）、或流处理（Kafka 实时分析对话标签）来更新。画像是"用户是谁"的权威答案，比单次对话记忆重要得多。

第七课新增了系统自动沉淀机制，对话满 20 条消息时自动提取前 10 条的摘要保存到 user_memory（pgvector），后 10 条保留在 Redis 作为最近上下文（`MemoryManager.PRECIPITATE_THRESHOLD = 20` / `KEEP_RECENT = 10`）。user_memory 和 user_profile 的关系是：记忆是"对话中发生了什么"（原始记录），画像是"用户是谁"（提炼后的结论）。画像从多轮记忆中提炼，不是每次对话都更新。记忆保存是系统行为，不通过 LLM 调用。

用户说"帮我下单"，Agent 完全无能为力。它没有调用订单系统的能力。

这三个问题的本质是一样的：Agent 缺少"做事"的能力。第七课要解决这个问题。

## Key Emphasis
三个问题不是独立的，它们指向同一个缺失：Agent 和外部系统之间缺少连接机制。第六课的 Agent 是一个"孤岛"——它有知识、有记忆，但不能和外部世界交互。

## Optional Extension
**学员问：价格和库存为什么不直接灌进向量库，让 RAG 一次答全？**
答：先分清两类数据——描述性知识（配置、亮点、适用场景）变的频率低，实时业务数据（价格、库存）每天甚至每分钟在变。灌进向量库意味着每次变更都要重新向量化，检索出来的是"变更前的快照"。
Demo 做法：商品描述进 pgvector（mcp-knowledge-server 的 `VectorSearchService` 做语义检索），价格库存留在 MySQL，由 mcp-product-server 的 `queryPrice` / `queryStock` 实时查询——同一份数据只有一个权威源。
生产做法：变动数据走 Tool 查权威源 + 短 TTL 缓存（Redis），向量库只存低频变化的描述；返回结果带数据时间戳，LLM 能说"截至 X 时刻的价格"。取舍：多一次实时查询换数据一致性，这类数据服务的统一治理在第十一课「AI 网关与成本治理」里展开。

## Take Away
判断一条信息该进向量库还是走 Tool 实时查，看它变的频率——低频描述进向量库，高频业务数据必须走 Tool 查权威源，混放的代价是"答得流利但数据是旧的"。

## Why This Slide Matters
跳过这页，学员会把价格库存灌进向量库、或让 LLM 凭训练数据硬答价格——上线第一周就出现"报价和订单系统对不上"，返工的不只是代码，还有已经建好的向量库和数据管线。
