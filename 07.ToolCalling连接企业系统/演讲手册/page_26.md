## Slide Objective
讲清审计的完整做法：本课 `v1.4` Demo 的调用日志 + LLM 交互日志为什么只是"排障日志"不是"问责审计"、审计表一条记录怎么答全"谁/何时/什么/结果/上下文"五个问题、写入与存储的硬要求。对应 `v1.4` 代码是 `McpToolCallback.java` 的 `call()` 日志和 `LlmInteractionLogger` 的 `logs/llm-chat.log` / `llm-route.log` / `llm-extract.log`（下一课第八课将引入内存级的 `TraceService`）。

## Suggested Presentation
先对着 `v1.4` 代码盘点 Demo 有什么：**MCP 调用日志**——`McpToolCallback.call()` 打 `[MCP] 调用 Tool: {}, 参数: {}`、`[MCP] Tool 响应: {}`，失败打 `[MCP] 调用 Tool 失败`，都进控制台/应用日志；**LLM 交互日志**——`LlmInteractionLogger` 按用途写入 `logs/llm-chat.log` / `llm-route.log` / `llm-extract.log`（logback 分文件）。至于结构化的步骤级执行追踪（Trace），本课 `v1.4` 还没有——**下一课（第八课 `v1.5`）**我们将手写 `TraceService` 把每步工具调用记进内存 `ConcurrentHashMap`，但即便加上内存 Trace，也依然重启即丢。结论直说：这是"排障用日志"，不是"问责用审计"——没有持久化表、没有字段规范、可被改写。

然后讲日志 vs 审计的区别，这是本页的认知核心：**日志**给开发排障，可裁剪、可打码、随版本变；**审计**给合规与问责，字段固定、独立存储、只增不改、有留存期。判断标准一句话——**这件事能不能拿到合规会上当证据**。拿现有文本日志（乃至第八课的内存 Trace）对号入座：无独立表结构、无防篡改权限隔离、没有 PII 脱敏规范、没有法定留存期，四条全不满足——排障很好用，但它不是审计。

接着是审计表设计，一条记录答全五个问题：**谁**——`userId + agentId + sessionId + trace_id`；**何时**——请求时间、耗时 `duration_ms`、结果状态（`success / timeout / rejected / compensated`）；**什么**——`tool_name` + 参数快照 + 参数哈希，**PII 脱敏后落库**（手机号留前 3 后 4）；**结果**——返回摘要 + 结果哈希 + 下游单号（`orderId`），错误码与错误摘要；**上下文**——幂等键 `idempotency_key`、触发来源（LLM 决策 / 系统自动 / 人工确认）、步骤号 `stepNumber`。注意幂等键和 `traceId` 都进审计表——上一页和这一页在这里咬合：审计记录是幂等键的天然归档处。

最后是写入与存储要求：**写入时机**——调用前记一笔意图、调用后补结果与耗时（两笔或带耗时的一笔），**失败也必须留痕**——超时报错、熔断跳过、用户拒绝确认，这些都是审计要的现场；**独立存储**——审计库与业务库分开、写入账号只给 INSERT 权限防篡改，按月分区 + 留存期（金融常 1~3 年）；**回放**——按 `traceId` 或 `sessionId` 把一次任务的调用链完整拼出来。

本页三格卡（与 PPT 的 ✗ 卡对应，讲解时逐格落）：
- **✗ 审计表设计**｜问题：`v1.4` 审计只到文本日志级，日志可被清、可被改，字段不固定、没有 PII 脱敏规范。｜不解决：出了事故（误下单、数据泄露、违规调用）无法回答"谁、何时、调了什么、结果是什么"，合规过不了，追责与复盘都无从下手。｜怎么解决：审计表（含幂等键/traceId/参数与结果哈希/耗时/状态）+ 调用前后双写 + 独立库只增不改 + PII 落库前脱敏 + 留存期与分区。取舍：全量参数快照可回放但存储大且有合规风险（存 PII），折中是存哈希 + 脱敏快照；审计写失败要不要挡业务——金融场景"审计失败即拒绝调用"。

## Key Emphasis
必须讲清：① 日志与审计的用途差异和判断标准；② 审计表五问的字段构成（尤其幂等键、PII 脱敏、状态枚举）；③ 失败也要留痕、审计独立存储只增不改。不要展开脱敏算法的具体实现和合规法规条文（GDPR/等保条款）——点到"PII 落库前脱敏"和"留存期"即可。

## Optional Extension
**学员问：审计存全量参数快照还是只存哈希？存快照不是能回放吗？**
答：能回放，但要想清楚存的是谁的数据。
Demo 做法：`McpToolCallback.call()` 里现在就是全量参数进日志，让学员翻一眼日志里如果传了手机号/地址这类 PII 会怎样——答案是明文落盘有合规风险，这本身就是教学素材。
生产做法：参数哈希 + 脱敏后快照（手机号留前 3 后 4）双存，哈希用于比对一致性、脱敏快照用于人工复盘；真正需要完整回放的场景（金融交易）另走加密归档，访问单独授权。取舍：全量快照回放最爽，但存储大且 PII 集中存放本身就是合规风险——审计表变成第二个泄露源就得不偿失。

**学员问：审计写失败了要不要挡住业务调用？**
答：看事故代价，分两档。
Demo 做法：现在 `McpToolCallback.call()` 只打 `log.info`，先让学员思考如果在这里加一行同步写 MySQL 审计表，每次 Tool 调用多一跳写库的延迟代价与异常处理怎么选。
生产做法：金融/支付类"审计失败即拒绝调用"（没有留痕的交易宁可不做）；一般业务"审计失败降级为本地告警 + 事后补录"，不挡主流程。取舍：挡业务换来的是证据链完整，代价是审计库的可用性直接成为业务可用性的一部分——所以审计库要独立部署、单独监控。

## Classroom Interaction
让学员在 `v1.4` 下问一句"ThinkPad X1 多少钱"，然后打开控制台日志 `[MCP] 调用 Tool` 和 `logs/llm-chat.log`，试着回答"是谁（userId）、在哪个会话（sessionId）、耗时多少毫秒、幂等键是什么"——学员会立刻发现 `McpToolCallback` 的日志里连 `userId` 和 `sessionId` 都没有透传！这就是文本日志与结构化审计的直观差距（也是练习 7 的课堂预演）。

## Take Away
审计表一条记录答全五问（谁/何时/什么/结果/上下文，含 traceId、幂等键、参数与结果哈希、耗时、状态），调用前后双写、失败也留痕、独立库只增不改、PII 落库前脱敏——判断标准就一句：这条记录能不能拿到合规会上当证据。

## Why This Slide Matters
跳过这页，学员会把"日志打得很全"当成"有审计"，然后在第一次数据泄露/误下单的复盘会上拿不出任何可采信的记录：日志被轮转清掉了、调用日志里关联不上 userId、参数里还带着用户明文隐私。合规场景下审计是上线前置项，事后补不回历史。
