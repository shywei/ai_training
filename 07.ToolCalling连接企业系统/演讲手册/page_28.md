## Slide Objective
讲清补偿的完整做法：失败回滚的三条路（不补偿/反向操作/人工介入）、Saga 把多步写操作编排成可回退的链、本地消息表不用分布式事务也做到最终一致、对账兜住漏网。对应本课 `v1.4` Demo 的现状是：`mcp-product-server` 只敢暴露 3 个只读查询 Tool，既没有事前人工确认拦截（下一课第八课将引入 `ConfirmationService`），也没有事后补偿与对账机制；同时讲清"事前确认拦截 ≠ 事后失败补偿"。

## Suggested Presentation
先立三条路，按操作性质选：**不补偿**——纯读、幂等写（重复无影响），记录即可；**反向操作（补偿动作）**——下单→取消订单、扣库存→回补、发券→作废，关键是**成对设计**：设计正向 Tool 时就定义它的补偿 Tool（`place_order` ↔ `cancel_order`），不要等出事再想怎么撤；**人工介入**——不可逆操作（已发货、已付款已清算），系统只能标记异常 + 告警 + 工单。判断标准两问：先问"能不能反向"，再问"反向的代价是否小于不一致的代价"。

本课 `v1.4` Demo 现状对着代码讲：`mcp-product-server` 目前只暴露了 `queryProductInfo`、`queryPrice`、`queryStock` 三个只读 Tool，还不敢开放真实写接口。到了**下一课（第八课 `v1.5`）**，我们会引入 `ConfirmationService` 把下单/退款等高风险操作拦下来先让用户确认——但必须跟学员讲透：**人工确认只是"事前拦截"**（防的是"不该做的做了"），而**补偿是"事后恢复"**（管的是"用户点确认放行之后，做了一半失败怎么撤"）。一旦接真实订单与库存系统，"下了单但后续扣库存失败"必须靠补偿机制回退。

Saga 讲两种编排：**编排式（集中协调）**——协调器按序调 T1→T2→T3，任一步失败就逆序调 C3→C2→C1，链路清晰好调试，代价是协调器单点、逻辑集中容易变胖；下一课第八课我们要写的 `AgentRuntime` 多步执行循环天然就像编排器——**如果在每个步骤（`WorkflowStep`）上挂一个"补偿动作"字段，就是最简 Saga**。**协同式（事件驱动）**——每个服务做完发事件，下游各自决定下一步/补偿，解耦好可扩展，但链路分散，排查要靠 Trace/审计串起来。取舍：步数少（≤5）、流程固定用编排式；跨团队、多系统用协同式。**两边共同前提：每一步幂等**——补偿动作本身也会失败也要重试（呼应幂等那页："补偿动作本身也要带同一个幂等键"）。

本地消息表解决"不引入分布式事务也要最终一致"：业务操作和"待发消息"在**同一个本地事务**里写库（订单 + outbox 消息表一起提交），后台任务扫表投递到 MQ / 直调下游，成功后标记已发。为什么不用两阶段提交——跨 ERP/订单/库存的 2PC 又慢又脆（锁资源、部分场景根本不支持），本地消息表保证"要么都生效、要么最终补上"，代价是短暂不一致 + 投递重试。

最后是对账，最后一道防线：T+1（或小时级）跑对账任务，把 Agent 侧的调用/订单记录（审计表里带幂等键与下游单号）与 ERP 侧数据逐条比对，找出**孤儿单**（我方有、对方无）和**重复单**（一幂等键多单），自动触发补偿（取消重复单）或转人工工单。一句话收束这一页的体系：**补偿解决"当下"，对账兜住"漏网"**——补偿链再设计也会有漏，对账是发现漏的那双眼睛，审计表（上上页）是对账的数据基础。五件套在这里闭环：幂等键 → 补偿可重试 → 审计留痕 → 对账可比对。

本页三格卡（与 PPT 的 ✗ 卡对应，讲解时逐格落）：
- **✗ 补偿事务与对账**｜问题：写操作失败即终止，没有反向操作、没有幂等键支撑的重试、没有跨系统对账——多步任务（下单→扣库存→发通知）半途失败只留下中间态。｜不解决：订单下了库存没扣（超卖/发不出货）、库存扣了单没成（货压死）、重复单无人发现——数据不一致靠客诉暴露，越晚发现代价越大。｜怎么解决：正向/补偿 Tool 成对定义，Saga 编排式（≤5 步固定流程）或协同式（跨团队）执行；本地消息表保证“业务+消息”同事务、异步投递最终一致；定时对账比对双方数据，孤儿/重复单自动补偿或转人工。取舍：没有银弹——补偿链会叠加延迟与复杂度，只给真正需要一致性的写链路用，读操作不做补偿。

## Key Emphasis
必须讲清：① 事前拦截（下一课的 `ConfirmationService`）与事后补偿是两件事；② 补偿 Tool 与正向 Tool 成对设计；③ Saga 编排式/协同式的取舍与"每步幂等"的共同前提；④ 补偿 + 对账两层防线的关系。不要展开分布式事务的完整理论（2PC/3PC/TCC 的协议细节）和 MQ 的选型对比——点到"为什么不用 2PC"即可，别把课带向分布式系统课程。

## Optional Extension
**学员问：每个 Tool 都要设计补偿吗？工作量要翻倍了。**
答：不用，按副作用分层。
Demo 做法：盘点当前 `v1.4` 里的所有 Tool——`queryProductInfo`/`queryPrice`/`queryStock`/`search_knowledge`/`search_memory` 全是纯读；`index_knowledge` 是可重建的幂等写；`save_memory` 是追加写；只有当我们在企业里接入 `place_order`（下单）、扣库存、退款这类强一致性写接口时，才需要配对设计补偿 Tool。
生产做法：只给"写链路 + 结果不一致代价高"的 Tool 设计补偿对（下单/扣库存/发券/转账）；读操作和幂等写记录即可。取舍：补偿链会叠加延迟与复杂度（每步多一个补偿分支要测），全量铺开是过度设计——先按"不做的后果"排序，只做真需要的。

**学员问：补偿动作自己也失败了怎么办？**
答：补偿失败不是终点，是转入对账。
Demo 做法：在多步任务状态设计里加上"补偿失败 → 状态置为 `compensated_failed`"，让学员看到状态机里必须有这个终态，而不是只有 success/fail。
生产做法：补偿带幂等键重试若干次（补偿本身可安全重试），仍失败则标记异常 + 告警 + 转人工工单，同时这条记录会在 T+1 对账里被自动捞出来（孤儿单/重复单）。取舍：自动重试解决 90% 的瞬时故障，剩下 10% 靠对账 + 人工兜底——不要试图写一个"永不失败"的补偿，那是假想。

## Classroom Interaction
口头设计一条三步写链路的补偿链："下单 → 扣库存 → 发通知"，让学员逐步回答：哪步有天然反向操作（下单→取消订单、扣库存→回补）、哪步没有（通知发出去收不回，只能标记 + 人工/忽略）、每步的补偿失败了走哪条路。标错"通知"的学员会意识到"不可逆操作只能转人工"——这是练习 6 的课堂预演。

## Take Away
正向/补偿 Tool 成对定义，多步写链路用 Saga 编排式（≤5 步固定流程）或协同式（跨团队）回退，本地消息表保证"业务+消息"同事务最终一致，定时对账捞孤儿单/重复单兜底——补偿管当下、对账管漏网，且每一步（含补偿本身）都要幂等。

## Why This Slide Matters
跳过这页，学员的多步任务半途失败时只会留下中间态：订单下了库存没扣（超卖/发不出货）、库存扣了单没成（货压死）、重复单没人发现——数据不一致靠客诉暴露，越晚发现代价越大。事前确认救不了执行中的失败，必须靠事后补偿与对账闭环。
