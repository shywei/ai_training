## Slide Objective
建立 Function Calling 的认知基础——LLM 天生不能"做事"，需要外部机制。不是"技术限制"，是"架构设计"。

## Suggested Presentation
LLM 的本质是文本生成器。给它一段上下文，它生成下一段文本。它不能访问互联网、不能查数据库、不能调 API。它的"知识"来自训练数据，有截止日期。

但企业场景需要的能力远超"生成文本"：查实时价格（数据库查询）、查库存（数据库查询）、下单（调用订单 API）、发邮件（调用邮件服务）、更新 CRM（调用 CRM API）。这些 LLM 都做不到。

解决方案是 Function Calling：LLM 不直接执行操作，而是返回一个"调用指令"——"我要调用什么函数、传什么参数"。系统执行函数，把结果回传 LLM。LLM 基于结果生成最终回复。

类比：LLM 是大脑，Tool 是手脚，Function Calling 是大脑告诉手脚"做什么"的指令。大脑不需要知道手脚怎么动肌肉，只需要说"拿杯子"。

这个架构的关键是**分离"决策"和"执行"**。LLM 负责决策（调什么、传什么参数），系统负责执行（查数据库、调 API）。LLM 不需要知道执行细节，只需要知道有哪些函数可用、每个函数做什么。

实际 Demo 中的例子："ThinkPad X1 多少钱"。LLM 不知道实时价格（训练数据有截止日期），但它知道"我有一个叫 queryProductInfo 的函数可以查价格"。于是它返回 tool_call: `queryProductInfo("NB001")`，系统查 MySQL 拿到价格 ¥9999，回传给 LLM，LLM 生成最终回复。

注意一个关键细节：LLM 自动把"ThinkPad X1"映射到商品 ID "NB001"。这个映射是 LLM 通过函数描述和上下文推断出来的，不需要我们写映射规则。这就是 LLM 的"理解"能力——它能从自然语言中提取结构化参数。

## Key Emphasis
**严正澄清函数调用（Function Calling）的执行权力边界**：
1. **彻底纠偏**：大模型（LLM）只负责输出结构化的工具调用决策（Tool Call JSON），它本身**绝不执行任何实际代码或物理动作**！它既不会去发网络请求，也不会碰数据库，它只是按概率分布预测出了一串带有函数名和入参的 JSON 文本。
2. **执行权唯一归属**：工具调用的实际物理执行权、入参安全校验、沙箱运行隔离、超时熔断与异常捕获完全且唯一归属于 **Agent Runtime / Host 环境**（如 Spring AI 的 ToolCallingManager）。
3. 必须坚决破除“大模型直接操作数据库”的错误心智模型——模型是参谋，Runtime 才是真正握有执行权和安全防线的执政官。

## Demo 与生产的差距
Demo 中 LLM 返回 tool_call 后，Spring AI 自动执行并回传结果。生产中需要加完备的企业级工程防线：入参白名单校验（防注入）、多租户鉴权与 RBAC（该调用者能不能调这个函数）、超时处理与熔断、写操作幂等控制、审计日志（记录每次调用）。Demo 没有这些，生产必须有。

## Optional Extension
**学员问：LLM 生成的 tool_call 参数要是错的呢？比如把 NB001 传成 NB002，或者传入 SQL 注入代码，谁负责发现？**
答：大模型是不可信的生成源，其输出必须被严格视作不可信数据。防线完全在 Agent Runtime：
1. **输入校验与白名单**：Runtime 执行前必须依据 JSON Schema 进行强制校验，关键字段跑业务正则白名单；
2. **沙箱与安全上下文**：工具代码在受限沙箱中运行，参数化传递，绝不允许直接拼接到 SQL 或 Shell 中；
3. **高危人机协同审批**：写操作和破坏性操作（如转账、删库）必须挂起等待人工确认。

## Take Away
牢记执行权力边界：**LLM 只负责决策（生成 Tool Call JSON），Agent Runtime 独占执行与安全防线（校验、沙箱、鉴权、物理调用）**。绝不让模型输出直达底层数据或物理系统。
