## Slide Objective
讲清限流的完整做法：令牌桶与滑动窗口的算法选型、按 Tool 粒度 + 按调用方分层的配额怎么定、写操作的超卖保护为什么光靠限流不够、超限之后返回什么。对应本课 `v1.4` Demo 的现状是**完全没有限流**——`ShoppingAgentController` 和 `McpToolCallback` 对所有工具调用直接放行，既不限制自身调用速率也不处理下游限流响应。

## Suggested Presentation
先选算法，两个候选讲透取舍：**令牌桶**按速率放令牌、桶满不叠加，请求取令牌执行，允许攒额度扛短时突发——用户点"对比 5 款"，5 个查询瞬间并发也放得过；实现是 Guava RateLimiter（单机）/ Redis + Lua（分布式）。**滑动窗口**统计最近 N 秒内的调用数、超了就拒，速率卡得准、好解释（"每分钟 60 次"），但突发容忍差；实现是 Redis ZSET 存时间戳 / Redisson。顺带点一下**固定窗口**（每分钟清零）：最简单，但窗口边界会突刺——59 秒放一批、61 秒又放一批，两秒内双倍流量，只在要求不高时用。取舍一句话：**要扛突发选令牌桶，要精确控速率选滑动窗口**。

本课 `v1.4` Demo 现状直说：`McpToolCallback.call()` 和 `mcp-product-server` 的 `McpServerConfig` 都没有任何速率控制——前端或被提示词注入的请求想调多少次 `queryProductInfo` 就调多少次。哪怕到了下一课（第八课）加上熔断器，也要分清两个方向：**熔断只防"下游挂了我们还去撞"，限流防的是"我们把活着的下游打挂"**——两个方向千万别混。

限流粒度两层：**按 Tool 分桶**——每个 Tool 一个桶，`queryStock` 这类高频读放得宽（如 100/min），下单/写入类低频高危卡得紧（如 10/min），读写分开定额；**按调用方分层**——userId / agentId / 租户各一层配额，防止一个 Agent 或一个用户吃光全局额度（多 Agent 编排在第十课展开，到时会看到 Supervisor-Worker 团队里多个 Worker 共享一个下游配额，这层分桶就是前置认知）。配额不是拍脑袋的：**从下游系统的 SLA 反推**——ERP 每秒能扛 50 次，Agent 侧就定 30 次留余量。

再讲超卖保护：下单/扣库存这类 Tool，限流只控**速率**，不控**同时在飞的请求数**。要防超卖还要三件：并发上限（同一商品同时最多 N 个扣减在飞）、库存乐观锁（`UPDATE product SET stock=stock-1 WHERE id=? AND stock>0` 或版本号）、幂等键（前面那页）。**限流 + 并发上限 + 幂等 + 乐观锁，四件一起才能保证不超卖**——少任何一件都有对应的事故。

最后是超限了返回什么，三种策略别静默吞：**排队**——有界队列 + 队列等待超时，体验平滑但队列不能无限长；**降级**——返回缓存/简化结果（"库存信息延迟 1 分钟"），保住主流程；**拒绝**——返回 429 + Retry-After + 可读原因（"查询频率超限，请 30 秒后再试"）。强调最后一条为什么重要：**LLM 拿到明确错误才能正确转述给用户，静默失败会让它编答案**——错误信息也是给 LLM 的 Prompt 的一部分。

本页三格卡（与 PPT 的 ✗ 卡对应，讲解时逐格落）：
- **✗ 限流（令牌桶/滑动窗口）**｜问题：Tool 调用没有任何速率与并发控制，LLM 循环失控、提示词注入批量调用、用户峰值都直接打到下游 ERP。｜不解决：下游被打挂（雪崩到所有系统）、并发扣减超卖（发不出货+客诉）、被注入的 Agent 变成打别人的“肉鸡”——事故都出在“调太多”。｜怎么解决：按 Tool 粒度限流（令牌桶扛突发 / 滑动窗口控速率，Redis+Lua 做分布式）+ 按用户/Agent 分层配额 + 写操作并发上限与乐观锁；超限三选一：有界排队 / 降级返回缓存 / 429 + Retry-After 明确错误码。取舍：限太紧误伤正常业务（峰值体验差），限太松等于没限——从下游 SLA 反推配额，先保命再优化。

## Key Emphasis
必须讲清：① 令牌桶 vs 滑动窗口的取舍一句话；② 按 Tool 分桶 + 按调用方分层，配额从下游 SLA 反推；③ 防超卖是"限流 + 并发上限 + 幂等 + 乐观锁"四件套；④ 超限返回明确错误（429 + Retry-After）而不是静默吞。不要展开 Guava RateLimiter 的源码实现、Redis Lua 脚本细节和滑动窗口的 ZSET 操作——工具怎么写是落地时的事，这页要立的是配额设计与超限语义。

## Optional Extension
**学员问：Demo 里用 Guava RateLimiter 就够了吧？为什么还要 Redis？**
答：单实例够，多实例就不够了。
Demo 做法：给 `McpToolCallback.call()` 或 `mcp-product-server` 的 `queryProductInfo` 分支包一个 `RateLimiter.create(10.0/60)`（10 次/分钟），循环调用 12 次看第 11 次被拦（练习 5 就是这个实验），单机内立竿见影。
生产做法：多实例部署时每台都放令牌等于总配额放大 N 倍，要集中计数——Redis + Lua 脚本做原子令牌桶，或 Redisson 滑动窗口；网关层统一做更省事（第十一课支柱一「AI 网关与成本治理」的 MCP Gateway 就管这个：注册/鉴权/RBAC/审计/版本，限流是它的准入面）。取舍：Redis 引入了网络依赖和单点考量（配额服务挂了放行还是拒绝？默认放行 + 告警是常见折中）；Guava 简单但只护得住单机。起步用 Guava 挡最大的风险，规模化再上 Redis，别一步到位搭平台。

**学员问：限流和熔断都跟"调用失败"有关，是不是重复了？**
答：方向相反，两个都要。
Demo 做法：下一课第八课我们将手写 `ErrorRecovery` 的熔断（连续失败 5 次、60 秒恢复），它的防护方向是"下游挂了，我们不再去撞"；而本页讲的限流反过来，是"下游活着，我们别把它打挂"。
生产做法：入口限流（准入）+ 出口熔断（自保）各管一头，中间配超时和重试——这套组合在第八课三级容错里会看到统一的参数面。取舍：只有熔断没有限流，事故模式是"我们把下游打挂后被熔断保护"——下游已经挂了才自保，晚了；只有限流没有熔断，下游真挂时请求还会排队去撞。两个是互补不是二选一。

## Classroom Interaction
让学员看 `McpToolCallback.java` 的 `call()` 方法，思考如果要给 `queryProductInfo` 挂一个 Guava `RateLimiter`（10 次/分钟），当 `tryAcquire()` 返回 `false` 时，应该抛异常还是返回一段结构化提示文本给 LLM？从"排队/降级/429可读提示"三选一里挑超限策略并说理由。这是练习 5 的课堂预演。

## Take Away
按 Tool 粒度配桶（读宽写紧）+ 按用户/Agent 分层配额，配额从下游 SLA 反推；防超卖要"限流 + 并发上限 + 幂等 + 乐观锁"四件齐上；超限明确返回 429 + Retry-After——让 LLM 拿到可转述的错误，静默失败只会让它编答案。

## Why This Slide Matters
跳过这页，学员的 Agent 会在两个方向出事：LLM 循环失控或提示词注入批量调用把下游 ERP 打挂（雪崩到所有系统），或者并发扣减不设防造成超卖（发不出货 + 客诉）。这类事故的讽刺之处在于肇事者是自己的 Agent——放行评审第一个问的就是"你限流了吗"。
