CHAPTER 07

限流 — 保护下游，不被 Agent "热情"打死

① 令牌桶 vs 滑动窗口（先选算法）
令牌桶：按速率放令牌，桶满不叠加（或带上限）；请求取令牌执行。 允许攒额度、扛短时突发——用户点了"对比 5 款"，5 个查询瞬间并发也放得过。 实现：Guava RateLimiter（单机）/ Redis + Lua（分布式）。
滑动窗口：统计最近 N 秒内的调用数，超了就拒。 速率卡得准、好解释（"每分钟 60 次"），但突发容忍差。 实现：Redis ZSET 存时间戳 / Redisson。
固定窗口（每分钟清零）最简单，但窗口边界会突刺（59 秒 + 61 秒里放行双倍）——只在要求不高时用。
取舍一句话：要扛突发选令牌桶，要精确控速率选滑动窗口。
② Demo 现状（v1.4）：完全没有限流
在 v1.4 中，ShoppingAgentController 与 McpToolCallback 既不限制自身调用速率，也不处理下游限流响应： 每次请求触发的 queryProductInfo / search_knowledge 直接打向 MCP Server 与 MySQL/pgvector。 即使第八课加上熔断器，熔断也只防"下游挂了还去撞"，不防"我们把下游打挂"。
③ 限流粒度：按 Tool 分桶，再按调用方分层
按 Tool：每个 Tool 一个桶——`queryStock` 高频放得宽（如 100/min）， `place_order` 低频高危卡得紧（如 10/min）；读写分开定额。
按调用方：userId / agentId / 租户各一层配额——防止一个 Agent 或一个用户吃光全局额度。
配额从哪来：下游系统的 SLA 反推（ERP 每秒能扛 50 次，Agent 侧就定 30 次留余量）， 不是拍脑袋定的。
④ 超卖保护下游：限流之外还要并发控制
下单/扣库存这类 Tool，限流只控速率，不控同时在飞的请求数—— 还要：并发上限（同一商品同时最多 N 个扣减在飞）、库存乐观锁 （`UPDATE product SET stock=stock-1 WHERE id=? AND stock>0` 或版本号），以及幂等键（上一页）。 限流 + 并发上限 + 幂等 + 乐观锁，四件一起才能保证不超卖。
⑤ 超限了返回什么（三种策略，别静默吞）
排队：有界队列 + 队列等待超时——体验平滑，但队列不能无限长，等太久照样超时。
降级：返回缓存/简化结果（"库存信息延迟 1 分钟"），保住主流程。
拒绝：返回429 + Retry-After 与可读原因（"下单频率超限，请 30 秒后再试"）—— LLM 拿到明确错误才能正确转述给用户，静默失败会让它编答案。
✗ 限流（令牌桶/滑动窗口） ｜ 问题
Tool 调用没有任何速率与并发控制，LLM 循环失控、提示词注入批量调用、用户峰值都直接打到下游 ERP。
不解决
下游被打挂（雪崩到所有系统）、并发扣减超卖（发不出货+客诉）、被注入的 Agent 变成打别人的"肉鸡"——事故都出在"调太多"。
怎么解决
按 Tool 粒度限流（令牌桶扛突发 / 滑动窗口控速率，Redis+Lua 做分布式）+ 按用户/Agent 分层配额 + 写操作并发上限与乐观锁； 超限三选一：有界排队 / 降级返回缓存 / 429 + Retry-After 明确错误码。 取舍：限太紧误伤正常业务（峰值体验差），限太松等于没限——从下游 SLA 反推配额，先保命再优化。
