CHAPTER 07

审计 — 出事之后要能回答"谁干了什么"

① Demo 现状（v1.4）：只有文本日志，无链路 Trace 与审计表
MCP 调用日志：McpToolCallback.call() 打印 [MCP] 调用 Tool: {}, 参数: {} 和 [MCP] Tool 响应: {}（失败打 [MCP] 调用 Tool 失败）到控制台与应用日志。
LLM 交互日志：LlmInteractionLogger 按用途分文件写入 logs/llm-chat.log / llm-route.log / llm-extract.log。
v1.4 缺口：连结构化的步骤级 Trace 都还没有（第八课将构建 TraceService 记录每步调用，但也仅存内存 ConcurrentHashMap 重启即丢）。
结论：这是"排障用日志"，不是"问责用审计"——无持久化表、无字段规范、无防篡改与脱敏。
② 日志 vs 审计：用途不同
日志给开发排障：可裁剪、可打码、随版本变。
审计给合规与问责：字段固定、独立存储、只增不改、有留存期。 判断标准：这件事能不能拿到法庭/合规会上当证据。
③ 审计表怎么设计（一条记录答全五个问题）
谁：userId + agentId + 会话 sessionId + trace_id（把 Demo 的 traceId 接进来）
何时：请求时间、耗时（duration_ms）、结果状态（success / timeout / rejected / compensated）
什么：tool_name + 参数快照 + 参数哈希；PII 脱敏后落库（手机号留前 3 后 4）
结果：返回摘要 + 结果哈希 + 下游单号（orderId）；错误码与错误摘要
上下文：幂等键（idempotency_key）、触发来源（LLM 决策 / 系统自动 / 人工确认）、Trace 的 stepNumber
④ 写入与存储要求
写入时机：调用前记一笔（意图）、调用后补结果与耗时——两笔或带耗时的一笔，但失败也必须留痕。
独立存储：审计库与业务库分开、账号只给 INSERT 权限（防篡改），按月分区 + 留存期（金融常 1~3 年）。
回放：按 traceId 能把一次任务的调用链完整拼出来（Trace 的内存模型直接换成审计表即可）。
✗ 审计表设计 ｜ 问题
v1.4 只有文本日志（无结构化 Trace、无持久化审计表），日志可被清理或篡改，字段不固定且无 PII 脱敏规范。
不解决
出了事故（误下单、数据泄露、违规调用）无法回答"谁、何时、调了什么、结果是什么"，合规过不了，追责与复盘都无从下手。
怎么解决
审计表（含幂等键/traceId/参数与结果哈希/耗时/状态）+ 调用前后双写 + 独立库只增不改 + PII 落库前脱敏 + 留存期与分区。 取舍：全量参数快照可回放但存储大且有合规风险（存 PII），折中是存哈希 + 脱敏快照；审计写失败要不要挡业务——金融场景"审计失败即拒绝调用"。
