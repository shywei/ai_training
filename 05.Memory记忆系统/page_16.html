CHAPTER 08 · DEMO vs 生产

Demo vs 生产 — 记忆系统的五项差距

1 · Redis 集群与持久化
问题（Demo 现状）：单实例 Redis，无主从/Cluster、无 AOF/RDB 持久化配置；SessionMemory 与 SummaryPipeline 的近期对话（messages）及累积摘要（summary）全存在单点内存中。
不解决：Redis 一挂，所有活跃会话的最近对话与累积摘要瞬间丢失，Agent 对当前对话直接失忆；单实例内存 = 会话容量上限；故障全靠人工恢复。
怎么解决：Redis Cluster / 云 Redis 主从 + 哨兵自动切换；AOF everysec 把丢失窗口压到 1 秒；多 key 操作（messages 与 summary）用 hash tag {sid} 保证落同分片。取舍：Cluster 运维翻倍；后续（v3.0）将长期过程记忆沉淀至持久库后，可降低 Redis 可靠性要求。
2 · Session TTL 与动态触发淘汰
问题（Demo 现状）：Demo 按固定条数滑窗（MAX 20）与满 8 条压缩属于教学演示简化（Educational Simplification）；无 maxmemory 策略，也不按 Token 预算动态裁剪。
不解决：内存无界增长触顶导致 OOM 或乱淘汰；条数不等于 Token，几条长代码就会撑爆 Context Window。
怎么解决：maxmemory + volatile-lru；空闲 TTL + 绝对 TTL 双上限；生产必须改由 Token 预算阈值（达窗口 65%） 或 任务语义边界 触发动态压缩沉淀。取舍：Token 动态计算消耗微量 CPU，换来上下文绝对安全。
3 · 异步抽取可靠性与失败重试
问题（Demo 现状）：Demo 虽用 @Async（UserProfileExtractor）异步触发画像抽取（或经 /profile/extract 触发），但仅靠内存线程池执行，JSON 解析或 LLM 调用失败只打印日志返回 null，无重试、无死信队列（DLQ）。
不解决：进程重启时排队中的异步任务直接丢失；抽取失败画像静默缺失——用户以为偏好被记住了其实没有，极难排查。
怎么解决：持久化消息队列（Redis Stream / RabbitMQ / Kafka）替代纯内存 @Async；失败指数退避重试 2-3 次，仍失败入死信队列（DLQ）+ 定时重放；幂等键（userId + sessionId + offset）防重复合并。取舍：异步队列引入最终一致性，需配合前端状态提示。
4 · 隐私合规（用户可遗忘权）
问题（Demo 现状）：/api/agent/memory/clear 只清理 Redis 会话缓冲；MySQL user_profile 表与日志文件（llm-interactions.log / llm-profile.log）没有任何级联删除通道；无入库 PII 脱敏、无删除审计。
不解决：GDPR / 个保法的被遗忘权无法履行——用户要求删数据，MySQL 画像与日志原文仍在；PII 明文入库又明文进日志，合规风险极高。
怎么解决：按 userId 的级联删除（MySQL user_profile + Redis session + 后续向量库）+ 删除审计记录；30 天宽限期后物理删除；入库前 PII 正则/NER 脱敏（手机号前 3 后 4、证件/卡号不落库）；画像可查可导出。取舍：脱敏损失少量细粒度信息换取合规安全。
5 · 跨实例记忆并发与共享
问题（Demo 现状）：单实例假设：SummaryPipeline（满 8 条压缩重写 Redis）与 UserProfileExtractor（读旧画像 → LLM 合并 → 写回 MySQL）均无分布式锁与版本控制。
不解决：多实例并发处理同一用户时，SummaryPipeline 会重复触发并覆盖新消息；画像合并发生经典"读-改-写"并发覆盖（Lost Update），丢失用户偏好更新。
怎么解决：按 (userId, sessionId) 加 Redis 分布式锁（SETNX + TTL）或按 session 分区队列串行消费；MySQL user_profile 增加乐观锁（version / updated_at），冲突时重读重合并。取舍：同一用户操作串行化，换取多实例下的数据强一致。
五项的共同点 · 平台化去向
Demo（v1.2.1）用"单点 Redis + 内存异步无重试 + 无级联删除"换取教学演示清晰；生产三件套 = 高可用存储 + 可靠异步队列(含重试/DLQ) + 级联删除与并发锁闭环。隐私合规与跨 Agent 记忆共享将在第十一课平台化落地，第九课框架重构时对比框架接管边界。
