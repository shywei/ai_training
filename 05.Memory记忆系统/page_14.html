CHAPTER 08 · 架构演进预告（v2.0 → v3.0）

记忆分层演进 — 从结论层(MySQL)到过程层(pgvector)

结论层（本课 v2.0 已落地）· MySQL user_profile — 画像存"结论"
存什么：LLM 合并后的结构化结论（facts / preferences / tasks / constraints）。
怎么写：UserProfileExtractor.extract() — 旧画像 + 新对话 → 推理模型合并，写 MySQL。
怎么读：MemoryManager.buildContext() 直查 MySQL，全量注入 context 的「## 用户画像」。
特点：每用户一行、有界、长期保留；可展示给用户、支持人工更正。
过程层（下节课 v3.0 演进目标）· pgvector user_memory — 对话存"过程"
演进定位：第六课（v3.0 引入 pgvector）与第七课（v4.0 MCP 化）落地！解决 Redis 累积摘要长期越压越厚问题。
存什么：自然语言记忆（对话切片提要、业务事件），存入 pgvector 的 user_memory 表（含 vector 列）。
怎么读写：满阈值自动将旧对话提要并向量化入库；对话时按需语义检索 top3 注入「## 相关记忆」。
特点：持续增长、只增不改（客观事实记录）；靠 top-k + 相似度阈值截流。
工作缓冲区（本课 v2.0 已落地）· Redis session:{sid}:messages & summary
本课 v2.0 形态：SessionMemory（滑动窗口 MAX 20 / 24h TTL）+ SummaryPipeline 滚动压缩。
v2.0 → v3.0 演进原因：累积摘要常驻 Redis 易失且不可按语义检索；下节课引入 pgvector 过程层后，旧对话沉淀进向量库，Redis 回归纯粹的近期工作缓冲区。
为什么必须分两个库？
1 · 读取模式不同
结论是全量注入（几行字直接拼进 Prompt），过程是按需语义检索（按当前问题查 top3）。全量注入塞不下持续增长的过程数据。
2 · 更新语义不同
结论会被修正（预算 8000 → 10000，新覆盖旧），过程只增不改（客观历史记录不能伪造）。两种更新语义无法在单表统一。
3 · 生命周期与合规不同
画像有界（每用户一行），过程无界（持续增长需向量索引截流）。画像支持用户直接查看与更正；过程数据包含历史 PII 原文，需支持级联删除以履行合规被遗忘权。
认知复用：第六课 Knowledge 数据分层
“结论进关系库、语义化原文进向量库”在 Knowledge 侧一模一样：商品静态描述进 pgvector，动态价格库存进 MySQL product 表。
⚠️ 教学演示简化标注：Demo 中的“满 8 条压缩”或“5 轮对话后从 Redis 刷入 pgvector”属于教学演示简化（Educational Simplification）；生产实践多采用 Token 预算阈值触发（达窗口 65%）、语义完整性任务边界触发或异步周期性合并沉淀。
