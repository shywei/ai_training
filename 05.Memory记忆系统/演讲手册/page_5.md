## Slide Objective
讲透 Session Memory 的方案全景——每种方案的原理、数据结构、适用场景、工程细节。

## Suggested Presentation
Session Memory 有四种方案，每种都有明确的适用场景。

**方案一：内存存储（ConcurrentHashMap / Caffeine）**

最简单。数据存在 JVM 堆里，读写零网络延迟。ConcurrentHashMap 是 JDK 自带的线程安全 Map，Caffeine 是 Google 出的高性能缓存库（Guava Cache 的升级版），支持过期策略、容量上限、异步加载。

但有两个致命问题。第一，重启丢失——JVM 一停，所有 Session 消失。用户正在聊天，服务重启了，对话历史全没了。第二，不支持多实例——如果你部署了 3 个实例，用户的请求被负载均衡到不同实例，每个实例只存了部分对话。

适用场景：原型开发、单机部署、对数据丢失不敏感的内部工具。

**方案二：Redis（Demo 选择，主流方案）**

Redis 是生产环境的主流选择。核心优势：List 结构天然适合消息队列——RPUSH 追加、LRANGE 读取、LPOP 裁剪。自带 EXPIRE 过期机制，不用自己写清理逻辑。支持集群部署，多实例共享同一个 Redis。

Redis 的数据结构选择：Demo 用了 List，因为消息是有序的、需要按时间追加。也可以用 Hash（以消息 ID 为 field）——好处是可以按 ID 删除单条消息，坏处是不保序。还可以用 Stream（Redis 5.0+）——天然支持消费者组和持久化，但复杂度更高。

踩坑经验：Redis 的 List 操作是原子的，但多个请求同时写同一个 Session 时，消息顺序可能乱。比如用户快速连发两条消息，两个请求同时 RPUSH，顺序不确定。实际项目中应该用 MULTI/EXEC 事务，或者用消息队列保证顺序。Demo 里没有处理这个问题。

另一个踩坑经验：Redis 的 EXPIRE 是从最后一次写入开始计时的。如果你设了 24 小时过期，用户每发一条消息，过期时间就重置为 24 小时后。这意味着只要用户持续对话，Session 永远不过期。只有用户停止对话 24 小时后，Session 才会自动清理。这通常是期望的行为，但要意识到这个特性。

**方案三：数据库（MySQL / PostgreSQL）**

读写慢但持久化、可查询。适合需要审计和合规的场景——比如金融行业的客服系统，每条对话都要留痕，监管机构随时可能要求调取。

数据库方案的另一个优势是可以做复杂的查询——"查找所有包含'退货'关键词的对话"、"统计每个用户的平均对话轮数"。Redis 做这些查询很困难。

适用场景：需要审计、合规、复杂查询的场景。缺点是读写延迟比 Redis 高一个数量级。

**Token 爆炸问题——所有方案都要面对**

不管用哪种存储，对话越来越长都会导致 Token 成本越来越高。两种解决策略：滑动窗口（裁掉旧消息，简单但丢失信息）和后台压缩（旧消息变摘要，保留信息但需要调用 LLM）。这两种策略在下一页详讲。

**Memory 生命周期**

企业必须回答的问题：Memory 会无限增长吗？答案是不能。必须有生命周期管理：Message（新消息）→ Session（当前对话）→ Summary（压缩后的摘要）→ Archive（归档到冷存储）→ Delete（最终删除）。Demo 只实现了前两步，实际项目需要完整的生命周期。

## Key Emphasis
每种方案的"为什么"比"是什么"更重要。不是"Redis 能存 Session"，而是"为什么选 Redis 而不是内存或数据库"。踩坑经验是核心——不是假设的坑，是做 Demo 时真正遇到的。
