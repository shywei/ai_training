# Page 9 — 用户画像 — 设计模式

## Slide Objective
讲透用户画像的完整知识体系——分类方式、触发机制、更新策略、存储格式、实际工程问题。

## Suggested Presentation
用户画像不是"聊天记录的摘要"，而是结构化的用户信息。这一页讲设计模式。

**分类方式——四维度的设计逻辑**

四维度不是随意设计的，每种维度的更新策略不同：
- **Fact 事实**（姓名、职业、年龄）：客观信息，补充修正，一般不会频繁反转。
- **Preference 偏好**（颜色、品牌、预算、风格）：主观喜好，新覆盖旧。用户先说"预算 8000"，后来说"预算改成 10000"，应该用新偏好覆盖旧偏好。
- **Task 任务**（当前需求、待办事项）：短期信息，完成即删。用户说"我在找一台写代码的笔记本"，买完就应该清除。
- **Constraint 约束**（禁区、限制、不要的东西）：长期保留。用户说"不要游戏本"，这个限制应该一直保留。

**触发机制——不只是"什么时候触发"**

1. **实时抽取（每轮对话后同步调）**：及时但成本高、拖慢响应。适合高价值低频场景。
2. **异步 / 事件触发（Demo 选择）**：对话后通过 `@Async` 后台异步抽取，或显式调用 `/profile/extract` 接口触发，外加会话结束（`/memory/clear`）兜底。优点是不阻塞主对话流、成本可控。
3. **批量抽取（定时任务）**：每天凌晨分析所有用户近期对话。成本最低，但有天级延迟。
4. **混合方案（实际项目推荐）**：高置信度信息异步准实时抽取，复杂潜在偏好夜间批量分析。

**更新策略——新信息和旧信息怎么合并**

直接覆盖会丢失历史。正确做法是**合并更新**——把 MySQL 中的旧画像和 Redis 中的新对话一起传给推理模型，让 LLM 根据新对话生成合并后的 JSON 画像，且空值不覆盖已有字段。

## Key Emphasis
四维度的更新策略是核心——Fact 补充修正、Preference 新覆盖旧、Task 完成即删、Constraint 长期保留。这个设计逻辑比具体表结构更重要。

## Optional Extension
**学员问：四维度设计在实际表结构里怎么存？**
答：本课 Demo（`v1.2.1`）在 MySQL `user_profile` 表中直接设计了 `facts`、`preferences`、`tasks`、`constraints` 四个字段（见 `UserProfile.java`），直观清晰；生产环境若维度需要动态扩展，可使用 PostgreSQL `JSONB` 或 MySQL `JSON` 列配合版本号字段。

## Classroom Interaction
让学员说三句话（"我叫张三，是程序员" / "预算改成 1 万" / "不要游戏本"），先预测各自落进四维度的哪个字段、用什么更新策略，再在下一页跑 Demo 对照 `logs/llm-profile.log` 的合并结果。

## Take Away
画像字段的更新策略（只增 / 覆盖 / 完成即删）比字段数量重要——设计字段前先想清楚"这个字段以后怎么变"。

## Why This Slide Matters
统一用"全量覆盖"更新画像的系统，会误删历史事实；统一用"无脑追加"的系统，会让新旧预算自相矛盾——更新策略必须在设计阶段定清。
