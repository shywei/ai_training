## Slide Objective
讲透用户画像的完整知识体系——分类方式、触发机制、更新策略、存储格式、实际工程问题。

## Suggested Presentation
用户画像不是"聊天记录的摘要"，而是结构化的用户信息。这一页讲设计模式。

**分类方式——四维度的设计逻辑**

四维度不是随意设计的，每种维度的更新策略不同：
- Fact 事实（姓名、职业）：客观信息，只增不改。用户说"我叫张三"，以后不会变成"我叫李四"。
- Preference 偏好（颜色、品牌、预算）：主观喜好，新覆盖旧。用户说"我预算 8000"，后来又说"预算改成 10000"，应该覆盖。
- Task 任务（当前需求）：短期信息，完成即删。用户说"我在找一台写代码的笔记本"，买完就应该清除。
- Constraint 约束（禁区、限制）：长期保留。用户说"不要游戏本"，这个限制应该一直保留。

这四种维度的更新策略不一样——如果统一用"新覆盖旧"，Fact 会被误改，Task 会永远积累。Demo 里用 LLM 自主判断保留什么、更新什么，但实际项目中应该在代码层面强制执行策略。

**触发机制——不只是"什么时候触发"**

实时抽取（每轮对话后）：每轮对话结束后调 LLM 分析对话，提取画像信息。优点是及时，缺点是成本高——每轮对话多一次 LLM 调用。适合高价值场景，比如金融顾问、医疗问诊。

事件触发（Demo 选择）：用户说"记住"时触发，会话结束兜底。优点是成本可控、用户有感知。缺点是用户不说"记住"，画像就不会更新。Demo 选择这个方案是因为它更符合产品设计原则——用户有知情权和控制权。

批量抽取（定时任务）：每天凌晨跑一次，分析所有用户近期对话。优点是成本最低（可以批量处理、用便宜模型），缺点是有延迟——用户今天的偏好，明天才会被记住。适合用户量大、对实时性要求不高的场景。

混合方案（实际项目推荐）：高置信度信息实时抽取（用户说"我叫张三"，立即存入 Fact），复杂偏好批量分析（用户最近总在看轻薄本，批量任务分析后存入 Preference）。

按条数触发是不好的设计——用户没说要记，你就在分析他的对话，感觉像偷窥。而且按条数触发会产生大量无效 LLM 调用（用户只是在闲聊，不需要抽取画像）。

**更新策略——新信息和旧信息怎么合并**

直接覆盖会丢失历史。正确做法是合并更新——旧画像传给 LLM，LLM 根据新对话生成合并后的画像。空值不覆盖——如果 LLM 返回 `{"preferences":""}`，不会覆盖已有的偏好。

踩坑经验：一开始用快模型做画像抽取，返回的 JSON 经常格式错误——值不加引号、多余逗号、少一个大括号。Jackson 解析直接报错。后来改成推理模型，JSON 格式稳定多了。但推理模型更贵，所以只在画像抽取时用，压缩还是用快模型。

**存储格式**

MySQL 结构化字段（Demo 选择）：四个字段对应四维度，简单直接。优点是可查询、可编程。缺点是维度固定，加新维度要改表。

JSONB：PostgreSQL 的 JSON 字段。优点是灵活，可以存任意结构。缺点是查询不如结构化字段方便。

向量数据库：把画像内容转为向量存储。优点是支持语义检索（"找喜欢轻薄本的用户"）。缺点是实现复杂，通常和 RAG 系统配合使用。

## Key Emphasis
四维度的更新策略是核心——Fact 只增不改、Preference 新覆盖旧、Task 完成即删、Constraint 长期保留。这个设计逻辑比"Demo 用了什么"更重要。
