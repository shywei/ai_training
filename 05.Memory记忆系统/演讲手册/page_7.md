## Slide Objective
讲透上下文压缩的完整知识体系——四种策略的原理、实现细节、实际工程中的问题。

## Suggested Presentation
对话越来越长，Token 成本越来越高。需要压缩。但压缩有四种策略，各有取舍。

**策略一：滑动窗口**

最简单。保留最近 N 条消息，裁掉旧的。N 的选择很关键——太小会丢失重要上下文，太大失去了压缩的意义。Demo 里设了 20 条上限，超过就 LPOP 最旧的。

滑动窗口的问题：用户前面说过"我预算 8000"，被裁掉后 Agent 就忘了。这在短对话里不是问题（3-5 轮的对话不需要压缩），但在长对话里是致命的——用户聊了 20 轮，前面的关键信息全丢了。

**策略二：累积摘要（Demo 选择）**

核心思想：不是直接丢弃旧消息，而是用 LLM 把旧消息压缩成摘要，摘要和新消息共存。

具体实现：当消息数超过阈值（Demo 设为 8），取出前 N-K 条（K 是保留的最近消息数，Demo 设为 4），把这些消息拼成一段文本，让 LLM 压缩成 200-300 字的摘要。摘要以 `[对话摘要]` 前缀存入 Redis，和最近的 K 条消息共存。

累积的关键：第二次压缩时，旧摘要也会被传给 LLM。Prompt 里明确告诉 LLM"之前已经有一份摘要，现在需要合并"。这样摘要 B 包含摘要 A 的信息，不会丢失历史。

踩坑经验：一开始 Prompt 只写了"压缩以下对话"，没有告诉 LLM 之前有旧摘要。结果每次压缩都从头开始，早期的信息反复丢失。后来加了"合并旧摘要"的指令，问题解决了。

模型选择：压缩用快模型（Qwen2.5-7B），因为它只是压缩文本，不需要推理能力。画像抽取用推理模型（Qwen3-8B），因为需要输出严格 JSON。踩坑经验：一开始画像抽取也用快模型，结果返回的 JSON 经常格式错误——值不加引号、多余逗号。改成推理模型后稳定多了。这就是为什么配置里 summary 和 extract 要分开。

阈值设置：Demo 设为 8 条方便演示。实际项目应该设 30-50。踩坑经验：一开始设为 8，结果每次聊 4 轮就触发压缩，压缩本身要调一次 LLM，有延迟，用户体验很差。后来改成 20，压缩阈值设为 8，问题解决了。所以阈值设置要考虑"压缩本身的延迟"。

**策略三：关键词抽取**

从对话中提取关键实体存入结构化字段。比如用户说"我预算 8000，喜欢轻薄本"，提取出 `budget=8000`、`preference=轻薄本` 存入数据库。

优点是精确、可查询——可以直接查"所有预算超过 5000 的用户"。缺点是丢失语境——你只知道用户说了"8000"，不知道是在什么上下文下说的（是买笔记本的预算还是买耳机的预算）。

通常和画像系统配合使用——画像的四个维度本质上就是一种关键词抽取。

**策略四：Embedding 压缩**

把每条对话消息转为向量，存入向量数据库。需要检索时，把用户的问题也转为向量，找最相似的历史消息。

优点是语义级别检索——用户问"我之前聊过什么关于笔记本的"，能匹配到语义相关的对话。缺点是需要向量 DB，实现复杂，成本高。

本质是把 Session Memory 和 Knowledge 的边界模糊化了。适合超长对话和企业级场景。

**组合使用**

实际项目中，滑动窗口加累积摘要组合使用最常见。关键词抽取作为补充（和画像系统配合）。Embedding 作为高级选项。

## Key Emphasis
每种策略的"为什么"比"是什么"更重要。累积摘要的踩坑经验（旧摘要合并、模型选择、阈值设置）是核心——这些是做 Demo 时真正遇到的问题。
