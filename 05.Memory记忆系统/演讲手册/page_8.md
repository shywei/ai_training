## Slide Objective
展示 Demo 的累积压缩实现，讲解代码细节和踩坑经验。

## Suggested Presentation
看左边的累积压缩流程。消息超过 8 条触发压缩。取前 N-4 条（含旧摘要），用快模型压缩，写回 Redis。

关键设计：第二次压缩时，旧摘要也会被传给 LLM。看 SummaryPipeline.java 的 summarizeSession 方法。它先检查消息里有没有以 `[对话摘要]` 开头的条目——如果有，说明之前已经压缩过，就把旧摘要内容也放进 Prompt 里，让 LLM 合并。Prompt 里写的是"之前已经有一份摘要，现在需要将旧摘要和新对话合并为一份更新的摘要"。

踩坑经验：一开始 Prompt 只写了"压缩以下对话"，没有告诉 LLM 之前有旧摘要。结果每次压缩都从头开始，早期的信息反复丢失。后来加了"合并旧摘要"的指令，问题解决了。

看右边的关键设计。阈值设为 8 方便演示——实际项目应该设 30-50，因为压缩本身要调一次 LLM，有延迟。模型用 `agent.model.summary` 配置，从 yml 读取。为什么不用推理模型？因为压缩只是压缩文本，不需要推理能力，用最便宜的模型就行。画像抽取才需要推理模型（因为要输出严格 JSON）。

踩坑经验：一开始画像抽取也用快模型（Qwen2.5-7B），结果返回的 JSON 经常格式错误——值不加引号、多余逗号、少一个大括号。Jackson 解析直接报错。后来改成推理模型（Qwen3-8B），JSON 格式稳定多了。这就是为什么配置里 summary 和 extract 要分开——不同任务用不同模型。

验证方法：聊超过 8 轮后，看 `logs/llm-summary.log 或 llm-profile.log`。里面有压缩请求的完整 Prompt（包括旧摘要）、LLM 返回的新摘要、以及压缩后的消息列表。这个日志文件是演示的核心工具——打开它，学员能直观看到"压缩是怎么工作的"。

## Key Emphasis
踩坑经验是核心——不是"理论上可能出问题"，而是"做 Demo 时真正踩过的坑"。模型选择的教训（快模型 vs 推理模型）要讲透。
