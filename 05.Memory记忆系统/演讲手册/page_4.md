# Page 4 — 记忆系统双层解耦架构：逻辑记忆分类 vs 物理存储映射

## Slide Objective
打破“记忆分类与物理存储混为一谈”的严重概念误区，建立 **双层解耦架构**：
- **第一层 · 逻辑记忆分类体系（Logical Memory Classification）：** 确立**课程定义的工程分类模型**，清晰区分作为**原始记录载体**的 **Conversation History**，与四大**认知记忆类型**（**Working Memory、Episodic Memory、Semantic Memory、Procedural Memory**）。
- **第二层 · 物理存储与生命周期实现（Storage Implementation）：** 按读写频率、生命周期与检索模式映射至 **Redis、MySQL、pgvector、事件溯源、TTL 衰减与滚动摘要**。
讲透两层之间不是一一对应关系，并清晰锚定当前 Demo（v2.0）的精准落地坐标。

## Suggested Presentation

### 一、打破认知误区：拒绝“概念浆糊”
在不少工程师的认知里，往往把“工作记忆、短期记忆、Redis、pgvector”杂糅在同一张表里：
- “工作记忆”和“短期记忆”是什么关系？
- “用户画像”到底算不算长期记忆？
- “pgvector”是一种记忆类型吗？

**明确正本清源：**
pgvector 是物理存储引擎，不是记忆类型；Context Window 是模型运行态上下文空间，不是持久化数据库；用户画像是长期语义记忆的一种结构化表现。
因此，必须在架构上明确划分为**两个独立的层次**：
1. **第一层（逻辑层）：** 采用**课程定义的工程分类模型**，解决“大模型在认知层面记住了什么、起什么作用”；特别说明：会话历史更接近原始时序记录的载体，是抽取下述各类认知记忆的数据源泉，而非认知记忆本身；
2. **第二层（工程物理层）：** 解决“数据存在哪里、生命周期多长、如何治理与并发控制”。

---

### 二、第一层：逻辑记忆体系解构（记录载体 + 四大认知类型）

1. **会话历史 (Conversation History) — 原始时序流水载体：**
   - **核心定义：** 用户与 Agent 交互产生的全部原始消息流水帧（User/Assistant/Tool），单调递增追加的记录载体。
   - **核心价值：** 审计质检、法律合规、纠纷回溯，以及作为提取认知记忆（画像、反思）的数据源。
   - **物理落点：** 活跃近景存 Redis List；历史归档全量持久化至 MySQL / ES。

2. **工作记忆 (Working Memory) — 运行态动态草稿纸：**
   - **核心定义：** Agent 在执行单次多步复杂任务（如 ReAct 循环、多工具协同、代码分析）时的临时状态、中间推理草稿（Scratchpad）与步骤变量。
   - **核心价值：** 支撑模型多步推理与反思，任务结束或请求返回后即刻销毁。
   - **物理落点：** 驻留在当前 LLM 的 Context Window 或 Java 进程内存（ThreadLocal / Memory Context）。

3. **情景记忆 (Episodic Memory) — 时空经历与事件复盘：**
   - **核心定义：** 包含明确时间、地点、因果背景与成败结局的具体经历事件记录（例如“上周为某 VIP 用户推荐轻薄本因未核对库存导致投诉事件”）。
   - **核心价值：** 赋予 Agent “从历史教训或成功案例中复盘反思”的类人能力，在相似场景主动规避重蹈覆辙。
   - **物理落点：** 事件记录（Event Sourcing）+ 向量时序索引与知识图谱。

4. **语义事实与画像 (Semantic Memory) — 稳定事实与静态偏好：**
   - **核心定义：** 跨越会话边界沉淀的结构化与非结构化客观事实，包括通用领域知识、规则，以及从历史对话中萃取的用户稳定属性画像（Profile）。
   - **核心价值：** 结构化部分（Profile）信息密度极高，可每轮稳定注入 Prompt；非结构化事实通过向量检索按需唤醒。
   - **物理落点：** 结构化画像落 MySQL `user_profile`；非结构化语义事实落 pgvector。

5. **程序记忆 (Procedural Memory) — 操作技能与任务 SOP：**
   - **核心定义：** 执行特定任务的经验策略、操作技能、最佳工具调用链路与工作流 SOP（“怎么做”的程序性知识）。
   - **核心价值：** 固化最佳实践，提升 Agent 工具调用的准确率与执行效率。
   - **物理落点：** Prompt 策略模板库、系统规则集或微调 LoRA 权重。

### 三、第二层：物理存储与生命周期映射

引导学员理解：**逻辑记忆与存储引擎是“多对多”映射，绝非一一绑定！**
- **Redis 内存缓存：** 专为高频读写设计，用于存放 Conversation History 的近期近景窗口（Sliding Window，如最近 20 条），配合 24h 滑动 TTL 衰减；
- **MySQL 关系数据库：** 提供强 ACID 事务与行级更新，用于存放结构化用户画像（Semantic Memory 的结构化部分），支持大模型异步抽取与新旧结论合并；
- **pgvector 向量检索：** 支撑非结构化语义记忆与情景经历的高维近似检索；
- **生命周期治理组件：** `SummaryPipeline` 滚动摘要、Mem0 状态冲突消解（ADD/UPDATE/DELETE/NOOP）、遗忘衰减与并发版本控制。

---

### 四、Demo（v2.0）精准落地坐标
- **当前 Demo 聚焦两项最关键的基础底座：**
  1. **短期会话历史缓冲：** 基于 Redis List 维护最近 20 条消息窗口，配合 Summary 摘要压缩；
  2. **静态画像沉淀：** 基于 MySQL `user_profile` 存储，异步触发大模型抽取与新旧偏好覆盖合并。
- **演进路线：** 后续第六课引入 pgvector 向量检索拓展长期语义记忆，第八课引入状态机强化工作记忆管理。

## Key Emphasis
1. **两层严格分离：** 逻辑层回答“记什么”，物理层回答“存哪里”。严禁把 pgvector 称作“一种记忆类型”。
2. **画像属于语义记忆：** 用户画像是 Semantic Memory 在企业中最典型的结构化表现形式。
3. **Demo 边界明确：** v2.0 Demo 稳扎稳打实现 Redis 会话缓冲 + MySQL 画像抽取合并。
