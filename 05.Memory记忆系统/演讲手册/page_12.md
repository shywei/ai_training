# Page 12 — 记忆安全与隐私 — 企业必须回答的问题

## Slide Objective
讲透记忆系统的安全与隐私——不只是"有哪些问题"，而是"企业落地怎么解决"。

## Suggested Presentation
这一页是企业架构必修课。Demo 为了教学聚焦没有实现复杂的脱敏与审计，但企业落地时，安全和隐私是第一优先级。

**1. 数据保留策略——Memory 不能无限增长**

企业必须回答四个问题：
- Session 数据保留多久？通常 24 小时到 7 天。本课 Demo 在 `SessionMemory` 中设了 24 小时 `EXPIRE`。
- 用户画像保留多久？通常长期保留，但应记录 `updated_at`（最后更新时间），超过半年未更新的偏好应降权或标记过时。
- 用户要求"忘记我"怎么办？GDPR 和《个人信息保护法》都要求提供被遗忘权（删除权）。需要同时清理 Redis 会话缓冲和 MySQL `user_profile` 画像。Demo 的"清空会话"按钮只清了 Redis，生产项目必须提供级联删除接口。
- 谁有权删除？只有用户本人和授权管理员，且删除操作必须留存审计日志。

**2. PII 脱敏——存入数据库与发送给 LLM 前必须处理**

用户说"我叫张三，手机号 13800138000"，画像和日志里绝不能存明文敏感 PII（手机号、身份证号、银行卡号、详细家庭住址）。
脱敏方法：在写入 MySQL 和拼接 Prompt 发送给第三方大模型 API 之前，通过独立的正则/NER 脱敏过滤器（如手机号打码为 `138****8000`、身份证与银行卡号直接拦截不落库）。

**3. 上下文泄露风险与合规要求**

画像和对话注入到 LLM 请求里，如果调用的是公有云大模型 API，数据就离开了企业边界。
解决方案：金融/政务/医疗等高敏场景采用私有化部署大模型，或严格执行"入库前 + 调用前"双层 PII 脱敏过滤。同时提供画像查询、更正、删除接口，满足 GDPR / 个保法合规要求。

## Key Emphasis
安全和隐私不是"附加功能"，而是"上线红线"。重点讲清：**PII 脱敏过滤防线**（落库前 + 调 LLM 前）和**被遗忘权级联删除**（Redis + MySQL 都得删）。

## Optional Extension
**学员问：用户要求"删掉我的数据"，到底要删哪儿？**
答：先画数据地图，再做级联删除。
Demo 做法：课堂上明确指出本课 Demo（`v1.2.1`）的缺口——`/api/agent/memory/clear` 只清了 Redis 的 `session:{sid}:messages`，MySQL 的 `user_profile` 表和 `logs/` 下的日志文件都没有清理。
生产做法：按 `userId` 执行级联删除（MySQL `user_profile` + Redis 会话 + 后续课程引入的向量库）+ 写入删除审计记录；入库前做 PII 脱敏。这套方案会在 Page 16 第 4 项（隐私合规差距）给出完整三格落地法。

## Classroom Interaction
让学员现场盘点本课 Demo 中"一个用户的数据散落在哪几个存储、哪几个日志文件"（答案：Redis `session:{sid}:messages`、MySQL `user_profile`、以及 `llm-interactions.log` / `llm-summary.log` / `llm-profile.log`）——盘点完立刻理解为什么"删除权是数据架构问题"。

## Take Away
隐私合规必须第一天进数据模型：入库前 PII 脱敏，删除时按用户数据地图级联清理。

## Why This Slide Matters
没有删除通道和脱敏过滤的系统上线后无法低成本整改——PII 明文一旦散落到数据库和日志各处，事后补救等于推倒重建。
