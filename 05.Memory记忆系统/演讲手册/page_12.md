## Slide Objective
讲透记忆系统的安全与隐私——不只是"有哪些问题"，而是"怎么解决"。

## Suggested Presentation
这一页是纯知识体系，Demo 没有实现，但比 Demo 更重要。企业落地时，安全和隐私是第一优先级。

**数据保留策略——Memory 不能无限增长**

企业必须回答四个问题：
1. Session 数据保留多久？通常 24 小时到 7 天。Demo 里设了 24 小时 EXPIRE。实际项目中，客服场景可能要保留 7 天（用户可能隔几天再来问），内部工具可能只保留 1 小时。
2. 用户画像保留多久？通常永久，除非用户要求删除。但要注意：用户的偏好会变化——三年前喜欢轻薄本，现在可能喜欢游戏本了。画像应该有"最后更新时间"，超过一定时间未更新的画像应该标记为"可能过时"。
3. 用户要求"忘记"怎么办？GDPR 和个保法都要求提供"删除我的数据"功能。需要同时删除 Session 数据（Redis）和画像数据（MySQL）。Demo 里有"清空记忆"按钮，但只清了 Redis，没有清 MySQL 的画像。实际项目中必须两个都清。
4. 谁有权删除？通常只有用户本人和管理员。需要权限控制。

**PII 脱敏——存入数据库前必须处理**

用户说"我叫张三，手机号 13800138000"，画像里不应该存明文手机号。PII（Personally Identifiable Information）包括：姓名、手机号、地址、身份证号、银行卡号、邮箱。

脱敏方法：手机号只存前三位后四位（138****8000），地址只存城市不存门牌号，姓名可以存（用户主动提供的），身份证号和银行卡号绝对不能存。

Demo 里没有实现 PII 脱敏——用户说什么就存什么。实际项目中，存入 MySQL 前必须过一层脱敏过滤器。

**上下文泄露——最容易被忽略的风险**

画像和对话注入到 LLM 请求里，如果 LLM API 是第三方服务（OpenAI、硅基流动、DeepSeek），数据就离开了企业边界。

风险等级：用户的姓名和偏好泄露风险较低，但手机号、地址、消费金额泄露风险很高。

解决方案：
1. 私有化部署 LLM：成本最高但最安全。适合金融、医疗等对数据安全要求极高的行业。
2. 数据脱敏后发送：把 PII 脱敏后再注入 context。折中方案。
3. 只发摘要不发原文：把对话历史压缩成摘要再发送，减少泄露面。Demo 里的累积压缩其实就有这个效果。
4. 使用国内合规的 API 服务商：硅基流动、DeepSeek 等，数据在国内，符合个保法。

**审计日志——合规要求**

GDPR 和个保法要求：用户有权查看自己的画像（需要提供查询接口），用户有权要求删除（需要提供删除接口），需要审计日志（谁在什么时候访问了什么数据）。

Demo 里的 `logs/llm-summary.log 或 llm-profile.log` 其实就是一种审计日志——记录了每次画像抽取的输入和输出。实际项目中还需要记录"谁查看了画像"、"谁删除了画像"。

## Key Emphasis
安全和隐私不是"附加功能"，而是"必须功能"。学员需要理解：技术方案只是 Memory 的一半，安全合规是另一半。Demo 为了演示简单没有实现这些，但实际项目中必须做。
