# Page 14 — 记忆分层演进 — 从结论层(MySQL)到过程层(pgvector)

### 一、本课已落地 vs 下一课演进目标
先看左边三张卡片，搞清楚**本课已经落地了什么、下一课要演进什么**：
1. **蓝卡：结论层（本课 v2.0 已落地）· MySQL `user_profile` —— 画像存"结论"**
   存的是 `UserProfileExtractor.extract()` 用推理模型合并出来的结构化结论（`facts / preferences / tasks / constraints`）。读的时候由 `MemoryManager.buildContext()` 按主键查出，**全量注入**到 `context` 的 `## 用户画像`（到了第七课 v4.0 会进一步封装成标准 MCP Resource）。特点是每用户几行、有界、可展示给用户更正。
2. **绿卡：工作缓冲区（本课 v2.0 已落地）· Redis `session:{sid}:messages & summary`**
   本课 v2.0 中，`SessionMemory` 存最近对话，`SummaryPipeline` 在满 8 条时把旧消息压缩为累积摘要留在 Redis。但留个思考题：如果一个老用户聊了半年、几百轮对话，Redis 里的累积摘要越压越厚，一旦 Redis 过期或重启就全丢了，而且也没法按当前问题去搜索"三个月前聊过的某款具体型号"——怎么办？
3. **橙卡：过程层（下节课 v3.0 演进目标）· pgvector `user_memory` —— 对话存"过程"**
   这就是下一课（第六课引入 pgvector）和第七课（MCP 化）要正式落地的**过程层**：把旧对话提要后通过 Embedding 写入 pgvector 的 `user_memory` 表；对话时按用户当前问题做**按需语义检索**（召回 top3 注入 `## 相关记忆`）。这样 Redis 就回归纯粹的短期工作缓冲区，长期过程记忆交给 pgvector。

### 二、为什么必须分两个库？（五大工程理由）
到了下节课引入 pgvector 后，为什么不能把 MySQL 画像也塞进向量库，而是必须分两个库？
1. **读取模式不同**：结论层是**全量注入**（几行字直接拼进 Prompt），过程层是**按需语义检索**（按当前问题查 top3）。
2. **更新语义不同**：结论**会被修正**（预算 8000 → 10000，新覆盖旧），过程**只增不改**（客观历史记录不能篡改）。
3. **生命周期不同**：结论有界（每用户一行记录），过程无界（随对话持续增长，靠向量索引 + top-k 截流）。
4. **合规与可解释不同**：结论要给用户看、让用户改；过程含对话细节，需脱敏、定留存期、级联删除。
5. **查询与索引不同**：画像按 `user_id` 主键一行查走；过程记忆按 `user_id + 向量余弦相似度（HNSW 索引）` 检索。

看右下角紫色卡片：**这个判断在第六课直接复用**——到了第六课做企业知识库（Knowledge）时，商品评测描述进 pgvector（语义检索），商品价格库存进 MySQL `product` 表（精确查询、频繁更新），底层逻辑一模一样！

### 三、⚠️ 教学演示简化（Educational Simplification）声明
看幻灯片底部的黄色横幅，向学员郑重指出：
- **Demo 的简化设计：** 
  Demo 中为了教学演示直观、便于断点和日志跟踪，使用了“固定满 8 条触发摘要压缩”或“5 轮对话后从 Redis 刷入持久库”。这种**固定条数/轮数切分属于教学简化（Educational Simplification）**。
- **生产实践的工业级触发机制：**
  在企业生产环境中，条数不等于 Token 开销（一段包含代码的提问可能高达 3000 Token，而闲聊一句仅 10 Token）。因此生产级系统通常采用：
  1. **Token 预算动态阈值触发：** 实时累加上下文中的 Token 数量，当达到设定阈值（如 Context Window 的 65%~75%）时，自动触发滑动窗口裁剪与记忆沉淀；
  2. **基于语义完整性的任务边界触发：** 利用小模型或分类规则检测用户话题切换点（如“订票任务已完成”、“好的明白了，下一个问题”），在语义自然闭合处进行记忆提取与入库；
  3. **周期性异步归档：** 结合前述的异步消息队列削峰，在空闲周期执行批量清洗。

## Key Emphasis
1. 必须讲清的边界：本课 Demo 落地 MySQL 结论层 + Redis 缓冲摘要；pgvector 过程层是下一课（第六课）演进目标。
2. 结论层 vs 过程层的区分标准：全量注入 vs 按需检索；合并修正 vs 只增不改。
3. 讲透教学简化与生产差异：固定轮数条数是教学脚手架，生产依托 Token 预算与任务语义边界。

## Optional Extension
**学员问：下节课引入 pgvector 后，为什么不把画像也存进 pgvector 一张表搞定？**
答：结论层要做"读旧画像 → LLM 合并 → 字段级更新（`updateById`）"，还要展示给用户看和修改；向量库擅长的是 append-only 文本的语义相似度检索，不适合做结构化字段的原地合并更新。

## Classroom Interaction
让学员现场判断三类数据分别归哪个层："用户的职业和当前预算结论"（结论层 MySQL `user_profile`）、"上个月聊过的三次比价细节记录"（过程层 pgvector `user_memory`，下节课落地）、"刚才前两句对话"（工作缓冲区 Redis `SessionMemory`）。

## Take Away
本课立住"MySQL 结论层 + Redis 工作缓冲"，并为下一课立下架构判断：**会被修正、全量注入的结论进关系库；只增不改、按需语义检索的过程进向量库**。教学演示固定轮数，生产系统紧盯 Token 预算与任务边界。

## Why This Slide Matters
提前在第五课讲清"结论层 vs 过程层"的演进蓝图与触发机制差异，学员既明白本课 Redis 累积摘要的适用边界，又能在第六课引入 pgvector 时无缝衔接，不会犯"有了向量库就把关系库废掉"的常见架构错误。
