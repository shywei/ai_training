## Slide Objective
明确 Demo 与企业生产环境之间的差距——学员需要知道"Demo 做到了什么、没做到什么、真正做项目时还要补什么"。

## Suggested Presentation
这一页很重要。Demo 是最基础的示例，不是可以直接用到生产环境的方案。学员需要清楚 Demo 和生产之间的差距。

**Session 并发问题**

Demo 里多个请求同时写同一个 Session 时，消息顺序可能乱。比如用户快速连发两条消息，两个请求同时 RPUSH，顺序不确定。Demo 没有处理这个问题。实际项目中需要 Session 锁——用 Redis 的 SETNX 实现分布式锁，同一时间只有一个请求能写入。或者用消息队列保证顺序。这个问题在用户量大的时候会频繁发生。

**PII 脱敏**

Demo 里用户说什么就存什么——"我叫张三，手机号 13800138000"，直接存入 MySQL。实际项目中必须脱敏。手机号只存前三位后四位，地址只存城市不存门牌号，身份证号和银行卡号绝对不能存。脱敏应该在"存入数据库之前"和"注入 LLM 之前"两个环节都做。

**画像准确性**

Demo 里 LLM 抽取的画像直接存入数据库，没有验证环节。但 LLM 可能会误解用户意图——用户说"我最近在看轻薄本"，LLM 可能抽取为"偏好：轻薄本"，但用户可能只是在帮朋友看。实际项目中需要：抽取后让用户确认（"我记录了你的偏好是轻薄本，对吗？"），或者设置置信度阈值，低置信度的画像标记为"待确认"。

**压缩质量监控**

Demo 里压缩后没有质量检查。但 LLM 压缩可能丢失关键信息——用户说过"不要黑色"，压缩后可能变成"偏好其他颜色"，丢失了"不要"这个约束。实际项目中需要：压缩后对比原始消息和摘要的关键信息覆盖率，或者定期让人工抽检压缩质量。

**Memory 成本监控**

Demo 里没有成本统计。但压缩和画像抽取都调用 LLM，有成本。实际项目中需要监控：每天触发了多少次压缩、每次消耗多少 token、画像抽取的成功率和失败率、总 token 消耗量。建议做成本看板，按用户维度统计。

**多租户隔离**

Demo 里用 userId 做隔离，但没有严格的权限检查。实际项目中需要：Redis Key 带租户前缀（tenant:{tenantId}:session:{sessionId}），MySQL 查询必须带 userId 条件，API 层做权限校验——A 用户不能查看 B 用户的画像。

**Session 生命周期管理**

Demo 里 Session 只有"创建"和"过期"两种状态。实际项目中需要更完整的生命周期：活跃（正在对话）→ 空闲（超过 N 分钟无操作）→ 归档（压缩后存入冷存储）→ 删除（超过保留期）。归档很重要——冷数据不占 Redis 内存，但需要时可以恢复。

**Memory 与其他组件的配合**

Demo 里 Memory 是独立的。实际项目中 Memory 需要和 RAG、Tool 配合。比如用户问"我上次看的那个笔记本还有货吗"——Memory 记住了"上次看了联想小新Pro"，RAG 去查库存文档，Tool 调用库存 API。三者配合才能回答。这就是为什么 context 要同时包含 Memory、Knowledge 和 Tool 结果。

这些差距不是"下一课的内容"，而是"你真正做项目时需要考虑的问题"。Demo 教你原理和基础架构，生产需要你在基础上补这些工程细节。

## Key Emphasis
这一页是整节课最有价值的页面之一。它告诉学员"Demo 是起点，不是终点"。学员需要带着这些差距去思考自己的项目。
