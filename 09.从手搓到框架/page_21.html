PART 3 · 防框架套牢架构（问题与概念：六边形 Ports & Adapters）

为什么不能把 @Tool 和 ChatClient 写进业务层？六边形防套牢架构

五步看透防套牢：问题：AI 框架迭代极快（Spring AI 1.0 ➔ 2.0 连 CallAroundAdvisor 与 AdvisedRequest 都改名重构）➔ 概念：六边形架构（Ports & Adapters）➔ 原理：依赖倒置，纯 POJO 领域核定义抽象端口，所有框架 SDK 关进外层 adapter/。
❌ 反模式：框架 API 直接入侵核心业务类 Vendor Lock-in
// 反模式：业务 Service 绑死特定 AI 框架的注解与消息类型 @Service public class OrderServiceImpl { @org.springframework.ai.tool.annotation.Tool public org.springframework.ai.chat.messages.Message createOrder( org.springframework.ai.chat.prompt.Prompt prompt) { // 业务风控逻辑与框架 Prompt/Message 强耦合 } }
真实代价：一旦升级大版本或切换 AgentScope，所有核心业务类与单元测试全部编译报错，必须推倒重测。
✅ 正解：Ports & Adapters 依赖倒置三层模型 零侵入切换
① 入站适配器 (Inbound Adapters) —— 唯一允许放 AI 框架
SpringAi2WorkflowAdapter / AgentScopeWorkflowAdapter、Controller
② 领域核心与端口 (Domain & Ports) —— 100% 纯 Java POJO
ShoppingDomainService、ToolOrderRequest、ShoppingAgentPort（零 AI 包导入）
③ 出站适配器 (Outbound Adapters) —— 对接数据库与 MCP
实现 CheckpointStorePort 与 EnterpriseToolPort
核心收益：业务核心与底层 AI 框架同时面向抽象 port/ 接口编程，外围可随时热替换。
