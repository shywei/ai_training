# 第 11 页：第一部分总结：V5 → V6 → V7 同构功能对照全景

## Slide Objective
以全景对照表汇总第一部分 `V5 → V6 → V7` 的同构代码演进，明确定性：**Agent 架构本质未变，收益在于框架吸收胶水带来的开发效率提升**；并顺畅切入第二部分（V5 极难手搓的企业级增量能力）。

## Suggested Presentation
各位同学，请看这一页全景表，我们给第一部分做一个干脆利落的收口。

这张表横向摆出了**同一套电商导购功能**在 V5（8080）、V6（8083）和 V7（8084）三套工程里的实现映射：
- 从 Prompt 组装、安全切面拦截、工具契约声明、单步工具解析、MCP 连接，到最后的 ReAct 主循环——
  - **V5 手搓**：1834 行，所有协议细节、正则匹配、循环推进全靠自己一行行敲；
  - **V6（Spring AI 2.0）**：降到约 950 行，通信协议、Prompt、单步工具与安全切面全部被框架吸收，**但多步循环依然得自己写 300 行**；
  - **V7（AgentScope 2.0）**：降到约 500 行，`ReActAgent` 接管了多轮主循环，开发者只需聚焦领域风控规则和业务扩展点。

在这里，我必须再次敲黑板强调第一部分的**核心定性**：
截至目前我们对比的这 6 块内容，**从 Agent 架构与设计的角度来看没有任何本质变化**！依然是 Prompt + Tool + MCP + ReAct 循环，变的只是“谁帮你写这些底层胶水”。所以从纯粹的**开发效率视角**看：
- 如果你的项目只是**单轮/少轮问答、标准 RAG、或者 1~2 步的只读工具查询**，引入 **V6（Spring AI 2.0）** 就已经足够轻便优雅，没必要杀鸡用牛刀。

**但是**，企业级真实生产项目往往还要面对 4 个让 V5 手搓架构直接崩溃的难题——那些就不再是“换个写法省几行代码”的问题了，而是 **V5 极难做好、必须依靠框架运行时机制补齐的企业级关键环节**！下面我们正式进入第二部分！

## Key Emphasis
1. **死死咬住 5.1 定位**：第一部分全是同构效率提升，架构本质没有变。
2. **代码行数准确对应真实工程**：V5 1834 行 vs V6 ~950 行 vs V7 ~500 行。
3. **自然过渡到 5.2**：用“写得短 ≠ 满足企业级生产要求”切入第二部分。

## Optional Extension
### Q1: 代码行数从 1834 行降到 500 行，是不是代表系统复杂度消失了？
**讲师解析**：复杂度从来不会消失，它只是从你的业务代码里转移到了框架内部（Complexity Conservation）。框架替你承担了协议编解码、状态循环和默认异常处理；但架构师依然必须理解这些底层原理，否则线上出 Bug 时连排查方向都找不到。这就是为什么课程要先学第 04~08 课手搓，再学第 09 课上框架。

## Classroom Interaction
“回顾表里这 6 个模块，哪一个模块的胶水消除让你觉得最解压？”（多数后端工程师会对‘正则提取归零’和‘651 行循环归零’最有感触）。

## Take Away
V5 ➔ V6 ➔ V7 在同构功能上只是框架替换与效率跃迁；简单场景止步 V6 即可，复杂生产场景则必须进入第二部分的增量能力。

## Why This Slide Matters
完成了对“同构提效”的完整定性与收口，让学员与后续“企业级增量能力”彻底区分开，不再混淆两类价值。
