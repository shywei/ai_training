# 第 03 页：破题：两条截然不同的演进主线与三套对照工程

## Slide Objective
帮助学员在概念上彻底切割两类问题（5.1 同构能力效率提升 vs 5.2 手搓极难做好的企业级增量能力），并明确 `V5`（8080）、`V6`（8083）、`V7`（8084）三套同业务标本工程的定位。

## Suggested Presentation
各位同学，请看这一页。在看具体代码之前，我们先把一个最容易混淆的问题掰扯清楚——**从手搓走向框架，到底改变了什么？**

请看屏幕左边的**主线一：同构能力替换（开发效率提升）**。
在第 04~08 课中，我们用 V5 手搓了 Prompt 拼接、安全过滤、工具调用、MCP 连接和 ReAct 状态机。如果我们把这些功能原封不动地搬到 Spring AI 2.0（V6）或 AgentScope 2.0（V7）上重写，**从 Agent 架构与设计的角度看，其实没有任何变化**——依然是构造 System+User 发给模型、依然是调 8081/8082 工具、依然是跑 ReAct 循环。变化的只是框架替换和 API 写法，它解决的是“写起来太繁琐、胶水代码太多、正则易写错”的**研发效率问题**。

再看屏幕右边的**主线二：企业级 Agent 应当有的增量环节**。
有 4 件事，在 V5 的单机内存架构和同步阻塞循环里**手搓极难做好**：
1. 服务一重启或跨天等待审批，内存状态全丢 ➔ 需要 **Checkpointer 断点复水与分支**；
2. 模型刚决定下单但还没扣款，必须当场拦住等待人类确认 ➔ 需要 **认知生命周期 Middleware**；
3. 同步跑完再拆字推送的伪流式体验极差 ➔ 需要 **多通道类型化事件流**；
4. 模型填错参数格式就崩溃降级 ➔ 需要 **Tool 强契约与自愈纠错循环**。
这 4 项才是真正补齐企业级生产能力的增量。

为了让大家能像做对比实验一样看清这两条线，我们准备了三套实现同一个电商导购业务的工程：
- **V5（8080）**：手搓基准；
- **V6（8083）**：Spring AI 2.0.2 GA（类比 **Servlet API**，管模型通信基础设施）；
- **V7（8084）**：AgentScope 2.0.0 GA（类比 **Spring MVC**，管多轮智能体运行时）。

## Key Emphasis
1. **必须划清的界线**：5.1（架构未变、写法变省事） vs 5.2（V5 极难手搓、框架提供的企业级能力）。
2. **核心类比**：Spring AI = 通信基础设施（Servlet API）；AgentScope = 智能体运行时应用框架（Spring MVC）。

## Optional Extension
### Q1: 既然 V7 更强大，为什么还要单独建一个 V6（Spring AI 2.0）工程来做对照？
**讲师解析**：很多 Java 团队认为“引入了 Spring AI 2.0 就万事大吉了”。通过单独跑一遍 V6，大家会亲眼看到：Spring AI 2.0 确实能把 Prompt、Tool 和单次安全切面省掉一半以上代码，但写到多步状态机和审批挂起时，依然要手写 300 行循环。这才能让你真正理解 V6 的边界和 V7 存在的意义。

## Classroom Interaction
提问：“在你们现在的项目里，遇到更多的是主线一的‘胶水代码太重’，还是主线二的‘状态丢失/无法中途拦截’？”

## Take Away
框架不是黑魔法：一部分帮我们少写胶水（同构提效），另一部分帮我们补齐手搓扛不住的生产级运行能力。
