CHAPTER 01 · 破题：为什么从手搓走向框架？

先分清两种完全不同的问题：开发效率提升 vs 企业级能力补齐

全课总纲：引入框架绝不能一锅炖！必须严格区分“同样功能换框架写更省事（架构没变）”与“手搓做不好、企业生产必须靠框架补齐的环节”。
主线一：同构能力替换（开发效率提升） 架构设计未变
第 04~08 课用 V5 手搓实现的导购功能，在框架下核心架构逻辑（Prompt+Tool+ReAct）没有任何变化，变的只是写法与胶水代码量：
1. Prompt 拼装 & 调用：PromptManager(65行) ➔ ChatClient.builder()
2. 工具声明 & MCP 接入：手写正则 + McpToolCallback ➔ @Tool + ToolCallingAdvisor
3. 横切安全 & ReAct 主循环：散落调用 + 651 行 while ➔ Advisor + ReActAgent
本质定性：消灭重复胶水代码（1834 行 ➔ ~500 行），解决“写得累、易写错”。
主线二：企业级 Agent 应当有的增量环节 V5 极难手搓实现
以下 4 个生产级能力在 V5 受限于内存态与同步循环极难做好，必须靠框架运行时机制提供支撑：
1. Checkpointer 断点复水与分支：K8s 重启或跨天审批后原位续跑、时光倒流分叉
2. 认知生命周期 Middleware：在工具真正执行前（onActing）无损挂起等待 HITL
3. 多通道类型化事件流 & 4. 契约自愈：告别伪流式、拦截参数幻觉自动修填
本质定性：补齐高可用、可挂起、真流式、强契约的企业级基础设施能力。
