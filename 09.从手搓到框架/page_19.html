PART 3 · 框架的边界（一）：自动 Schema 反射不是万能的 ✅ Demo 已覆盖（扁平化 ToolOrderRequest）

为什么不能把内部实体直接暴露给 @Tool？三大反射死穴与扁平 DTO

问题本质：@Tool 反射推导 Schema 遇到多态接口、泛型擦除、JPA 双向循环引用会直接失效或栈溢出崩溃；必须为大模型专门设计 1~2 层扁平化 Tool DTO。
死穴 1 · 多态接口与深层嵌套
入参含接口或抽象类时，反射拿不到具体子类属性，导出空对象 {}；嵌套超 4 层时模型漏填率飙升。
class OrderCmd { PaymentStrategy pay; // ❌ 丢失子类字段 List<Node> tree; // ❌ 深层嵌套易漏 }
死穴 2 · 泛型擦除与弱类型 Map
Java 运行时泛型擦除导致 Map<String, Object> 或通配符无法推导字段名，Schema 退化为无约束 object。
public String query( Map<String, Object> p, // ❌ 模型盲猜键名 PageQuery<?> page // ❌ 通配符丢失 )
死穴 3 · 双向关联栈溢出
直接暴露 JPA 实体（User 持有 Order，Order 又反向持有 User），启动期生成 Schema 直接 StackOverflowError！
class UserEntity { List<OrderEntity> orders; } class OrderEntity { UserEntity user; } // ❌ 启动期反射 Schema 递归死循环！
✅ 开发者必须落地的解法：面向大模型的扁平化 Tool DTO 准则 把复杂度留在 Java Adapter，把极简留给大模型
① 物理隔离数据库实体
严禁把 DB Entity 直接作 Tool 入参，独立定义无循环引用的 ToolOrderRequest。
② 结构拍平与枚举展开
嵌套压平至 1~2 层基本字段；多态策略改用显式枚举或字符串标识。
③ 适配层组装复杂领域对象
模型只填扁平字段，再由 Java Adapter 查询构造内部复杂领域实体。
