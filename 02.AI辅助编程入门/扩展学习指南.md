## 主题一：终端与代理式编程最佳实践（Claude Code 与 OpenCode）

### 1. 为什么值得深潜（Why - 生产触发场景）
很多开发者习惯在 IDE 右侧的 Chat 插件中向 AI 提问，然后人肉把代码拷贝到项目编辑器中，遇到报错再把报错信息拷贝回聊天框。这种“人肉消息总线”在处理跨 5 个以上文件的微服务重构、大型依赖升级（如 Spring Boot 2.x 升级至 3.x）或单测补全时，效率极其低下。  
掌握以 Anthropic Claude Code、OpenCode (`opencode-ai`) 和 Aider 为代表的**终端自主代理（Terminal Agentic Coding）**，让 Agent 直接运行在代码仓库本地，利用 Shell 命令自发编译、运行测试并查看 Git 差异，是实现 10 倍研发提效的质变分水岭。

### 2. 权威一手资料（Where - 核心信源与链接）
- **Anthropic 官方权威实践**：Anthropic, *"Claude Code: Best practices for agentic coding in the terminal"*  
  [Anthropic Documentation: Agentic Coding Best Practices](https://docs.anthropic.com/en/docs/agents-and-tools/agentic-coding)
- **开源终端 Coding Agent**：`opencode-ai` 官方架构规范与仓库  
  [https://github.com/opencode-ai](https://github.com/opencode-ai)
- **顶级开源基准评测**：Aider 架构与 LLM 编程能力榜单  
  [https://aider.chat/docs/](https://aider.chat/docs/) 与 [https://aider.chat/docs/leaderboards/](https://aider.chat/docs/leaderboards/)

### 3. 高效阅读指引（What - 核心看点与避坑）
- **核心必看点**：
  1. **Anthropic 紧凑反馈循环（Tight Feedback Loop）原则**：
     - 不要让 Agent 一口气生成数百行未经验证的代码；
     - 必须将“验证命令（Verification Command）”作为任务执行的标准环节（例如每次修改后强制自动触发 `mvn test-compile` 或运行指定单测）；
     - 赋予 Agent `git diff` 检查权限，让它像资深工程师一样审查自己的修改改动量。
  2. **Plan Mode 先行与原子化提交（Atomic Execution）**：
     - 在 OpenCode 或 Claude Code 中，复杂任务必须坚持“两阶段范式”：第一阶段进入 Plan 模式，仅生成只读的改造方案与影响面清单，等待人类 Review；第二阶段才允许进入 Act 模式，逐步落地代码。
  3. **Git 秒级回滚（Safety Net）**：
     - 每次执行 Agent 任务前，确保工作区处于 Clean 状态；
     - 熟练使用 `git stash` 或轻量分支隔离 Agent 实验性代码，一旦上下文退化，3 秒内通过 Git Reset 止损，严禁在污染的上下文上与模型反复扯皮。
- **工程师避坑**：
  - **避坑**：切忌给 Agent 授予无限制的全局 `rm -rf` 或危险写库权限，必须配置可控的工具黑白名单。
  - **重点吸收**：掌握“小步快跑、单测驱动、验证先行”的 Agent 协作心智。

## 主题二：跨工具工程规范标准：`AGENTS.md` 与分级 Rules 体系设计

### 1. 为什么值得深潜（Why - 生产触发场景）
在现代化研发团队中，团队成员可能使用不同的 AI 辅助工具（有的用 OpenCode，有的用 Cursor，有的用 Windsurf 或 Claude Code）。如果每个工具都要独立配置一份规则，必然导致规范碎片化与严重漂移。  
更严重的是，在大型 Spring Boot 多模块或单体巨石工程中，若将上万字的企业级编码规范、异常处理规范、数据库规范全部堆砌在项目根目录，会导致两个致命工程问题：**一是消耗海量 Token 导致前缀缓存被挤爆；二是模型在注意力稀释下频频忽视业务核心指令**。掌握跨工具标准与分级约束体系是架构师的必修课。

### 2. 权威一手资料（Where - 核心信源与链接）
- **跨平台 Agent 约束协议**：`AGENTS.md` 社区开放标准倡议  
  [https://agents.md/](https://agents.md/)
- **Cursor 官方规则规范与分层机制**：Cursor Documentation, *"Project-specific and directory-specific Rules (.cursor/rules)"*  
  [https://docs.cursor.com/context/rules-for-ai](https://docs.cursor.com/context/rules-for-ai)
- **企业级多模块标准模式**：Spring Boot 官方工程结构与规范实践指南

### 3. 高效阅读指引（What - 核心看点与避坑）
- **核心必看点**：
  1. **三层金字塔规则分级体系（Tiered Architecture）**：
     - **L1 根目录通用准则（Root `AGENTS.md`）**：定义跨工程硬性铁律（如：强制 Java 17、严禁吞噬受检异常、严禁在代码中硬编码任何 Secret、必须使用 Lombok `@Slf4j` 记录结构化日志）。篇幅严格控制在 300 词以内。
     - **L2 模块级局部准则（Submodule `module/AGENTS.md`）**：仅在进入特定子模块目录时生效。例如在 `order-domain/AGENTS.md` 中约束 DDD 充血模型与聚合根原则；在 `payment-gateway/AGENTS.md` 中约束外部 HTTP 调用的幂等重试与熔断降级。
     - **L3 任务级动态准则（Dynamic `.cursor/rules/*.mdc`）**：基于 Glob 通配符（如 `**/*Test.java`）触发专属于单元测试编写的 Mockito 与 AssertJ 规范。
  2. **契约编写的“反形容词法则”**：
     - **错误写法（无效模糊指令）**：“请编写健壮、可维护、性能优异的优雅代码”；
     - **正确写法（机器可验证确定性断言）**：“新写的方法圈复杂度（Cyclomatic Complexity）不得超过 10，每个公开 API 必须包含 `@Valid` 参数校验注解，且必须配备覆盖正向与异常路径的 JUnit 5 单元测试”。
- **工程师避坑**：
  - **避坑**：严禁把《阿里巴巴 Java 开发手册》全本 50 页直接复制进 `AGENTS.md`。
  - **原则**：只写模型默认行为容易偏离、且能够被编译器或静态分析工具（Sonar / Checkstyle）验证的元规则（Meta-Rules）。

## 主题三：Prompt Prefix Caching 计费与底层 KV Cache 复用机制

### 1. 为什么值得深潜（Why - 生产触发场景）
在使用商业化 LLM API（如 OpenAI GPT-4o、Anthropic Claude 3.5 Sonnet、DeepSeek-V3）进行多轮编程会话时，上下文往往累积了大量项目代码与规范文件。很多团队发现：**“为什么只跟 Agent 聊了 10 轮对话，API 账单就消耗了数十美元？为什么第 10 轮的等待响应时间从第 1 轮的 500ms 恶化到了 8 秒以上？”**  
其核心根源是破坏了底层服务商的 **Prompt Prefix Caching（前缀缓存）**！一旦掌握前缀缓存的判定机理并规范上下文排布顺序，多轮会话成本将直接下降 **75%~90%**，同时首字延迟（TTFT）降低一个数量级！

### 2. 权威一手资料（Where - 核心信源与链接）
- **Anthropic 官方前缀缓存架构**：Anthropic Docs, *"Prompt Caching (Beta) - How it works & Pricing"*  
  [https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)
- **OpenAI 官方自动提示词缓存机制**：OpenAI Platform Docs, *"Prompt Caching in the Chat Completions API"*  
  [https://platform.openai.com/docs/guides/prompt-caching](https://platform.openai.com/docs/guides/prompt-caching)
- **DeepSeek 上下文缓存计费与性能白皮书**：DeepSeek 开放平台技术文档  
  [https://api-docs.deepseek.com/guides/kv_cache](https://api-docs.deepseek.com/guides/kv_cache)

### 3. 高效阅读指引（What - 核心看点与避坑）
- **核心必看点**：
  1. **前缀缓存的底层物理机制（Radix Tree / Prefix Tree）**：
     - 服务端推理引擎（如 vLLM / SGLang）使用基数树缓存已计算好的 KV Cache。
     - **缓存命中铁律**：请求的 Prompt 必须从第 1 个 Token 开始，与历史缓存保持**完全逐字节（Byte-by-Byte）一致**！一旦中间某个字符（哪怕只是多了一个空格或时间戳变化），从该字符起之后的所有 Token 全部缓存击穿失效，必须重新全量执行昂贵的 Prefill 计算并全额收费！
  2. **上下文装配顺序的“静态在前、动态在后”黄金法则**：
     ```text
     ┌────────────────────────────────────────────────────────┐
     │ 1. System Prompt（系统预设角色与能力定义）              │ ◀── 100% 静态不变（永恒缓存命中）
     ├────────────────────────────────────────────────────────┤
     │ 2. Project AGENTS.md / Rules（项目全局工程规范）        │ ◀── 静态文件（长效缓存）
     ├────────────────────────────────────────────────────────┤
     │ 3. Core Domain Models / Schemas（核心实体契约代码）     │ ◀── 会话期静态（长效缓存）
     ├────────────────────────────────────────────────────────┤
     │ 4. Multi-turn Historical Dialogues（多轮历史对话消息）   │ ◀── 仅尾部追加（历史前缀复用命中）
     ├────────────────────────────────────────────────────────┤
     │ 5. Current User Input & Dynamic Timestamps（当前动态输入）│ ◀── 动态变化（仅计算增量 Token）
     └────────────────────────────────────────────────────────┘
     ```
- **工程师避坑**：
  - **致命反模式（Anti-Pattern）**：在 System Prompt 头部注入动态变量，例如：`You are a coding assistant. Current Time: 2026-11-11 15:30:25`。这样每次请求时间戳都不同，**前缀缓存 100% 击穿**，每次会话均被按最昂贵的完整输入费率计费！
  - **正确做法**：动态时间、当前打开的文件路径等动态上下文，必须严格放置在当前用户轮次的最后面。

## 主题四：Agent Skills 渐进式披露架构与编写指南

### 1. 为什么值得深潜（Why - 生产触发场景）
随着团队希望 Agent 承担更多复杂任务（例如自动查 MySQL 慢查询、执行 Redis 键分析、调用 Swagger 导出 API、执行 Kubernetes Pod 诊断），很多团队直觉地把所有这些能力的工具定义（Tool Schemas）和详细 SOP 教程全部一次性写进全局 System Prompt 中。  
这种做法会导致严重的工程副作用：**一是开局就白白浪费 20K+ 的上下文 Token；二是引入严重的“上下文污染（Context Pollution）”**，大模型在面对简单写代码需求时，往往误触发数据库查询或无关工具。**渐进式披露（Progressive Disclosure）**是构建工业级高可扩展 Agent 系统的必备设计模式。

### 2. 权威一手资料（Where - 核心信源与链接）
- **Anthropic 官方智能体架构设计**：Anthropic Research, *"Building Effective Agents - Augmented LLMs and Workflows"*  
  [https://www.anthropic.com/research/building-effective-agents](https://www.anthropic.com/research/building-effective-agents)
- **Agent Skills 协议与 OpenCode 实现规范**：`opencode-ai` 技能系统设计规范  
  [https://github.com/opencode-ai](https://github.com/opencode-ai)
- **Model Context Protocol (MCP) 核心规范**：Anthropic & 开源社区标准  
  [https://modelcontextprotocol.io/](https://modelcontextprotocol.io/)

### 3. 高效阅读指引（What - 核心看点与避坑）
- **核心必看点**：
  1. **渐进式披露的三层漏斗模型（Three-tier Funnel Architecture）**：
     - **第一层：元数据索引层（Index Tier - 极低开销）**  
       全局系统提示词中只保留每个 Skill 的一句话摘要与触发关键词（例如：`database-profiling: 用于查询慢 SQL 与执行 EXPLAIN 计划，当用户涉及数据库性能调优时调用`）。开销仅 30~50 Token/Skill。
     - **第二层：按需挂载层（On-demand Loading Tier - 动态读取）**  
       当 Agent 判断当前任务需要该能力时，自主调用内部工具（如 `read_file`）读取 `skills/database-profiling/SKILL.md`，此时才把该技能的详细约束、操作步骤和环境要求加载进上下文。
     - **第三层：执行与精简反馈层（Execution & Compact Feedback Tier）**  
       运行技能目录下的独立脚本（如 Python/Bash），只将处理完成的精炼结论返回给主会话，避免中间海量日志污染主窗口。
  2. **高规格 `SKILL.md` 的工业级结构标准**：
     - `YAML Frontmatter`：声明技能名称（name）、触发场景（description）；
     - `Preflight Checks`：前置依赖检查（如依赖的 CLI 工具、环境变量权限）；
     - `Step-by-Step SOP`：确定性执行步骤指南；
     - `Self-Correction`：常见异常与自愈补偿策略。
- **工程师避坑**：
  - **避坑**：不要把 Skill 写成一个庞大而死板的自动化脚本；Skill 的价值是向智能体传授“具有容错能力的思考逻辑与操作步骤规范”。

### 思考题 1：前缀缓存击穿的财务排查与优化
**问题**：某团队使用 Claude 3.5 Sonnet 开发了一款企业级智能编程助手。项目平均代码上下文为 40,000 Token。团队在测试中发现，每次连续对话 10 轮，账单消耗高达近 2 美元，响应延迟明显变慢。经排查，其客户端代码在构建每一轮请求时，采用了如下结构：
```json
{
  "system": "你是一个 Java 专家助手。当前时间：2026-11-11 16:05:12。\n项目全局规则：...\n40,000 Token 代码上下文",
  "messages": [
    {"role": "user", "content": "帮我看看这个类怎么写"},
    {"role": "assistant", "content": "..."}
  ]
}
```
请结合底层 Prefix Caching（KV Cache）的 Radix Tree 匹配机理，指出其致命设计缺陷，并给出降本 80% 以上的重构方案。

<details>
<summary>👉 查看架构参考思路</summary>

- **缺陷诊断**：
  - 该团队在 `system` 提示词的最前部插入了秒级动态时间戳：`当前时间：2026-11-11 16:05:12`。
  - 大模型服务商（Anthropic / OpenAI / DeepSeek）的前缀缓存判定是**从字符串第 1 个字符开始进行严格的前缀哈希匹配（Radix Tree 索引）**。
  - 由于时间戳每秒都在变动，导致每一轮新对话发起时，Prompt 在第 25 个字符处就发生了差异，后续高达 40,000 Token 的代码上下文和规则**永远无法命中前缀缓存**！每一轮对话都被迫支付全额的写入（Input Write）计算费率和漫长的 Prefill 排队时间。
- **重构优化方案（三部曲）**：
  1. **将静态内容绝对置顶**：将 `system` 改为纯静态内容（去除动态时间），包含不变的角色设定、项目全局规则及核心类定义。在 Anthropic API 中显式为系统静态内容打上 `cache_control: {"type": "ephemeral"}` 标记。
  2. **动态时间后置化**：如果确实需要让模型感知当前时间，将其作为当前最新一条 `user` 提问末尾的元数据注入（例如放在用户提问的附加信息中），确保其永远处于整个 Prompt 序列的最末端。
  3. **效果收益**：重构后，前 40,000 Token 的静态前缀在多轮会话中持续命中 Cache Read（计费仅为原输入单价的 10%~25%），每轮对话仅对最新产生的几十个 Token 进行全量计费，整体财务成本直降 80%~90%，首字延迟（TTFT）从数秒骤降至数百毫秒。
</details>

### 思考题 2：大型 Spring Boot 多模块工程的 `AGENTS.md` 分级设计
**问题**：你负责一个包含 4 个 Maven 子模块的企业核心中台工程：
- `mall-common`：基础公共包（工具类、通用枚举、统一 Result 封装）；
- `mall-order-service`：高并发订单微服务（Spring Boot, MyBatis-Plus, Redis 分布式锁, RocketMQ）；
- `mall-finance-service`：财务结算核心（严格事务、防重幂等、BigDecimal 精确计算）；
- `mall-admin-api`：后台管理端控制器。

请为该工程设计一套规范合理的 `AGENTS.md` 分层架构，说明根目录和各子模块应该分别承载什么规则，避免“规则冲突”与“注意力稀释”。

<details>
<summary>👉 查看架构参考思路</summary>

- **分层落地架构设计**：
  1. **根目录 `AGENTS.md`（项目级硬性红线 - 控制在 200 行内）**：
     - **环境基线**：强制 Java 17，Spring Boot 3.4.x，Maven 3.8+；
     - **跨模块硬性约束**：严禁在 Controller 之外使用 `null` 传递数据，统一使用 `Optional`；禁用 `System.out.println`，强制使用 `@Slf4j` 结构化日志；严禁在代码中硬编码任何 IP/密码/Token；
     - **工程规范**：所有公共返回值必须包装为 `Result<T>`；单测必须使用 JUnit 5 + Mockito，禁止启动全量 SpringBootTest 容器以加速执行。
  2. **`mall-order-service/AGENTS.md`（高并发与分布式专属规则）**：
     - **并发控制**：涉及库存扣减与订单状态流转，必须显式指明分布式锁方案（如 Redisson 租赁时间规范）；
     - **MQ 规则**：发送 RocketMQ 消息必须提供确定性事务监听器与幂等 Message Key，严禁无事务直接投递。
  3. **`mall-finance-service/AGENTS.md`（高安全资金计算规则）**：
     - **数值精度**：资金计算严禁使用 `float` / `double`，强制全部采用 `BigDecimal`，且必须使用 `String` 构造函数并显式指定舍入模式（如 `RoundingMode.HALF_UP`）；
     - **事务与审计**：涉及账户变动的 Service 方法必须标注 `@Transactional(rollbackFor = Exception.class)`，并强制要求记录前后状态的审计变更记录（Audit Log）。
  4. **设计收益**：
     - 当 Agent 在 `mall-finance-service` 下进行代码重构时，仅激活“根目录全局红线 + 财务专属规则”，避免了被分布式锁或后台 API 等无关规则干扰，上下文聚焦，命中率与合规率大幅提升。
</details>

### 思考题 3：渐进式披露（Progressive Disclosure）与全量注入的 Token 经济学对比
**问题**：一个研发平台计划为 Coding Agent 扩展 30 个特定业务技能（如：数据库 DDL 校验、K8s 容器排障、Swagger 生成、Sonar 漏洞修复等），每个技能的完整操作 SOP 和提示词约为 1,500 Token。  
如果采用“全量注入 System Prompt”与“采用 `SKILL.md` 渐进式披露”两种方案，在典型的 15 轮日常开发会话中（假设该会话实际只触发了其中 1 个 K8s 排障技能），请对比两者的 Token 消耗与模型推理质量。

<details>
<summary>👉 查看架构参考思路</summary>

- **定量与定性深度对比**：
  1. **方案 A：全量注入（Brute-force Injection）**：
     - 初始静态开销：$30 \times 1,500 = 45,000 \text{ Token}$！
     - 每一轮对话无论用户提问多么简单（哪怕只是“帮我写一个快速排序”），系统底座均背负着 45,000 Token 的沉重包袱。
     - 15 轮会话累积产生的输入 Token 将迅速超过数十万，极易触碰上下文窗口上限，导致早期历史被强行截断淘汰。
     - **注意力稀释（Context Pollution）**：模型在处理普通任务时，注意力被 29 个无关工具的规范所分散，极其容易出现逻辑幻觉或误调用工具。
  2. **方案 B：渐进式披露（Progressive Disclosure）**：
     - 初始静态开销：仅在 System Prompt 中放置 30 个技能的轻量索引目录（每个技能约 40 Token），总开销仅 $30 \times 40 = 1,200 \text{ Token}$，节约了 **97.3%** 的初始空间！
     - 动态按需加载：前 10 轮写代码过程中，完全不加载任何多余技能文档；直到第 11 轮用户明确提出“帮我查一下线上 Pod 为什么崩了”时，Agent 才通过内部工具读取 `k8s-diagnose/SKILL.md`（仅加载 1,500 Token），完成特定步骤并输出精炼结论。
     - **总结**：渐进式披露不仅在 Token 账单上降低了数倍成本，更在根本上保护了核心上下文的纯净度，是企业扩展大规模技能库的唯一可行路径。
</details>
