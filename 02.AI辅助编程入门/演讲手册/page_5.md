## Slide Objective
剖析 Token 经济学与 Prefix Caching（前缀缓存）对 Coding Agent 循环成本与延迟的决定性影响。深度纠偏“缓存命中率高就等于一切都好”的片面认知，严密辨析缓存命中率与上下文质量之间的辩证关系，阐明长上下文引发的注意力退化与错误污染，引导学员树立“主动上下文剪枝与压缩优于盲目贪图缓存”的高级工程心智。

## Suggested Presentation
我们来到第二章：Token、缓存与模型选型。请看第 5 页。
在这一页，我们要解决每一个带团队推行 AI 编程的 Leader 都会面临的灵魂拷问：
“Agent 改一个复杂需求，动辄在后台自动调用 20 轮工具（读文件、Grep、改代码、跑单测）。大模型 API 每次都是无状态的，每轮都要把前序几万字的历史重新灌一遍，这一个月下来 API 账单会不会把公司直接搞破产？”

答案是：绝对不会！因为拯救我们的是屏幕左边的**【Prefix Caching（前缀缓存机制）】**。
现代主流大模型 API（如 Claude、DeepSeek-V3/R1、OpenAI）在服务端均实现了 KV Cache 前缀缓存。
只要你的上下文是从左往右严格匹配的，那些保持不变的 System Prompt、`AGENTS.md` 规则和历史对话，模型服务商根本不需要重新算一遍 Prefill 矩阵，直接在显存里复用算好的 KV Cache！
**命中缓存后，输入 Token 的费用直接打 1 到 2 折（仅收 10%~25%），而且首字延迟 TTFT 暴跌 3 到 5 倍！** 这就是为什么 Agent 连续循环 20 轮，账单依然极其便宜的物理秘密。

**但是，请各位架构师务必高度警惕右半部分的重大认知陷阱：**
**“缓存命中率高，绝不等于你的上下文质量好！”**
很多工程师懂了前缀缓存之后，陷入了另一个极端：为了追求 90% 的缓存命中率，恨不得一次会话聊三天，把上下文一路膨胀到 100K 甚至 150K Token。他们以为“反正命中缓存了，只要一毛钱，多便宜啊”！
如果你这么干，代码质量马上就会遭遇**断崖式雪崩（Context Degradation）**：
1. **第一，大海捞针退化（Lost-in-the-Middle）**：
   学术界多次证实，当上下文超过 50K 之后，大模型的注意力呈现 U 型分布——它只能看清最开头和最末尾，中间几万字的内容注意力衰减高达 50% 以上！你写在 `AGENTS.md` 里的核心业务规则，在超长上下文中直接被模型“选择性失明”；
2. **第二，脏历史与错误假设严重污染**：
   Agent 在前 10 轮排查中，往往尝试了 3 种错误的假设，改废了两段代码，打印了长篇大论的报错堆栈。这些内容全部驻留在上下文里！大模型看到自己曾经写过的错误逻辑，会在错误的道路上越走越远，陷入死循环打补丁的“死亡螺旋”；
3. **第三，每一步自回归 Attention 的计算量依然在膨胀**。

所以，高级工程师的上下文治理军规是：
**不要为了贪图几分钱的缓存折扣，放任被污染的上下文拉垮代码准确率！**
当一个任务阶段性完成，或者排障陷入死胡同、上下文超过 40K 时，果断使用 `/compact` 命令提炼摘要，或者开启新会话重置干净窗口；同时，把翻阅海量文件的探索任务交给 **只读 Subagent（子智能体）** 独立运行，只将 200 字结论带回主会话，实现主上下文窗口的永久纯净！

## Key Q&A / Clarifications
**Q：在长任务中，什么时候应该果断执行 `/compact` 或清理上下文，哪怕这会暂时降低前缀缓存命中率？**
A：两大典型信号必须立刻清理：第一，**排障遇到死胡同、开始反复在同一处报错打补丁时**，此时历史上下文里充满了被证伪的错误假说和垃圾堆栈，必须 `/compact` 清空历史并重新总结事实；第二，**单次功能开发已通过验收，准备进入下一个无关功能模块时**，上一个功能的几万字实现细节对新功能毫无帮助，必须开启新会话或截断，避免注意力干扰。
