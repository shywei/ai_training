# Token机制与上下文窗口

## Slide Objective
让学员理解 Token 和上下文窗口的底层逻辑，以及计费模式，这是开发者使用 AI 时控制成本和把控任务大小的基础知识。

## Suggested Presentation
为什么我让 AI 读我整个项目，它却经常遗漏或者乱写？
答案在 Token 和上下文窗口里。大模型是不认识字的，它只认识 Token（词元）。
上下文窗口，就是大模型一次能处理的最大 Token 数量。这就好比模型的工作台，输入和输出的东西都必须放在这台子上。如果你的项目太大，超过了它的工作台，它就会把最前面的东西“挤掉”。
现在的主流模型虽然号称有 100万、200万的上下文，能塞进整个项目中，但大家一定要注意，不是塞得越多越好。
为什么？不仅是因为给的信息太多它会“看走眼”，更现实的原因是：钱。
Token 是要计费的。大家记住一个规律：AI 产出的代码（输出Token）通常比你给它看的代码（输入Token）贵 2 到 5 倍。不过好消息是，现在的 Agent 框架会自动把重复的上下文缓存起来，这能帮你省下一半的成本。
所以，理解 Token 机制，不仅是为了少踩坑，更是为了少花钱。

## Key Emphasis
强调上下文窗口的限制，以及“不是越大越好”的观点。
重点讲清楚输入、输出、缓存的三类计费差异，强调缓存对于 Agent 模式的重要性。不需深入 Tokenizer 的算法实现。

## Optional Extension
如果学员问中文 Token 为什么比英文费钱，可以简单解释：因为底层模型主要用英文训练，一个英文字母往往就是一个 token，而一个中文字符可能被拆成多个 token。

## Classroom Interaction
如果有谁最近 API 账单突然暴涨，可以举手示意一下。很可能就是你在不知不觉中，频繁地把整个项目文件塞给了模型，而且没有利用好缓存。

## Take Away
理解 Token 机制决定了你能给模型多少信息，以及你将为此付出多少成本。

## Why This Slide Matters
不理解 Token，开发者在使用 Agent 时就会无节制地投喂整个代码库，导致响应奇慢且成本高昂。这是实操前必须跨越的认知门槛。

## Transition
明白了 Token 这个“物理限制”后，我们怎么才能在有限的 Token 里，让 AI 懂我们的意思呢？这就是提示词工程要解决的问题。
