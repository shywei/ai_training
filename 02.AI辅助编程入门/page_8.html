CHAPTER 03 · 面向 CODING AGENT 的提示词工程

编程提示词实战正反面对比（Java / Spring Boot 真实场景）

反面教材：一句模糊指令引发的工程灾难 Vibe Coding 翻车现场
User > “给订单导出接口加个分页和 Redis 缓存，再优化一下查询性能。”
Agent 自由发挥导致的 5 大灾难后果：
1. 全库盲搜烧光 Token：没给 `@` 文件锚点，Agent 先调 8 次 Grep 翻遍 40 个类寻找“订单导出接口”，白白消耗 35K Tokens。
2. 破坏前端接口契约：擅自把原本返回 `List<OrderVO>` 的接口改成了 `PageResult<OrderDTO>`，导致线上前端页面直接白屏报错！
3. 重复造轮子与风格割裂：不知道项目已有 `RedisCacheHelper`，自己生造了一套 `StringRedisTemplate` 序列化代码，且未设置过期时间导致内存泄漏。
4. 顺手乱改无关代码：借着“优化性能”的名义，把隔壁核心下单方法的 SQL Join 给改坏了（典型改 A 坏 B）。
5. 未经验证直接交差：改完直接说“已完成优化”，实则连编译都没跑，Mapper XML 里少写了一个闭合标签。
正面标杆：四要素齐备的 Agent 工程指令 一次绿灯交付
[上下文锚点] 修改 @OrderReportServiceImpl.java 中的 `#queryExportOrders` 方法，缓存工具请复用 @RedisCacheHelper.java。
[I/O 契约]
1. 使用 MyBatis-Plus `Page<OrderPO>` 分页查询，单页上限 `pageSize <= 500`（超限抛 `IllegalArgumentException`）；
2. 以 `"order:export:" + tenantId + ":" + md5(queryParam)` 为 Key 写入缓存，TTL 设为 10 分钟。
[禁改边界] DO NOT 修改 `@OrderController.java` 对外暴露的 URL 与返回类型签名；DO NOT 修改其他方法。
[验证闭环] 在 @OrderReportServiceTest.java 新增缓存命中与分页超限单测，并执行 `mvn test -Dtest=OrderReportServiceTest` 直至通过。
为什么这段指令能实现 100% 确定性交付？
· 零盲搜直达病灶：直接锁定目标类与工具类，Agent 第一步直接 `Read` 两个文件，省时省钱且完全遵循项目既有规范。
· 契约量化无歧义：连 Key 命名规则、TTL 时长、分页阈值与异常类型都做了定量约束，杜绝 AI 拍脑袋瞎猜。
· 护栏 + 终端自愈：明确锁死 Controller 签名不准动，且强制要求跑过 `OrderReportServiceTest` 单测才算完工。
