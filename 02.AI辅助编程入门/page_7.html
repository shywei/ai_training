CHAPTER 03 · 面向 CODING AGENT 的提示词工程

告别 2023 对话套话：面向 Coding Agent 的结构化提示词四要素

彻底淘汰 2023 年玄学咒语： 在 2026 推理模型与 Coding Agent 面前，手写“你是一位 20 年经验的 Java 架构师，请深呼吸一步步思考，做对了给你 200 美元小费”毫无意义（模型原生自带 Thinking 思维链，且角色已由 `AGENTS.md` 固化）。
给情绪价值 ❌ ➔ 给工程契约 ✅
要素 ① 精准锚定上下文（`@File` / `@Symbol` / `@Git Diff`）
不要让 Agent 在十万行代码里大海捞针盲猜！直接用 `@` 喂给它参考样板文件（Golden Sample）与目标修改文件，信噪比提升 10 倍，且省去大量搜索 Token。
# 精准锚定示例
参考 @OrderController.java 的统一返回包装与异常处理风格，
在 @RefundServiceImpl.java 的 #applyRefund 方法中新增部分退款逻辑。
要素 ② 明确输入输出契约与异常边界（I/O Contract）
把自然语言变成消除歧义的工程契约：显式声明入参 DTO 校验规则、状态流转条件、并发幂等要求以及业务异常码。
# 契约定义示例
1. 入参 `RefundApplyReq` 需校验 `refundAmount <= paidAmount - refundedAmount`
2. 超额时抛出 `BizException(ErrorCode.REFUND_AMOUNT_EXCEEDED)`
3. 以 `orderNo + requestId` 加 Redis 分布式锁防重（TTL=5s）。
要素 ③ 划定禁改边界（Negative Constraints 负面约束）
Coding Agent 极度热衷“顺手重构”你没让它动的代码！必须明确告知禁止修改哪些公共类、禁止升级依赖、禁止破坏存量接口签名。
# 禁改红线示例
[DO NOT] 严禁修改 `OrderEntity` 表结构及已有 public 方法签名；
[DO NOT] 严禁改动 `pom.xml` 依赖版本或顺手格式化无关代码行。
要素 ④ 指定闭环验证命令（Verification Command）
这是区别于网页聊天的灵魂一击！在指令末尾指定定向单测或编译命令，赋予 Agent 明确的“完成定义（Definition of Done）”。
# 闭环验收命令示例
完成后请在 `@RefundServiceTest.java` 补充正常/超额/幂等 3 个单测用例，
并在终端运行 `mvn test -Dtest=RefundServiceTest` 直至全部绿灯通过。
2026 编程 Prompt 黄金公式： [@精准锚点 + 参考样板] + [I/O 业务契约] + [DO NOT 禁改红线] + [终端单测验收命令]
