CHAPTER 02 · TOKEN、缓存与编程模型选型

Token 经济学与 Prefix Caching：缓存命中率 vs 上下文质量辩证法

前缀缓存（Prefix Caching）拯救了多轮 Agent 的账单与延迟，但必须深度辨析：缓存命中率高，绝不等于上下文质量好！
1. Coding Agent 多轮循环为什么不破产？
Agent 完成一个需求通常需自动循环 15~25 轮（Grep→读文件→Edit→单测）。如果每轮都对前序 50K 上下文全额计费，20 轮将烧掉上百万 Token！
救星是 Prefix Caching（KV Cache 复用）：
常规输入 Input
100% 基准价
模型输出 Output
300%~500%
Cache Hit 命中
仅 10% ~ 25%!
2. 缓存友好的上下文内存布局（从静到动）
Prefix Cache 严格从左到右匹配。必须保持最稳定的静态规则在前，动态增量在后：
System Prompt
AGENTS.md
历史稳定上下文 (1..N-1)
最新增量
前 80% 连续命中缓存（单价打 1~2 折，首字 TTFT 暴降 3~5 倍）
⚠️ 缓存收益深度依赖厂商策略（Anthropic 显式缓存块、DeepSeek 自动前缀匹配、OpenAI 自动缓存）与严格严格的前缀字节对齐！
3. 核心纠偏：警惕“高缓存命中率”掩盖下的“上下文退化”
许多工程师误以为只要命中率 90%，上下文放任膨胀到 100K 也没关系。这是致命的认知误区！
• 大海捞针退化（Lost-in-the-Middle）：上下文超过 50K 后，注意力呈 U 型分布，中间核心业务规则遵循率从 95% 暴跌至 60% 以下！
• 错误假设与废弃代码污染：前序 10 轮试错产生的废弃代码段、无效报错堆栈成为“认知垃圾”，严重干扰模型当前决策。
• 推理算力与延迟累加：即便命中了缓存，自回归生成每吐一个字，注意力计算量依然与总上下文长度正相关。
4. 架构师上下文治理铁律：主动剪枝 > 盲目贪图缓存
• 周期性主动 Compaction：遇到大重构或排障死胡同，执行 /compact 提炼精华，重置干净窗口；
• Subagent 物理隔离：翻阅海量文件交给探索子智能体，只带回 200 字结论，杜绝主窗口污染！
架构师选型心智： Prefix Caching 优化的是运行成本与响应速度，而 Context Engineering 守护的是代码交付质量。绝不能为了省下几分钱缓存费用，放任污染的脏上下文拉垮模型的代码生成准确率！
