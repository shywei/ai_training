## Suggested Presentation
上一页我们讲了量化压缩能把模型体积砍掉 70%。
很多年轻工程师学会了公式，兴冲冲地跑去给领导写预算申请：“领导，7B 的 INT4 权重才 3.5GB，我们买张 8GB 的显卡就能跑了！”
结果显卡一买回来，服务刚拉起来就直接爆出 `CUDA out of memory` 崩溃！
为什么？因为**实验室的理论计算和企业真实的工程部署之间，隔着一条巨大的鸿沟！**

今天我们要把这套**“工业级显存速算工程模型”**彻底讲透！
真实线上环境的总显存需求，绝不能只算静态权重，它由五大物理分量加一个核心膨胀系数构成：
公式写在顶部：
$\text{VRAM}_{\text{total}} = (M_{\text{weights}} + M_{\text{kv}} + M_{\text{activations}} + M_{\text{cuda}} + M_{\text{comm}}) \times (1 + \text{Fragmentation})$

我们逐个拆解这五个分量和工程修正项：
1. **第一分量：静态模型权重（$M_{\text{weights}}$）**。
   BF16 下每 10 亿参数（1B）需要约 2GB 显存；而在 INT4 下，加上 Scale 缩放因子和量化元数据，每 1B 参数大约需要 0.55GB~0.6GB；
2. **第二分量：动态 KV Cache（$M_{\text{kv}}$）**。
   这是高并发长文本场景下的**“首要显存杀手”**！公式是：$2 \times 2 \times \text{层数} \times \text{KV头数} \times \text{头维度} \times \text{上下文Token总数} \times \text{并发数}$。一个 70B 模型如果并发 32 个请求、每个请求 16K 上下文，光是 KV Cache 就能吃掉上百 GB 显存！
3. **第三分量：前向计算激活值（$M_{\text{activations}}$）**。
   单步推理做矩阵乘法时的临时张量，通常需要常驻预留 0.5GB 到 1.5GB；
4. **第四分量（工程修正项 ①）：CUDA Runtime 与显卡上下文（$M_{\text{cuda}}$）**。
   显卡驱动加载、CUDA Context 初始化、CUBLAS 算子临时工作区（Scratchpad），**即使模型一行代码都不跑，直接吃掉 1.0GB 到 2.0GB 显存**！很多买 8GB 卡跑 7GB 模型的同学，就是被这一项直接送走的；
5. **第五分量（工程修正项 ②）：框架调度与多卡通信缓存（$M_{\text{comm}}$）**。
   如果你用 vLLM 或 SGLang，系统会为 PagedAttention 预先申请 Block Table 显存池；如果你上了多卡张量并行（Tensor Parallelism，TP），NCCL 跨卡通信需要开辟专属通信 Ring Buffer，这项通常占用 1GB 到 3GB；
6. **最致命的工程修正系数：显存分配器物理碎片（Fragmentation 15%~25%）**。
   PyTorch 和 CUDA 的显存管理机制是通过 Memory Pool 动态分配的。不同用户的请求长短不一（有的问一句话 50 字，有的发了一篇 8000 字代码），频繁的动态申请和释放必然造成严重的内部与外部内存碎片。**在实际生产容量规划中，必须预留 15% 到 25% 的安全缓冲（乘以 1.20 系数）**，否则只要线上遇到瞬时突发流量，立刻雪崩 OOM！

看清了这套工程修正模型，大家看底部的**硬件选型矩阵表**：
- **7B/8B 规模**：INT4 模式下单卡 RTX 4090（24GB）是性价比极高的单兵神器，轻松承载 32K 上下文；
- **14B 规模**：这是企业部门级业务的“甜点规模”，单卡 4090 或 A10/L40 完美承载；
- **32B 规模**：DeepSeek-R1 蒸馏版的 32B 在代码和数学上表现极其强悍，双卡 4090 或单卡 A800 是中流砥柱；
- **70B/72B 规模**：企业级全能中枢，双卡 A800/H800 或四卡 4090 构成主力生产阵列。

拿着这套严谨的工程测算表去和运维、财务沟通，你的方案不仅能 100% 跑通，而且经得起任何资深架构师的现场质询！

## Key Q&A / Clarifications
**Q：如果预算有限，显存刚刚好卡在临界点，有什么紧急工程配置防止线上 OOM？**
A：在 vLLM 或 SGLang 中有两大保底参数：第一，设置 `--gpu-memory-utilization 0.90`，给 CUDA Runtime 和临时激活留出 10% 的物理兜底空间；第二，开启 **Automatic Prefix Caching** 和 **Chunked Prefill**，平摊突发大请求的显存脉冲，并设置合理的 `--max-model-len` 限制极端长文本，同时开启请求队列调度（Queueing），宁可让后序请求排队等待几秒，也绝不超发显存导致进程崩溃。
