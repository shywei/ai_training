## Slide Objective
深入解析现代大模型推理调度系统的两大革命性突破：PagedAttention（显存虚拟分页管理）与 Continuous Batching（迭代级连续批处理调度机制）。建立并发数（Concurrency）、系统总吞吐量（Throughput）、首字延迟（TTFT）与字间延迟（TPOT）之间的四维工程权衡模型，帮助学员具备生产级模型服务调优与 SLA 保障能力。

## Suggested Presentation
上一页我们学会了怎么算显存。
显卡买回来了，驱动和模型也装好了。但在真实的私有化生产部署中，架构师马上会遇到两个极其头疼的“终极瓶颈”：
1. **为什么并发一上来，显存利用率看起来只有 30%，系统却开始频频报 OOM？**
2. **为什么显卡的 GPU Core 占用率常年在 20%~40% 晃荡，明明还有算力，服务吞吐量却卡死了？**

要解决这两个难题，我们必须掌握当今开源推理引擎（如 vLLM、SGLang、TensorRT-LLM）赖以成名的**两大调度革命与性能权衡矩阵**！

我们看左边的第一大革命：**PagedAttention（显存虚拟内存分页）**。
在传统的推理框架里，为了防止生成过程中显存爆掉，系统必须假设每个请求都会生成到最大长度（比如 8K），提前在显存里给它切出一大块连续的物理内存。
但大家知道，用户真实的回答往往只有两三百字。结果导致**系统 60% 到 80% 的昂贵显存变成了被占着茅坑不拉屎的“内部碎片”！**
vLLM 的天才之处在于：它向操作系统的虚拟内存管理偷师！它把 KV Cache 拆解成一个个固定大小的 Block 页（比如 16 个 Token 一页）。显存像拼积木一样按需动态申请，底层物理显存完全可以东一块西一块离散分布，通过类似 OS 页表的 **Block Table** 在逻辑上把它们映射成连续序列。
**这一招，直接把显存碎片浪费率从 80% 打到了 4% 以下！同样的硬件，可支撑的并发量瞬间翻了 2 到 4 倍！**

我们看右边的第二大革命：**Continuous Batching（迭代级连续批处理）**。
以前做深度学习推理，采用的是传统的“静态 Batching”：比如 4 个请求打包在一起，其中请求 A 只需要 10 个字，而请求 D 需要 1000 个字。系统必须傻等请求 D 全部吐完，这 4 个请求才能一起退出、放新请求进来！在漫长的等待中，GPU 的大量算力核心被迫闲置，这就是严重的“气泡（Bubbles）”！
Orca 论文提出的 Continuous Batching 彻底改变了游戏规则：**把调度粒度细化到每一次迭代吐字（Iteration-level）！**
每个 step 吐一个字。请求 A 在第 10 步生成完毕了？立刻让 A 带着结果离场，并在第 11 步毫秒级把队列里等待的请求 E 插进 A 空出来的槽位！GPU 核心永远在被高效喂饱，**系统总吞吐量直接再次暴增 3 到 5 倍！**

最后，请各位架构师死死盯住中间的**“四大性能指标权衡矩阵（Trade-off Matrix）”**：
当你做线上 SLA 承诺时，必须分清：
- **并发数（Concurrency）**：系统同时并行的请求量；
- **总吞吐量（Throughput，Tokens/s）**：系统每秒生产的总 Token 数。一般来说，Batch Size 越大，吞吐量越高，显卡综合 ROI 越高；
- **首字延迟（TTFT，Time to First Token）**：用户发完请求到看到屏幕跳出第一个字的等待耗时。这个阶段叫 **Prefill 阶段**，它是**算力密集型（Compute-Bound）**；
- **字间延迟（TPOT，Time per Output Token）**：流式打字机吐字的速度（比如每个字 30ms 还是 100ms）。这个阶段叫 **Decode 阶段**，它是**显存带宽密集型（Memory-Bound）**！

**架构师的权衡法则：**
如果你为了追求极致吞吐量，盲目把 Batch Size 开得特别大，那么每个 Decode 步长要搬运的 KV Cache 就会巨幅膨胀，导致单个用户的 **TPOT 变慢、打字变卡顿**；而且突发的长 Prompt 会让正在排队的请求 **TTFT 剧烈抖动**！
生产中我们怎么兼顾？
利用屏幕底部的 **Chunked Prefill** 将长请求切片，与连续批处理的 Decode 混合运算；再结合 **Automatic Prefix Caching（APC）** 让并发请求共享知识库物理页，最终实现高吞吐与丝滑低延迟的完美平衡！

## Key Q&A / Clarifications
**Q：在代码编写（Coding）场景中，TTFT 和 TPOT 哪一个更影响工程师的使用体验？**
A：首字延迟（TTFT）通常更为致命！工程师在 IDE 里按 Tab 补全或修改 Bug 时，如果等了 4~5 秒才出来第一个字，思维节奏就会被打断，心理体验极差；一旦首字在 500ms 内快速跳出，即使后面的 TPOT 稍微慢一点（类似打字机匀速输出），人类注意力也会被流式文本吸引，容忍度大大提升。因此在 Coding Agent 私有化部署中，必须开启 Chunked Prefill 和 Prefix Caching，将 TTFT 压到极致。
