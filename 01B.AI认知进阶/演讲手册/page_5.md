## Slide Objective
深入剖析 Tokenizer 的底层构建算法（BPE Byte Pair Encoding），厘清词表与 Merge Table 的生成原理；分析分词压缩比对工程成本的影响，并指出生产中最常见的 3 大分词深坑（多字节截断、数字未对齐与代码空格敏感性）。

## Suggested Presentation
很多初学者以为大模型“懂得汉字和英语单词”，其实大模型根本没有文字的概念，它看到的唯一实体就是分词器转化出的整数编号（Token IDs）。今天绝大多数主流大模型（GPT-4、LLaMA-3、Qwen、DeepSeek）使用的都是 BPE（字节对编码）或其变体。

大家看上方左侧卡片，BPE 是怎么构建出来的？
它极其优雅：首先以 256 个最原始的二进制字节（Bytes）为基础词表，这意味着只要是合法的 UTF-8 二进制流，BPE 永远不会抛出“未登录词（OOV）”异常；接着，在预训练阶段统计海量语料中哪两个相邻字节出现的频次最高，比如 `'t'` 和 `'h'` 频繁相邻，就把它们合并为一个新词 `'th'`，并把这条合并规则记录到 Merge Table；如此循环迭代数万次，直到词表达到设定的容量（例如从 32K 扩充到 150K）。

在上方右侧，我们给出了一个关键指标——压缩比（Compression Ratio）。早期很多欧美开源模型（如早期 LLaMA）词表主要针对英文设计，导致一个常见汉字会被生硬拆成 2 到 3 个 Token，不仅让中国企业调用 API 的费用高出两倍，还硬生生将上下文窗口挤压了三分之二。而今天优秀的开源模型（如 Qwen2.5、DeepSeek-V3）通过针对中英文进行联合词表构建，中文压缩比已经能够达到 1 个汉字仅消耗 0.6 到 0.8 个 Token，信息密度大幅提升。

最后，请大家务必警惕底部的 3 大生产工程陷阱：
第一，多字节拆分：UTF-8 汉字是 3 字节，如果你的系统在做 RAG 字符串硬截断（按字符数切片），很容易在分词边界处把一个 3 字节汉字切成两半，模型就会收到乱码字节；
第二，数字未对齐：旧版分词器对多位数字的分词极度混乱，导致模型在计算 `12345 + 6789` 时无法像人类一样按个位、十位逐位对齐，从而频繁出现算术计算错误；
第三，代码缩进敏感：在解析 Python 或 YAML 等对缩进敏感的语言时，连续空格是否被打包为独立 Token，直接影响模型的代码生成质量。

## Key Q&A / Clarifications
**Q：在做 RAG 文本切块（Chunking）时，应该按字符长度（Characters）切分还是按 Token 长度切分？**
A：必须使用与底层大模型完全一致的 Tokenizer 进行切分！如果按字符切分（比如每 500 字一截），既可能切碎 UTF-8 多字节字符，又无法精确控制注入 Prompt 时的实际 Token 消耗，极易引发上下文溢出错误。
