CHAPTER 02 · 模型推理核心机理

Tokenizer 深度剖析：BPE 字节对编码算法与分词陷阱

分词器（Tokenizer）是大模型看世界的唯一感官窗口，其编码规则直接决定了模型的压缩效率、算术稳定性与代码理解精度。
算法核心 Byte Pair Encoding
BPE 构建与 Merge Table 合并机理
1. 初始词表：以 256 个基础字节（Bytes）为起点，保证任意二进制数据永远不会 OOV（Out-Of-Vocabulary）。
2. 统计频次：在海量预训练语料中统计相邻 Byte 对的共现频次。
3. 迭代合并：将最高频的字节对合并为新 Token（如 'l' + 'o' ➔ 'lo'，'l' + 'o' + 'w' ➔ 'low'），记录进合并表（Merge Table），直到词表达到预设容量（如 128K 或 150K）。
Merge Rule: ('r', 'e') ➔ 're' | ('re', 'ad') ➔ 'read'
性能指标 Compression Ratio
分词压缩比演进与多语言成本
压缩比定义：$R = \text{Bytes} / \text{Tokens}$。压缩比越高，相同上下文窗口内能容纳的信息密度越大，推理成本越低。
早期英文优先分词器：
英文 1 word ≈ 1.3 tokens；
中文 1 个汉字常被拆成 2~3 个 tokens，导致中文模型昂贵且变慢。
现代 2025–2026 分词器：

实现 1 个汉字仅消耗 0.6~0.8 token，上下文有效容量翻倍！
架构师必须警惕的 3 大典型分词工程陷阱
1. 中文多字节截断与碎片化
UTF-8 汉字占 3 个字节。若分词器词表不包含该生僻字，会被生硬打碎为 3 个独立字节 Token。模型无法建立整词语义关联，导致 RAG 检索截断与乱码。
2. 数字未对齐导致算术失真
旧分词器常将 12345 随机切成 ['12', '345']，而 12346 切成 ['123', '46']。数位未对齐直接破坏了加减法进位规律，是模型算术差的隐形元凶。
3. 代码缩进与空格不连续
连续 4 空格、2 空格与 Tab 在不同分词器中可能有不同 Token 组合。分词器若缺少专门的前缀空格合并规则，会导致 Python 代码缩进错位与语法报错。
