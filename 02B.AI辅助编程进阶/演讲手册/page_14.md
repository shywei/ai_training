## Slide Objective
直击团队级引入 AI 编程第 2 个月普遍遭遇的“Context 治理灾难”，深入剖析 3000 行巨型大杂烩 `AGENTS.md` 引发注意力迷失、信号崩塌与规则冲突的底层机理。同时严肃纠偏团队工程中的环境隔离误区：明确指出 Git Worktree 只提供工作区与分支隔离，绝不等于独立的端口、数据库或容器运行环境，为后续分层上下文治理与多 Agent 环境隔离打牢基石。

## Suggested Presentation
我们进入第四章：团队级 Context 治理与工程免疫飞轮。请看第 14 页。
大家知道，很多团队推行 AI 编程，第 1 个月大家觉得太爽了，单兵效率翻倍。
但到了第 2 个月，架构师马上就会撞上一堵坚硬的南墙——**团队级上下文治理灾难（Context Collapse）**！

当时大家怎么想的？
“既然 Cursor、Claude Code 支持在根目录读 `AGENTS.md`，那我们把团队所有的规范全部写进去吧！”
于是，前端同学把 800 行 React Hooks 与 Tailwind 规范贴了进去；
后端同学把 1200 行 Spring Boot 分层架构、分库分表规则贴了进去；
DBA 把 600 行 MySQL 慢查询优化与索引命名军规贴了进去；
安全合规团队又贴了 400 行 PII 脱敏规范……
这个文件瞬间膨胀到了近 3000 行！
结果，所有工程师都发现了一个诡异的现象：**Agent 开始大面积失灵、答非所问、选择性失明，甚至连最顶层写的第一行编译命令都记不住了！**

为什么？请看屏幕中间的三大病根：
1. **病根 1：迷失在中间（Lost in Middle）**。
   大模型自注意力机制对超长上下文呈现显著的 U 型分布：它只对最开头和最末尾几十行保持敏锐，而第 500 到 2500 行的注意力权重衰减超过 50%！你写在中间的规则，模型实际执行时直接当成了空气；
2. **病根 2：噪音稀释核心信号（Signal Collapse）**。
   后端工程师明明只是想改一个订单 Service，结果每次会话头部白白被 800 行前端规范挤占。宝贵的上下文窗口被严重挤压，导致真正要读的领域模型代码反倒放不下了；
3. **病根 3：规则腐化与冲突（Rule Contradiction）**。
   大文档没人敢删，第 200 行写“用 StringRedisTemplate”，第 1800 行写“必须用 Redisson”。两条规则自相矛盾，AI 只能随机抛硬币碰运气！

**不仅如此，很多团队在做多 Agent 并发开发时，还陷入了另一个重大认知误区——对 Git Worktree 产生了不切实际的幻想！**
请大家看底部的【架构师警钟】：
很多团队以为“我们用 Git Worktree 给每个 Agent 开了一个独立目录，它们就完全物理隔离了”。
**大错特错！Worktree 只提供代码目录与 Git 分支隔离，绝不等于独立的运行环境！**
- 当你在 3 个 Worktree 里启动 3 个并发 Agent 跑单测时，它们跑在同一台物理宿主机上，如果单测启动本地 Spring Boot，**会立刻因争抢同一个本地端口（如 :8080）引发端口冲突**；
- 如果单测连接了本地共享的 MySQL 或 Redis 测试库，3 个 Agent 并发执行会导致**数据库脏数据交叉污染，引发诡异的偶发红灯！**
因此，真正的多 Agent 隔离，必须把 **Git Worktree 目录隔离** 与 **Docker / DevContainer 容器沙箱** 紧密结合，为每个任务分配隔离的独立端口与测试数据库实例！

## Key Q&A / Clarifications
**Q：在多 Agent 并行开发中，如何彻底避免多个 Worktree 之间的数据库冲突与端口踩踏？**
A：标准工程打法有两套：第一，**无状态轻量化优先**：单测必须解耦外部物理依赖，全面采用 H2 内存数据库 / Testcontainers 动态临时容器，每个测试用例分配随机动态端口（如 `local.server.port=0`），从根源杜绝端口与数据争抢；第二，若必须依赖外部组件，利用 Docker Compose 为每个 Worktree 分配独立的隔离环境变量前缀与独立容器网络栈。
