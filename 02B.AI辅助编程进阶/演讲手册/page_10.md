## Slide Objective
深入剖析复杂跨模块 Bug 根因分析（RCA）四步法，建立涵盖复现红灯单测、假设检验链、微创手术与回归网的科学排障流水线。同时向学员严正纠偏 Hook 的安全边界：明确澄清本地 Hook 可以被绕过或篡改，绝不能将其等同于最终防线，阐明企业级防作弊与代码防护必须依赖远程 CI、分支保护与同行 Code Review 的纵深防御体系。

## Suggested Presentation
各位工程师，在日常排查 Bug 时，屏幕上方的这个反模式可能很多人都干过：
终端里或者监控平台上蹦出一行 `NullPointerException`，你急急忙忙把它复制下来，直接扔进 AI 聊天框：“线上报空指针了，快帮我改一下！”
这就是软件工程中臭名昭著的 **Shotgun Debugging（散弹枪式乱改反模式）**。

大模型看到一句孤立的报错，它的条件反射是什么？它会直接在报错那一行上面给你加个 `if (x != null)` 或者 `return;`。
这种做法不仅没有解决根因，反而把真实的错误给“人为掩盖”了——原本应该拿到的业务数据变成了 null，数据不一致在下游链路中雪崩式降代，合流后在另一个模块爆出更诡异的 ClassCastException！
为了杜绝这种乱象，我们必须推行严格的**复杂 Bug 根因分析（RCA）四步法**：
- **STEP 1：先写最小复现失败单测（Red Test 验证）**。
  这是整个排障流程中最神圣的一条红线：**如果在本地没有写出一个能 100% 稳定复现该故障的红灯单测，绝对不允许修改一行生产代码！**
- **STEP 2：提出 Top-3 根因假设并科学排查**。
  强制要求 Agent 列出 3 个最可能的根因假设，按概率降序排列并给出代码行号证据，逐一排除伪因；
- **STEP 3：最小范围微创手术**。
  仅对确认的缺陷点做最小侵入微创修复（通常 $\le 10$ 行），严禁顺手做无关重构；
- **STEP 4：补齐防御性回归网（Green Test 闭环）**。
  第一步的红灯单测变绿，全套既有测试 100% 保持绿灯，Bug 测试用例永久合入回归测试资产库。

**但是，请各位架构师特别注意底部的【警钟】：纠偏 Hook 的防篡改安全边界！**
在很多团队里，大家配置了本地的 PreToolUse Hook，就误以为代码防线坚不可摧了。
**这是非常危险的技术天真！**
本地 Hook 运行在开发者的个人机器上，本地环境完全是可以被篡改或绕过的：
- 比如开发者或者某个拥有 Bash 执行权限的 Agent，完全可以执行 `git commit --no-verify` 直接跳过全部本地 Git Hook！
- Agent 甚至可能在排错过程中不小心把 `.claude/settings.json` 或本地的 `./scripts/guard.sh` 脚本改坏；
**所以，本地 Hook 只能作为第一道本地开发辅助防护，绝不能等同于企业的最终安全边界！**
企业真正的防篡改与代码保护，必须依赖**多重纵深防御**：
1. **远程不可控 CI 流水线**：代码推上去后，云端 GitHub Actions / GitLab CI 会在一个全新的独立容器里拉取主干最权威的单测基线强制执行。云端沙箱是本地 Agent 绝对触碰不到的物理隔离区；
2. **主干分支保护规则（Branch Protection）**：主干分支死锁，禁止任何人直接 push，必须通过 PR 流程且 CI 全绿才能合流；
3. **强制 Code Review（运动员与裁判员绝对分离）**：由人类资深工程师最后审查：核实单测的断言到底是不是真实的业务边界，有没有被悄悄改松或者加了 `@Disabled`。

记住：**用本地 Hook 防范无心之失，用远程 CI 与分支保护筑牢企业防作弊终极铁壁！**

## Key Q&A / Clarifications
**Q：既然本地 Hook 可以被 `--no-verify` 绕过，为什么我们还要花精力在本地配 Hook？**
A：这正如汽车上的“安全带”和“碰撞气囊”的区别。本地 Hook 是安全带，它提供的是秒级、实时的就地拦截与自动格式化反馈，能够帮工程师在本地编码过程中挡掉 90% 的低级错误、语法疏漏与不经意的危险命令，极大地降低调试成本；而远程 CI 和分支保护是碰撞气囊与防撞钢梁，它是无论本地怎么折腾都绝对无法逾越的底线安全保障。两者结合才是完整的防线。
