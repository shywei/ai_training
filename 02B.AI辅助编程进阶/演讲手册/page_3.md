## Slide Objective
深度剖析“Vibe Coding（凭感觉编程）”在多人协作、十万行存量工程中必然遭遇的四大工程灾难，通过系统维度的横向对比，确立“Spec-Driven Agentic Engineering（规格驱动工程）”作为企业级唯一可落地研发范式的正当性与必要性。

## Suggested Presentation
大家可能在社交媒体上经常刷到这样的词汇：“Vibe Coding”——指的是开发者躺在沙发上，喝着咖啡，仅凭一句口语化的模糊需求，跟 AI 聊着天就把一个网站或者小 App 给拼出来了。这在黑客松或者从零写个个人玩具项目的场景下确实很爽。

但是，如果我们把这种“边聊边改、不看代码只看能跑、全凭感觉”的模式直接套用在企业核心存量生产系统上，等待团队的必然是惨烈的系统性溃败。在企业实践中，我们总结出了 Vibe Coding 的**四大致命工程灾难**：

1. **架构腐化与重复造轮子**：Agent 没有全局架构感知，它不知道公司基础架构组早就封装了统一的分页插件、Redis 分布式锁、Token 鉴权和脱敏组件。只要你随口一提，它就会在当前目录自作主张新写一套工具类。三个月后，同一个仓库里能并存 5 套分页逻辑和 3 套不同的异常封装！
2. **隐式业务契约被静默破坏**：生产系统的老代码中充满了未写入文档的潜规则——比如某行看似多余的向下取整，实际是三年前对接某家特定银行通道的结算契约。Agent 凭感觉重构时，顺手将其“优化”掉，本地没有单测报警，上线后直接触发严重的资损对账故障。
3. **巨型 PR 无人敢审（审查瘫痪）**：几轮发散式聊天下来，Agent 往往在十几个文件中改动了 3000 多行代码，其中夹杂了海量无关的代码格式化、未使用的导入和幻觉逻辑。面对这种巨型 Diff，任何 Reviewer 都会陷入认知瘫痪，要么当橡皮图章闭眼 Merge，要么直接要求推倒重来。
4. **线上故障丧失排障心智**：在编码过程中当了“甩手掌柜”，一路狂按 Accept。一旦凌晨两点线上突发熔断雪崩，业务链路中断，负责值班的开发者连核心事务边界在哪、调用了哪个下游接口都不知道，彻底丧失兜底抢修能力。

请大家对比屏幕下方的范式对比表：
- **单一事实源（SSOT）**：Vibe Coding 依赖易逝的聊天会话，窗口一关灰飞烟灭；而 SDD 依靠版本控制的结构化规格工件——`requirements.md`、`design.md` 和 `tasks.md`。
- **精力分配**：Vibe Coding 是 10% 随口提需求，90% 替 AI 擦屁股调试肉眼排错；而 SDD 倡导 **60% 精力前置于架构评审**，10% 监督编码，30% 验收验证。
- **任务粒度**：告别一把梭，拆解为 5~15 分钟原子切片，单步测试闭环，随时可以 Git 秒级安全回滚。

大家一定要认清这个现实：在 AI 时代，写代码已经不值钱了，**最昂贵的是团队对系统的控制力**。把关前移到 Spec，**审查 200 行 Spec 的收益，远远大于去人肉审查 5000 行跑偏的代码！**

## Key Q&A / Clarifications
**Q：Vibe Coding 既然这么危险，那它在企业中就完全没有存在价值吗？**
A：不是完全没有价值，而是必须圈定严格的适用边界。Vibe Coding 适用于生命周期极短、随时可以全盘抛弃的场景，比如：黑客松验证、写一个临时解析脏数据的一次性单文件 Python 脚本、或者前端做纯 UI 布局走样验证（代码不超过 500 行）。一旦进入核心业务链路、多人维护的微服务或存量系统，必须无条件切换至 SDD 规格驱动模式。

**Q：为什么说大模型生成代码越多，审查成本反而指数级上升？**
A：因为人类阅读代码的认知负荷（Cognitive Load）随着 Diff 行数和上下文跨度呈非线性增长。当 Agent 凭感觉一次性修改 20 个文件时，人类需要在大脑中重建完整的依赖图谱和状态流转链条；而在 SDD 模式下，人类在编码前就通过 `design.md` 确定了改动边界，阅读单步切片 Diff 时只需验证代码是否如实兑现了既定契约，心智负担直接下降了 80% 以上。
