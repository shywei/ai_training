## Slide Objective
系统传授源自软件工程经典《修改代码的艺术》并结合 AI Agent 现代化演进的“祖传代码安全重构四步法”，掌握利用 Characterization Testing（特征描摹/黄金回归测试）锁定老代码现状快照、焊死测试护栏、小步重构并在零行为偏差下完成解耦的核心实操技术。

## Suggested Presentation
各位请看屏幕上的这套方法论。在软件重构领域，有一部封神之作——Michael Feathers 写的《修改代码的艺术》（Working Effectively with Legacy Code）。书中给“遗留代码（Legacy Code）”下了一个极其硬核的定义：**所谓遗留代码，就是没有测试保护的代码！**

面对一段长达几百行、没有文档、嵌套极其复杂的祖传老方法，很多工程师习惯去纠结：“这个边界条件的逻辑到底对不对啊？这个负数处理是不是当时写错了？”
注意，**千万不要陷入这个思维陷阱！**
因为很多时候，当年自作聪明的“错”，在经过 3 年的线上运行后，已经被上下游当成了必须兼容的“事实标准（De Facto Standard）”！

这就是为什么我们要引入 **Characterization Testing（黄金特征回归测试）**：
它的核心精髓是——**我们先不评判这段代码在道德上或逻辑上“对不对”，我们只用自动化单测，把这段老代码“当前在各种入参下的真实输出行为（哪怕包含怪癖和历史补丁）”，像高保真相机一样 100% 拍下快照，牢牢锁死！**

有了 AI Agent 之后，这套原本需要几天才能补全的测试，现在只需 2 分钟。具体落地分为**四步手术法**：

**第一步：锁死现状（生成黄金特征测试）**
严禁修改任何生产源码！直接向 Agent 下达指令：“扫描目标老方法的所有条件分支、边界情况和特殊字符输入，编写 15~30 个基于 JUnit 5 `@ParameterizedTest` 的参数化测试用例。并且**必须在未经任何修改的老代码上运行，确保 100% 绿灯通过！**”
大家看左下角代码示例：针对我们靶场中的 `LegacyParserCharacterizationTest`，测试用例不仅覆盖标准 Markdown 代码块，还专门锁定了“字符串值内含右花括号”、“思维链标签含伪括号”以及“无 JSON 时返回 null”等怪癖基线。

**第二步：焊死护栏（只读锁定测试文件）**
测试全绿之后，立即执行 `git commit` 保存快照。同时，利用我们在第 02 课中学过的 PreToolUse Hook，**将刚刚生成的测试文件设为绝对只读！** 这一步生死攸关，因为如果不锁死，大模型在后面重构代码写砸了的时候，会偷偷去把测试断言改掉蒙混过关（这正是下一章我们要严厉打击的 Reward Hacking 作弊）！

**第三步：小步手术（结构化解耦与管道化）**
在确保黄金测试被死死锁定的前提下，命令 Agent 对业务源码开展小步重构：“对外接口签名与返回值完全不变，内部将单方法的 6 层深层嵌套，重构为单一职责的三阶段管道（Stage 1: 剥离思维链与围栏 → Stage 2: 定位定界符 → Stage 3: 平衡状态机扫描）。”

**第四步：秒级回归（零行为偏差验证）**
每改完一个局部函数，立即在终端触发定向单测：
`mvn test -Dtest=LegacyParserCharacterizationTest`
大家看右下角的终端输出：24 个黄金用例，耗时 0.42 秒，0 失败，0 错误！
一旦有任何一个用例变红，说明 Agent 刚刚的手术不小心切到了某条历史怪癖分支，它能在 3 秒内对照 Diff 立即定位并自动修正。

**不锁死测试不重构！** 只要有了这套黄金回归防线，再可怕的祖传屎山，我们也能在 10 分钟内将其优雅地重构为高内聚、低耦合的现代架构，且 100% 杜绝线上回归事故！

## Key Q&A / Clarifications
**Q：如果老代码里确实有一个明显的 Bug，特征测试把它当成“期望行为”锁死了，重构完之后 Bug 岂不是依然存在？**
A：完全正确！这正是专业软件工程的要求——**“重构（Refactoring）”的严格定义就是“在不改变外部可观测行为的前提下改善内部结构”**。如果重构的同时顺带修 Bug，测试行为发生改变，一旦出现新问题你就无法区分是重构导致的破坏还是修 Bug 带来的副作用。正确的做法是：先通过重构把混乱的代码梳理成清晰的架构（此时 Bug 行为也被特征测试如实保护），然后再针对该 Bug 单独开辟一个分支，按照正常流程补失败单测、修复它、并将该测试更新为期望断言。

**Q：生成参数化特征测试时，怎么确保 Agent 覆盖到了所有隐藏分支？**
A：可以结合代码覆盖率工具（如 JaCoCo）。在 Step 1 生成完特征测试后，让 Agent 执行 `mvn clean test jacoco:report` 并检查覆盖率报告。要求目标老方法的**分支覆盖率（Branch Coverage）必须达到 90% 以上**。如果某些分支没覆盖到，命令 Agent 针对未覆盖行定向补充输入参数用例，直至关键执行路径全覆盖。
