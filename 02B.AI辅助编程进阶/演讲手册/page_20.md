## Suggested Presentation
各位请看大屏幕，现在我们将理论化为真刀真枪的代码实战。在靶场中，我们设计了两项极具代表性的高难度实操任务（对应《Demo演示步骤.md》中的“演示 2”与“演示 3”）：

**演练任务 A（新特性 SDD + Agentic TDD）：PII 敏感数据脱敏护栏**
用户在企业客服与工单处理系统中提交消息时，经常会在输入框里发送：“我的手机号是 13812345678，身份证 11010119900307123X，帮我查下订单。”如果直接把这段话发给外部大模型或写入审计日志，属于严重的个人隐私数据（PII）泄露违规！
我们统一在独立工具类 `PiiMaskUtils` 中开发 `mask(text)` 预编译脱敏能力。
请看实战推进流程：
1. **生成 `requirements.md`（严密 EARS 契约）**：
   - AC1 规定手机号脱敏为 `138****5678`；
   - AC2 规定 18 位身份证保留前 6 后 4，中间掩码为 8 个星号；
   - **最关键的 AC3（防误伤边界）**：如果用户输入的是 20 位的快递单号或者 `SKU1381234567899`，系统必须保持原样，**绝对不能盲目误脱敏！**
2. **Agentic TDD 红绿闭环**：
   Agent 首先根据 AC 编写包含 8 个用例的 `PiiMaskUtilsTest.java`，运行确认报错红灯；然后使用预编译正则 `(?<!\\d)...(?!\\d)` 实现前瞻后顾无边界误伤的脱敏逻辑；在终端运行：
   `mvn test -Dtest=PiiMaskUtilsTest`
   8 个用例在 0.3 秒内全部变绿，完美收官！

**演练任务 B（存量老代码重构）：复杂文本解析器安全解耦（LegacyParser）**
这是本节实操最精彩、最刺激的高潮部分！
请大家看 `LegacyParser.java` 中的 `extractJson` 方法。这段老代码负责从大模型的回复文本中把合法的 JSON 报文抠出来。它里面既有针对 `<think>` 思维链标签的粗暴正则，又有对 Markdown 代码块的剥离，还有两层混乱嵌套的 for 循环去数括号，圈复杂度高达 18，没有任何单测保护，谁动谁翻车！

现在我们按照四步法实施安全手术：
1. **第一步（生成黄金特征测试）**：命令 Agent 生成 `LegacyParserTest.java`，覆盖包含嵌套对象、字符串内含未配对花括号、转义引号、前后大段闲聊废话等 12 种刁钻的线上历史边界，在老代码上跑通确认 **12/12 绿灯**！
2. **第二步（激活防篡改物理护栏）**：在终端执行：
   `export LOCK_TESTS=1`
   此时，我们在上一页配置的 PreToolUse Hook 正式布防！
3. **第三步（现场触发防作弊拦截演示 🔥）**：
   我们命令 Agent 开始重构，将庞大的方法拆分为独立的状态机管道。重构中，Agent 难免会因为漏掉了字符串转义状态 `inEscape`，导致某个特征测试用例失败。
   **此时注意看终端的精彩瞬间：** Agent 发现测试挂了，下意识地想要调用编辑工具去修改测试用例以求蒙混过关——
   **终端瞬间弹出刺眼的红色 Hook 拦截报错：**
   `❌ [ANTI-CHEAT BLOCKED] 测试已锁定！严禁篡改测试断言 (Reward Hacking)！`
   Agent 的作弊企图被操作系统当场逮捕！Agent 被迫转换思路，老老实实回到业务实现中，修复状态机的转义判断逻辑；
4. **第四步（零回归全绿达成）**：
   重新运行测试（`mvn test -Dtest=LegacyParserTest`），终端打印出：
   `Tests run: 12, Failures: 0, Errors: 0 — Time elapsed: 0.32 s`！
   主方法从原先的 80 行乱麻缩减为清晰职责单一的状态机管道，**零回归事故达成！**

通过这两个靶场任务的洗礼，大家可以清晰看到：**在规范的 SDD 与硬核 Hook 的护航下，AI 编程不再是一场凭运气的盲盒赌博，而是一门精度堪比机械手表的现代精密工程！**

## Key Q&A / Clarifications
**Q：在任务 A 中，为什么必须强调正则表达式的前瞻后顾断言 `(?<!\d)` 和 `(?!\d)`？**
A：很多初学者让 AI 写手机号脱敏，AI 往往会写出简单的 `\d{11}`。如果文本里包含一个 13 位的订单号（如 `1381234567899`），简单的正则会把前 11 位误认为是手机号并替换成星号，破坏了订单号数据！在 EARS 契约中明确加入 AC3 防误伤条款，能直接逼迫 Agent 采用零宽断言（Negative Lookaround），确保匹配到的 11 位数字前后绝不存在其他连续数字，这正是“规格定义系统边界”的绝佳体现。

**Q：课堂演练中，如果学员机器上的 Agent 表现各异怎么办？**
A：不必慌张！因为我们有两套坚固的防线：第一是我们的 `AGENTS.md`，它锁定了 Maven 编译与单测命令；第二是我们的《Demo演示步骤.md》，其中为每个演示环节提供了现成可用的标准代码片段与预案。讲师在台上演示时，即使模型在某一步推理稍慢，也能通过预置的 Checkpoint 分支或预留代码无缝衔接。
