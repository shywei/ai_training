## Slide Objective
拆解企业级 SDD 从需求输入到最终交付的四步标准化 SOP 流程，重点揭示“Step 2 审 Spec”作为全生命周期中杠杆回报率最高的控制点，并传授如何结合工具的 Plan Mode 与 `/clear` 上下文重置技术实现无损长程交付。

## Suggested Presentation
大家请看大屏幕，这是我们在企业实践中经过上千个生产特性锤炼总结出来的 **SDD 四步标准化实操 SOP**：

**STEP 01 · 只读调研与起草（Plan Mode）**
首先切记：面对一个新特性需求，第一轮对话绝对不要开启 Write 模式让 AI 乱改代码！在 Claude Code 或 Cursor 中按下 `Shift+Tab` 切换为只读的 **Plan Mode**。向 Agent 下达只读指令：“请先扫描相关模块与公共依赖，针对该需求按 EARS 语法起草 `.specs/<feature>/requirements.md` 与 `design.md`，严禁修改任何业务源码。”这一阶段，Agent 扮演的是一位勤恳的“架构调研助理”。

**STEP 02 · 人类架构师把关（🔥 全流程最高杠杆点！）**
当 Agent 吐出设计初稿后，**绝对不要马上同意执行！** 这是人类工程师体现技术含金量与把关价值的黄金 5 分钟。请看屏幕下方的“缺陷放大定律”：
- 如果在 **Spec 阶段**发现 Agent 漏掉了公司统一的 Redisson 锁组件、或者异常码搞错了，你只需要改 3 行 Markdown，耗时 **30 秒**，此时代码库依然纤尘不染；
- 如果你放任它直接写代码，到了 **PR 阶段**才发现它自己写了个有并发穿透 Bug 的裸锁，你必须让它回滚 20 个文件、重写并补单测，至少浪费 **2 小时**；
- 万一这 20 个文件混杂着隐患溜过了评审，在 **线上生产环境** 触发高并发超卖故障，你面临的是紧急回滚、通宵修复脏数据、被全员复盘通报，损失高达 **数天甚至绩效清零**！
因此，在 Step 2，人类架构师必须亲自核查：是否漏用了既有资产？事务边界与加锁顺序是否安全？异常降级是否闭环？

**STEP 03 · 切片拆解与单步授权（Task Breakdown）**
设计方案经过人类修改并确认锁定后，命令 Agent 将其拆解为 `tasks.md`。这里必须执行严格的工程纪律：**严禁授权 Agent 一次性执行所有 Task！** 必须明确要求：“生成 tasks.md 后先停下，每次只执行 1 个 Task，每完成一个必须在终端运行绑定的定向单测，汇报成功后等待我的下一步指示。”

**STEP 04 · 闭环验证与上下文无损接力（Verify & /clear）**
Agent 完成一个切片，运行单测通过后，在 `tasks.md` 中将对应项勾选为 `[x]`。此时，我们传授大家一个极其关键的进阶秘籍：
**每推进 1~2 个原子切片，务必在终端执行 `/clear`（或重开新会话）！**
为什么？因为之前写代码、报语法错、调试单测积累的大量中间日志和 Diff，已经把当前会话的上下文窗口污染得千疮百孔，继续聊下去必然触发模型退化。由于我们所有的进度和契约都已经固化在磁盘上的 `.specs/` 目录中，新会话启动后只需一句指令：“请阅读 `.specs/` 下的文件，查看 `tasks.md` 当前进度，继续执行下一个未勾选的 Task 2 并跑通单测。”大模型就能带着 **100% 崭新、纯净的注意力**，无损接力下一程！

## Key Q&A / Clarifications
**Q：在 Step 2 审查 design.md 时，有哪些典型的“红线信号”一眼就能看出 Agent 在胡思乱想？**
A：总结有三个最显著的危险信号：
1. **重复造轮子**：出现类似 `MyRedisUtil`、`DateUtils2` 或自定义手写 HttpClient 调用的描述；
2. **锁与事务倒置**：在 `@Transactional` 注解修饰的方法内部去加锁和释放锁（锁在事务提交前就释放了，别的线程立刻能读到未提交数据）；
3. **模糊异常处理**：出现“发生异常时记录日志并返回 null”这类描述。一旦在 design.md 中看到这三类字眼，必须立即要求其纠正！

**Q：为什么任务一定要切片到 5~15 分钟这么碎？大模型一次性写完不是更快吗？**
A：大模型的推理准确率与单次生成的多文件跨度呈极陡峭的负相关。当要求它一次性生成 10 个文件时，它在第 7 个文件往往会遗忘前几个文件的变量命名和方法签名；而将任务约束在 5~15 分钟内（每次只改 1~3 个文件并立刻单测），不仅能将 Agent 的注意力集中在极小的局部问题上，而且即便写砸了，执行一次 `git checkout .` 就能毫秒级止损，彻底避免沉没成本。
