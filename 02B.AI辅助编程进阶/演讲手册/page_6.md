## Slide Objective
通过在 Spring Boot 电商交易系统中实现“订单提交幂等与库存预占”特性的真实代码级正反对比，让学员直观认清 Vibe Coding 盲写产生的并发竞态、超卖穿透和事务失效漏洞，深刻领会 SDD 驱动下复用存量基础设施、原子操作与严密异常补偿的工业级工程品质。

## Suggested Presentation
各位请仔细看大屏幕，这是一起非常经典的真实代码对比，左右两边都是大模型生成的 Java 代码，但质量却有着云泥之别：

**左边：一句话 Vibe Coding 盲写的反面教材**
如果你只给 Agent 输入一句模糊的话：“帮我给 OrderService 的 createOrder 方法加上防重幂等和扣库存逻辑，用 Redis 实现。”
大模型在没有 Spec 约束、没有存量代码深度感知的情况下，会非常自信地写出左边这段“看似能跑，上线即生产 P1 事故”的代码：
- **致命漏洞 1（并发竞态与 NPE）**：它自己用字符串拼接 Key，不仅没有租户隔离，还写成了 `if (redis.hasKey(key))` 然后再 `set`！在高并发场景下，两个线程同时判定为 false，防重锁形同虚设；更可怕的是检测到重复时它直接 `return null`，上游调用方直接抛出空指针异常；而且它竟然忘了给 Key 设 TTL 过期时间，随着时间推移 Redis 内存直接被打爆！
- **致命漏洞 2（非原子库存超卖）**：它用 `redis.get()` 查出库存，如果大于 0 再通过 `set(stock - 1)` 扣除。只要有瞬时秒杀流量涌入，多个线程拿到相同的 stock 值，必然发生毁灭性库存超卖！
- **致命漏洞 3（静默吞异常废掉 Spring 事务）**：最致命的是最下面的 `try-catch`！AI 把所有数据库和网络异常一把吞掉，仅仅打了一行日志，然后顺手 `return new OrderDTO()` 假成功！大家知道，Spring 的声明式事务 `@Transactional` 依赖异常未捕获并向上抛出才能触发 AOP 回滚。AI 把异常给吞了，Spring 以为执行成功并提交事务，生成了一堆半吊子脏数据！

**右边：Spec-Driven 规格驱动工程交付的高可靠实现**
现在看右边。当我们在编码前先建立了 `.specs/order-idem/`，并在 `design.md` 中强制约束：“必须复用系统既有的 Lua 原子库存预占脚本”且“锁必须置于独立事务外部”之后，Agent 交付的代码展现了资深高级架构师的素养：
1. **严格契约与租户隔离**：使用标准格式化包含租户与业务幂等 Key；
2. **原子 SET NX EX**：使用单条 Redis `setIfAbsent(key, "PROCESSING", 15m)` 原子指令，并发重放时精准抛出既定的业务异常码 `DUPLICATE_ORDER_SUBMIT`；
3. **复用底层 Lua 脚本防超卖**：直接调用公司基建 `stockLuaService.tryReserveStock()`，在 Redis 内部单线程原子扣减，从物理层杜绝并发超卖；
4. **明确事务边界与严密补偿**：将幂等锁置于外部，在内部通过独立事务 `orderTxService.createOrderInNewTx` 创建订单。一旦发生任何运行时异常，在 `catch` 块中立即释放预占库存、删除幂等占位 Key 允许用户稍后重试，并且**将原始异常原样上抛（throw ex）**，确保 Spring 事务精准回滚！

大家对比一下：左边的代码，你在本地随便点一下接口测试，可能看起来“一切正常”；但右边的代码，才能经受住 20 个线程并发压测与异常注入考验！**这就是凭感觉聊天与按规格施工的核心差异。**

## Key Q&A / Clarifications
**Q：右边代码中的 Lua 脚本和独立事务类，Agent 是怎么知道工程里有的？**
A：这正是 SDD 中 `design.md` 的威力！在 Step 1 只读调研阶段，Agent 在阅读工程时扫描到了 `StockLuaService` 和 `RedissonLockTemplate` 的存在，并将它们记录在了 `design.md` 的“存量资产复用清单”中。人类架构师在 Step 2 确认签字后，Agent 在 Task 编码阶段就会定向注入并调用这些类，而不是像左边那样随手裸写。

**Q：为什么左边的代码单元测试能过，右边也能过？**
A：如果你的单测只是用单线程、传一个合法入参断言返回不为 null，那么左边充满漏洞的代码也能 100% 变绿！这说明：**弱单测根本防不住劣质 AI 代码！** 在 SDD 中，我们在 `requirements.md` 的 EARS 条款（如 AC1、AC2）中明确限定了“相同 Key 连续重放”与“多线程并发抢占”，在 Task 阶段必须配套编写多线程 `CountDownLatch` 并发单测，左边那段代码在并发测试下第一秒就会被击碎。
