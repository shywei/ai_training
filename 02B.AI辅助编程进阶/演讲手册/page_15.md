## Suggested Presentation
上一页我们剖析了 3000 行巨型 `AGENTS.md` 的灾难。
那么，大厂团队到底是怎么治理海量研发规则的？
请看第 15 页：**分层级与按需触发的上下文架构（Hierarchical & Scoped Context）**。

我们把原先揉在一起的大杂烩文档，解耦成了清晰的三层金字塔：
- **第 1 层：根目录全局宪法（`/AGENTS.md`，建议 $\le 100$ 行）**。
  这里是全工程的绝对真理。只写三件事：第一，最核心的极速单测与打包命令；第二，全工程的模块拓扑与职责划分；第三，底线安全红线（严禁修改单测断言、Fail-Closed 错误处理原则）。绝不写任何局部模块的具体业务！
- **第 2 层：子模块目录规范（`core/AGENTS.md`、`web/AGENTS.md`）**。
  采用“就近挂载原则”：只有当 Agent 的工作区切入 `core/` 目录时，这套规则才会被继承。后端规则只讲 Redisson 分布式锁、事务模板与脱敏；前端规则只讲 React 状态库；互不干扰、永不串台！
- **第 3 层：按文件后缀/路径动态激活的 Glob 规则（Scoped Rules）**。
  比如配置 `globs: "src/main/resources/mapper/*.xml"`。平时它静静躺在磁盘上，消耗 0 个 Token；只有当 Agent 打开或修改 MyBatis XML 文件时，防慢查询的 SQL 军规才瞬间“动态注水”进入上下文。

这一套组合拳打下来，**无关规则噪音直接暴降 85%！** Agent 在任何一个具体任务中，上下文里的信噪比都处于极高状态。

**接着，请大家看下半部分的【架构师核心概念对齐】：**
我们在这一课（02B）和第 17 页讲到了“Multi-Agent 并行重构”，在后续的第 10 课《Multi-Agent 业务协作》中又会深入学习 Multi-Agent。
很多同学会问：“这两个 Multi-Agent 是一回事吗？”
**绝对不是一回事！两者的架构目标、运行环境和可靠性要求有着本质区别：**
1. **编码阶段 Multi-Agent（本课 02B · 研发态任务并行）**：
   - **面向的对象**：是本地的研发代码库；
   - **协作模式**：主控 Agent（Orchestrator）负责解析需求、拆解 SDD 任务列表，然后派出多个 Worker Agent 在各自独立的上下文与 Git Worktree 物理分支中并行写代码、跑单测；
   - **最终交付物**：是一个通过 CI 验证的代码分支、一组合格的单元测试与提给人类的 Pull Request。这是**研发效率杠杆**；
2. **运行时业务 Multi-Agent（第 10 课 · 生产系统业务协作）**：
   - **面向的对象**：是企业线上真实的生产业务环境；
   - **协作模式**：每一个 Agent 都是一个独立部署的微服务应用（比如智能导购 Agent、库存查询 Agent、风控审批 Agent、售后仲裁 Agent）。它们之间不能靠 Git 分支交互，而是通过 **A2A（Agent-to-Agent）标准协议**、分布式消息总线、Saga 分布式事务以及状态机一致性协议进行跨系统协同；
   - **最终交付物**：是企业真实的商业订单、资金划拨、库存预占以及向 C 端用户的最终履约结果！

把这两个维度的 Multi-Agent 概念彻底切分清楚，你才能在研发时用好并行编码提效，在架构设计时搭出高可用的分布式智能体业务系统！

## Key Q&A / Clarifications
**Q：在编码阶段让多个 Agent 并行开发时，主控 Agent 如何与 Worker Agent 传递任务？**
A：采用轻量级的 Markdown 契约或 JSON 任务单！主控 Agent 在规划阶段产出严格的 `tasks.md`，每个子任务明确写清：目标文件路径、前置依赖条件、输入参数与验收测试命令。Worker Agent 启动时只接收属于自己的那个子任务定义，完成后输出结构化变更摘要（Changed Files / Test Passed），主控 Agent 仅汇总摘要，严禁将 Worker 的全量排错日志重新塞回主上下文。
