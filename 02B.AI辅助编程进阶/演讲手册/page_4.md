## Slide Objective
详细拆解 2026 年业界前沿（如 AWS Kiro、GitHub Spec Kit、OpenSpec）推行的 SDD 三阶段核心规格工件（`requirements.md`、`design.md`、`tasks.md`），重点阐述 EARS 语法体系、技术架构四要素及原子任务切片规则，使学员掌握编写与审查高质量 Spec 的标准模式。

## Suggested Presentation
大家请看屏幕，这是目前全球顶尖工程团队（对标 AWS Kiro 架构工作流、GitHub 官方开源的 Spec Kit 以及 OpenSpec 开源生态）统一沉淀出的 **SDD 三阶段规格工件体系**。

在项目的特性分支下，我们约定统一建立 `.specs/<feature-name>/` 目录，由 AI 协助生成、人类架构师最终审批以下三个核心 Markdown 文档：

**第一工件：`requirements.md`（定义 WHAT & WHY——需求与验收标准）**
业务人员或产品经理给我们的自然语言描述通常是充满模糊性和歧义的。在这个工件中，我们强制 Agent 采用航空航天与高端工业界验证成熟的 **EARS 语法（Easy Approach to Requirements Syntax）**，将业务诉求转化为零歧义的确定性响应契约。
EARS 的通用公式是：
> **WHEN** [明确的前置条件/触发事件]，**THE SYSTEM SHALL** [可验证的确定性系统行为]。
例如我们在做订单防重与库存预占时：
- AC1 明确正常流：携带合法 `Idempotency-Key` 首次提交且库存充足，系统必须扣减 Redis 预占库存并返回 `ORDER_CREATED`；
- AC2 明确并发重放流：相同 Key 在 15 分钟内重放，系统必须拦截重复落库并直接返回首次订单快照；
- AC3 明确边界防御：缺失请求头时立即抛出确定性业务异常。
这样的每一条 AC，后续都能直接 1:1 映射为一个自动化单元测试断言，没有任何模棱两可的扯皮空间！

**第二工件：`design.md`（定义 HOW & BOUNDARY——技术架构设计）**
这是防范大模型“胡乱造轮子”的核心防火墙！在动笔写业务代码前，强制 Agent 必须先扫描工程现有代码库，明确回答架构师必审的四大要素：
1. **存量资产复用清单**：明确指出复用哪个既有的二方包或内部模板（如屏幕示例中复用 `common-redis` 模块的 `RedissonLockTemplate`，严禁自己裸写锁）；
2. **类职责与方法签名**：定义新增加的注解 `@Idempotent`、核心切面类及缓存 Key 命名规则（如 `ord:idem:{tenantId}:{idemKey}`）；
3. **数据一致性与事务边界**：明确锁粒度必须在 `@Transactional` 事务提交之后才能释放，避免高并发下的脏读穿透；
4. **下游降级与异常回滚策略**：库存扣减失败时如何精准清理缓存防重占位符。

**第三工件：`tasks.md`（定义 ATOMIC STEPS——原子任务拆解单）**
有了架构设计，能不能直接让 Agent “帮我全写出来”？绝对不行！我们必须将其拆解为由 Checkbox 构成的原子任务清单：
- 每个 Task 严格限制在 **5~15 分钟**的工作量，修改文件一般不超过 3 个；
- 每个 Task 必须清晰绑定**“修改文件范围 + 对应的 AC 编号 + 自动化编译或单测验证命令”**。
Agent 在后续实施中，必须逐项执行、单步验证、逐项打勾，未通过验证绝不允许向下冒进。

大家看底部的提示：**工件即资产！** 这三个 Markdown 文件不是一次性的草稿纸，它们会跟随最终的代码变更一起 `git commit` 提交入库。不仅在当前开发中让 AI 保持绝对清醒，更成为了未来任何新人和新会话永不过期的“活体架构设计资产”！

## Key Q&A / Clarifications
**Q：为什么一定要使用 EARS 语法，普通的 User Story（As a... I want to...）不够用吗？**
A：User Story 适用于早期产品与业务方沟通“用户动机与价值”，但对于代码生成智能体而言，其语言颗粒度太粗、缺乏严格的系统状态与边界限定。EARS 语法的强项在于它具有极高的“条件逻辑敏感度”（Precondition → Trigger → Expected System Action），模型可以直接根据 EARS 句式直接推导并编写 JUnit 5 `@Test` 中的 `given-when-then` 代码结构。

**Q：编写这三个工件会不会极大地增加开发者的工作负担？**
A：完全不会！因为这三个文档的初稿是由 Agent 在只读模式下根据自然语言需求和存量代码**在 30 秒内自动起草出来的**。人类工程师的角色不是从零码字，而是扮演“高级评审官”，花 3~5 分钟时间审阅、修改其中的设计硬伤。相比于后期在几千行烂代码中排查事务死锁，这几分钟的前期投入具备极高的杠杆回报率。
