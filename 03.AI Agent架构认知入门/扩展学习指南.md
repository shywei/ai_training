## 主题一：智能体奠基综述与工程设计范式（Workflow vs Autonomous Agent）

### 1. 为什么值得深潜（Why - 生产触发场景）
当前业界充斥着“万物皆可自主 Agent（Autonomous Agent）”的狂热，许多团队盲目照搬 AutoGPT 式的开放推演架构，导致上线后出现陷入死循环、Token 账单不可控、任务达成率不足 30% 等严重事故。
真正的企业级架构师必须清晰回答：**什么场景该用确定性的 Workflow（工作流编排），什么场景才真正需要自主 Agent？**
系统性研读业界奠基综述与顶级工业指南，能帮助工程师建立去伪存真的工程分水岭认知。

### 2. 权威一手资料（Where - 核心信源与链接）
- **学术奠基综述**：Lilian Weng (OpenAI 早期核心负责人). *“LLM Powered Autonomous Agents”* (2023).
  - 核心博文：[lilianweng.github.io/posts/2023-06-23-agent/](https://lilianweng.github.io/posts/2023-06-23-agent/)
  - 贡献：首次从系统工程角度确立了 `Agent = LLM (Brain) + Planning + Memory + Tool Use` 四象限体系。
- **工业界去泡沫宝典**：Anthropic. *“Building Effective Agents”* (2024).
  - 官方研究博客：[anthropic.com/research/building-effective-agents](https://www.anthropic.com/research/building-effective-agents)
  - 贡献：系统化梳理了最适合工业落地的高可靠性 5 种 Workflow 模式，告别盲目自主化。

### 3. 高效阅读指引（What - 核心看点与避坑）
- **重点研读 Anthropic 指南中的五大 Workflow 模式**：
  1. **Prompt Chaining（链式处理）**：前序输出作为后序输入，适用于强依赖顺序分解的任务。
  2. **Routing（分类路由）**：意图分流到专门优化的 Prompt 或小模型，降本提速。
  3. **Parallelization（并发处理）**：分片并发（Sectioning）与投票校验（Voting），提升吞吐。
  4. **Orchestrator-Workers（主编排-工作者）**：主模型动态分解并指派子任务，汇总后收敛结果。
  5. **Evaluator-Optimizer（双环评估优化）**：一个模型输出，另一个模型对照准则挑刺，多轮收敛。
- **核心辨析准则（何时用 Workflow，何时用 Agent）**：
  - **用 Workflow**：如果任务的执行路径大多已知、容错率极低（如金融转账、订单履约、法规审批），**必须优先使用确定性状态机与 Workflow 编排**。
  - **用 Agent**：只有当面对开放未知环境、调用步骤无法在编译期穷举、需要根据环境反馈动态推演下一动作时（如开放式代码 Bug 排查、竞品动态调研），才将控制权交由 Agent 驱动循环。
- **省时建议**：Lilian Weng 博客中关于 AutoGPT/BabyAGI 的早期演示可以略读，重点看其关于 Memory 分类与 Subgoal Decomposition 的抽象论述。

## 主题二：规划与推理范式演进深度对比（ReAct / Reflexion / Plan-and-Solve / GOAP）

### 1. 为什么值得深潜（Why - 生产触发场景）
大模型在没有良好规划框架时，容易出现“盲动”（未思考直接调错工具）或“妄想”（纯 Chain-of-Thought 推理陷入自我循环而与环境真实状态脱节）。
为了让智能体兼具逻辑推理与外部执行能力，学术界与工业界演进出一系列规划范式。理解每种范式的**延迟成本（Latency）、Token 消耗、抗幻觉能力与适用边界**，是架构选型的必修课。

### 2. 权威一手资料（Where - 核心信源与链接）
- **ReAct 奠基论文**：Shunyu Yao et al. *“ReAct: Synergizing Reasoning and Acting in Language Models”*, ICLR 2023.
  - 论文地址：[arXiv:2210.03629](https://arxiv.org/abs/2210.03629)
- **Reflexion 强化反思论文**：Noah Shinn et al. *“Reflexion: Language Agents with Verbal Reinforcement Learning”*, NeurIPS 2023.
  - 论文地址：[arXiv:2303.11366](https://arxiv.org/abs/2303.11366)
- **Plan-and-Solve 宏观规划论文**：Lei Wang et al. *“Plan-and-Solve Prompting: Improving Zero-Shot Chain-of-Thought Reasoning by Large Language Models”*, ACL 2023.
  - 论文地址：[arXiv:2305.04091](https://arxiv.org/abs/2305.04091)
- **GOAP 经典算法参考**：Jeff Orkin. *“Three States and a Plan: The AI of F.E.A.R.”*, GDC 2006.（工业界广泛引用的目标导向确定性规划）

### 3. 高效阅读指引（What - 核心看点与避坑）
- **核心范式横向对比与关键图表**：
  | 规划范式 | 核心思想 | 优势 | 痛点 / 生产代价 |
  | :--- | :--- | :--- | :--- |
  | **ReAct** | `Thought -> Action -> Observation` 闭环交替循环 | 紧贴环境反馈，实时调整下一步 | 步骤多时串行延迟极高，单步失败易盲目重复 |
  | **Reflexion** | 在执行失败后注入自然语言反思缓冲区（Episodic Memory） | 具备自我纠错与长时记忆避坑能力 | 需要昂贵的自我审视轮次，多次推理成本翻倍 |
  | **Plan-and-Solve** | 先自顶向下规划所有子步骤，再按部就班分步求解 | 减少长上下文下的目标漂移，便于子任务并行 | 缺乏弹性，当中间某步遇到不可抗力异常时整体失效 |
  | **GOAP (传统AI)** | 明确设定前置条件（Preconditions）与产出效果（Effects），A* 搜索最优图路径 | 绝对确定性，计算极快，零 Token 消耗 | 无法处理未定义的未知场景，规则维护成本高 |
- **Java 架构师看点**：
  - 读 ReAct 论文重点看 **Figure 1 的对比实验**（Act-only vs ReAct vs CoT-only），理解为什么单纯 CoT 缺少外部观测容易内耗，纯 Act 缺少 Thought 极易调错参数。
  - 在企业工程中，**最稳健的做法是“Plan-and-Solve（宏观编排） + ReAct（单节点微循环）”的嵌套架构**，杜绝无边界全局自由 ReAct。

## 主题三：2026 智能体三大正交协议标准（MCP / A2A / AG-UI）

### 1. 为什么值得深潜（Why - 生产触发场景）
智能体正在走出单机单模型时代。在异构企业 IT 架构中，系统必须面对三类连接：
1. **模型与外部工具/数据源的连接**；
2. **不同智能体之间的协作与会话流转**；
3. **智能体向用户终端界面呈现自适应流式状态的交互**。
如果每个团队自研一套私有协议，企业将重新陷入点对点网状集成的灾难。理解 2026 形成的**三大正交行业协议标准**，是构建可插拔、可演进 AI 中台的基石。

### 2. 权威一手资料（Where - 核心信源与链接）
- **MCP（Model Context Protocol）**：
  - 官方规范与文档：[modelcontextprotocol.io](https://modelcontextprotocol.io/)
  - GitHub 官方组织：[github.com/modelcontextprotocol](https://github.com/modelcontextprotocol)
  - 核心定义：统一规范 Client（宿主应用如 Claude Desktop / IDE）、Host（编排引擎）、Server（数据库、API、文件系统代理）之间关于 Resources、Prompts、Tools 的 JSON-RPC 2.0 传输标准。
- **Google A2A（Agent-to-Agent 协议）**：
  - 官方设计理念与协作白皮书：参考 Google Multi-Agent Collaboration Protocol 规范与开源实现。
  - 核心定义：智能体跨进程、跨组织通信标准，负责声明 Agent 的 Capability Card（能力名片）、会话协商（Negotiation）与授权委派（Delegation）。
- **AG-UI（Agent-to-UI / Generative UI 流式协议）**：
  - 规范参考：开源社区 Generative UI 标准规范（如 Vercel AI SDK RSC/UI Protocol 与跨端自适应组件推流规范）。
  - 核心定义：解耦 Agent 运行时与前端界面，通过 SSE 传输包含 Tool Call 进度条、审批确认卡片、动态图表的一等公民事件流。

### 3. 高效阅读指引（What - 核心看点与避坑）
- **三大协议的正交职责矩阵（架构师必须画得出的拓扑）**：
  ```
  +-------------------------------------------------------------+
  |              人类用户 (Human-in-the-Loop)                   |
  +-------------------------------------------------------------+
                                ▲
                                │ [AG-UI 协议: 流式卡片/审批/交互状态]
                                ▼
  +--------------------+   [A2A 协议]    +---------------------+
  |   Agent A (主导购)   |<------------->|  Agent B (物流对账)   |
  +--------------------+                 +---------------------+
            │                                       │
            │ [MCP 协议: Tools / Context]            │ [MCP 协议]
            ▼                                       ▼
  +--------------------+                 +---------------------+
  |  ERP / MySQL / RAG |                 | WMS 仓储系统 / 第三方 |
  +--------------------+                 +---------------------+
  ```
- **核心避坑点**：
  - 不要把 MCP 和 A2A 混为一谈：**MCP 是“主仆/客户端-服务端架构”**（模型调工具），**A2A 是“对等/联邦协作架构”**（智能体与智能体谈合作）。
  - 不要把 AG-UI 视作普通 Markdown 字符串流：AG-UI 要求前端按 JSON 事件解析并在特定时刻挂起等待人类点击确认按钮，驱动后端恢复执行。

## 主题四：企业级 Agent 评估体系（Trajectory Evals 与评估驱动开发）

### 1. 为什么值得深潜（Why - 生产触发场景）
很多团队在优化 Agent 效果时全凭体感：“我试了三个提问，感觉回答比昨天聪明了”。这种“抽卡凭感觉”的做法是企业软件工程的灾难。
Agent 具有多轮交互、非确定性推演和工具调用的特性。仅凭单轮输入输出的对比，根本无法发现“虽然最终答案对了，但中间调错了三次接口、白白消耗了 5000 个 Token”的劣质推演。
**缺乏系统化评测基线（Evals），Agent 的所有代码重构与 Prompt 调优都等于盲目负优化。**

### 2. 权威一手资料（Where - 核心信源与链接）
- **工业界评测权威指南**：Anthropic. *“Demystifying Evals for AI Agents”* (2024).
  - 官方指南地址：[anthropic.com/research/demystifying-evals-for-ai-agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- **企业实战参考**：OpenAI Evals 开源框架（[github.com/openai/evals](https://github.com/openai/evals)）与 LangSmith 轨迹评测文档。

### 3. 高效阅读指引（What - 核心看点与避坑）
- **重点看点**：
  1. **轨迹评估（Trajectory Evaluation）vs 结果评估（Outcome Evaluation）**：
     - *Outcome Eval*：只检查终态（比如数据库里订单生成了没有）。
     - *Trajectory Eval*：检查调用路径是否最短、是否有无效重试、是否存在敏感参数泄露风险。
  2. **三层评估漏斗（从确定性到模糊）**：
     - **第一层：代码级硬断言（Deterministic assertions）**：毫秒级完成，检查返回 JSON Schema 合规性、HTTP 状态码、工具调用的必填参数完整性（零成本高效率）。
     - **第二层：环境状态差分（State Diffs）**：沙箱数据库执行前后对比，验证业务副作用。
     - **第三层：LLM-as-a-Judge（模型裁判）**：使用能力更强、温度设为 0 的模型对多轮推演的“逻辑合理性与语气规范”打分（设定严格 Rubric 评分标准量表）。
- **避坑指引**：
  - 切忌一开始就搞几百条昂贵耗时的全局大模型评审。企业应优先打磨 50 条覆盖核心业务黄金用例（Golden Trajectories），将其集成至 Git CI 流水线，每次修改 Prompt 或模型路由时自动跑回归。

## 课后架构自测与思考题（Self-Check）

完成上述研读后，请尝试在架构层面回答以下三道进阶思考题：

### 思考题 1：工作流与智能体的边界抉择
> **问题**：某大型保险公司的核心理赔系统需要引入 AI：系统需接收用户上传的事故照片与医院发票、校验真实性、核对保单条款、计算赔付金额并执行银行转账。技术负责人提出：“应该做一个端到端的全自主 ReAct Agent，让大模型自由调用 OCR、保单库、反欺诈库和转账接口来处理理赔”。你作为外部架构顾问，请指出该方案的重大架构缺陷，并给出合理的架构重构建议。
> 
> **参考思路**：
> 1. **重大缺陷**：理赔涉及财务合规与资金安全，全自主 ReAct Agent 存在非确定性风险、容易受提示词注入攻击，且在面对恶意构造发票时可能错误触发转账操作，缺乏确定性的状态回滚机制与审计溯源。
> 2. **重构建议（Workflow + 局部 Agent）**：
>    - **外层采用确定性状态机（Workflow）**：严格划分【材料提取】$\to$【真伪核验】$\to$【条款匹配】$\to$【金额试算】$\to$【人工复核】$\to$【转账放款】六大串行阶段；
>    - **内层在特定阶段内嵌受控能力**：在【条款匹配】阶段使用 RAG + LLM 提供理赔依据解读建议；在最终【转账放款】前，必须通过 HITL（人在回路）由核赔专员确认，系统方可调用金融网关，杜绝模型直调高危交易接口。

### 思考题 2：推演死循环与步数熔断机制
> **问题**：在实践 ReAct 模式时，智能体可能陷入“调用工具失败 $\to$ 换个参数重试 $\to$ 再次失败 $\to$ 反复折腾”的自杀式死循环，不仅极大消耗 API Token，还会导致前端长久挂起超时。在生产级 Agent 运行时中，应该设计哪三级防护机制来优雅防御此问题？
> 
> **参考思路**：
> 1. **第一级：硬性步数与超时熔断器（Max Steps & Timeout Breaker）**：在 AgentRuntime 中强行设置 `max_iterations = 5` 与整体超时阈值（如 30 秒）。超过阈值立即触发降级，中断推演；
> 2. **第二级：同类工具重复调用检测（Idempotent Call Throttling）**：如果连续两次调用相同工具且输入参数语义相似度超过阈值，判定为推演停滞，强行向 Context 注入系统干预提示词：“系统检测到你反复调用该工具未获新进展，请直接基于已有 Observation 给出当前最佳回答或承认无法完成”；
> 3. **第三级：自我反思与熔断降级兜底**：若重试仍不通过，状态机优雅跳转至人工客服转接或兜底工单分派，向用户清晰解释已尝试的步骤与受阻原因。

### 思考题 3：多智能体协作下的协议隔离
> **问题**：在跨部门的多智能体协作（如“营销智能体”委派“风控智能体”审核活动预算）中，为什么不能直接让营销智能体通过私有微服务 REST 接口直接查询风控数据库，而必须通过 A2A 协议进行智能体间对话？
> 
> **参考思路**：
> 1. **业务意图封装与自主权（Autonomy）**：风控审核不单单是一个静态的只读查询，它包含动态的上下文合规判断、权限校验以及基于风控策略的意图协商；
> 2. **安全隔离与最小权限原则（Least Privilege）**：直接开放底层数据查询或直调微服务会造成紧密耦合与数据穿透越权；通过 A2A 协议，风控智能体作为本领域的守门人，有权根据上下文决定“披露多少信息”或“拒绝该审批请求”；
> 3. **审计追溯与非结构化解释**：A2A 交互保留了完整的任务委派契约与决策依据链条，便于事后责任界定与审计追溯。
