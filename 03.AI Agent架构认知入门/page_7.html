智能体系统的核心中枢：Context Engineering（上下文窗口动态组装全景图）

为什么 Memory、RAG、MCP、Workflow 能协同工作？因为所有组件最终都汇聚成发往 LLM 的那一个 `messages + tools` JSON 请求体！
1. 组件层：按需拉取/准备物料
PromptManager · 模板与规则
加载导购专家人设、安全红线、JSON 输出 Schema
Tool Registry · 工具与协议注册表
从标准化 MCP Server 拉取当前状态允许的 Tool Schema
MemoryManager · 三层记忆体系
• MySQL user_profile：尺码/预算/偏好标签
• pgvector user_memory：语义召回 Top-3 历史片段
• Redis session:msg：最近 N 轮对话 + 历史摘要
Knowledge Engine · 私域知识库检索
从 pgvector knowledge_vector 混合检索 + Rerank Top-K 商品手册/售后规则
Runtime Engine · 执行轨迹与状态
当前 FSM 状态、TaskPlan 进度、前序 Tool 执行结果
2. 组装层：单次 LLM 调用的 Context Window 内存布局 上静下动 · 命中 Prefix Cache
🔒 静态前缀区（Static Prefix — 跨轮次保持字节级一致，触发 KV Cache 省 50%~90% 成本）
[system] 核心角色定义 + 行为准则 + 安全护栏 + JSON 输出格式约束 ~800 Tokens
[tools] MCP 工具 JSON Schema 列表（search_products, create_order...） ~1,200 Tokens
⚡ 动态上下文区（Dynamic Context — 每轮由服务端按相关性与预算实时注入）
[system/context] 用户画像（MySQL）+ 召回长期记忆（pgvector）+ 早期对话摘要 ~600 Tokens
[system/rag] 检索到的私域知识块（pgvector Top-5 商品参数与退换货政策） ~1,500 Tokens
[user / assistant] Redis 近期滑动窗口对话历史（最近 6~10 轮原始消息） ~1,500 Tokens
[user + assistant(tool_calls) + tool(observation)] 当前问题 & 本轮已执行工具反馈 ~1,000 Tokens
Context Engineering 黄金法则：不是窗口越大越要塞满（塞满会导致 Lost-in-the-Middle 注意力稀释），而是精准塞入当前步最相关的高信噪比信息！
3. 预算与生命周期
① 前缀缓存纪律
严禁在第一条 System Prompt 顶部塞入每秒变化的 currentTime 或随机 UUID，否则整段 Prefix Cache 全部失效！
② Token 水位线裁剪
当历史对话超过阈值（如 4000 Tokens），自动触发异步摘要压缩，将旧对话折叠为 Summary。
③ 工具结果瘦身
MCP 工具严禁返回整张数据库表或万字 HTML，只返回模型决策必需的精简字段。
一句话记住：Prompt Engineering 写静态指令，Context Engineering 管动态全局。
