CHAPTER 03 · 认知层与执行层组件拆解 · 编排与工作流 (Workflow)

执行层组件 ② · Workflow 状态机运行时与 Multi-Agent 协作拓扑

① 单 Agent 内部控制：有限状态机（FSM / StateGraph） 受控状态引擎
为什么纯 `while(true)` 的 ReAct 循环在生产环境不可控？因为缺乏显式状态迁移、高危拦截与故障降级。工业级方案引入受控有限状态机：
AGENT RUNTIME FINITE STATE MACHINE (FSM) · 状态流转主干：
INIT
护栏/记忆
→
PLANNING
任务拆解
→
EXECUTING
受控循环(≤5步)
→
WAIT_CONFIRM
人工确认挂起
→
COMPLETED
写回/上报
Human-in-the-Loop（人在回路）
当模型意图调用 create_order 等高危写工具时，ConfirmationService 立即拦截并冻结现场快照存入 Redis，向前端推送确认卡片；用户点击“确认下单”后才恢复执行。
ErrorRecovery 三级容错体系
• L1 指数退避重试：网络抖动/429限流自动重试
• L2 模型/工具降级：主模型挂切备用模型；向量检索挂切关键词检索
• L3 友好兜底响应：返回安全话术并转人工客服
关键结论：Workflow 管的是“怎么做（控制流与可靠性）”，让单 Agent 达到生产级 SLA。
② Multi-Agent 多智能体协作 角色分工与协作
当一个 Agent 挂载超过 15~20 个工具、System Prompt 塞满多个领域的冲突规则时，选错工具率急剧上升。此时需按职责拆分为多智能体协作拓扑：
模式 A：Router / Triage（前台路由分诊）
入口轻量 Triage Agent 识别意图，一把将请求分发给导购专家 Agent、售后退换货 Agent 或物流查询 Agent（单跳高效）。
模式 B：Supervisor-Workers（主管-专家协同）
中央 Supervisor 拆解跨领域复杂任务（如“帮我配齐一套川西徒步装备并核算凑单满减”），先后调度穿搭知识 Agent 与价格库存 Agent，最终汇总回复。
模式 C：Handoff（状态接力移交）
导购 Agent 聊到用户抱怨旧订单质量问题时，携带浓缩会话摘要（Context Handoff）平滑移交给售后专员 Agent，无需用户重述。
架构原则：先用单 Agent + Workflow 跑通业务；只有当工具集膨胀或职责冲突时，才拆分为 Multi-Agent。
