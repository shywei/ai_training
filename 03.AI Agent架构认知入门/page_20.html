CHAPTER 06 · 架构误区辨析与演进总结

组件边界与存量系统融合辨析（五问五答）—— 厘清职责，平滑演进

❶ Memory（长期记忆）和 RAG（知识库）到底怎么划清边界？
虽然底层都用到了 pgvector 向量表，但职责完全正交：
• Memory 记的是“人（User-Scoped）”：与特定 user_id 强绑定（画像、偏好、历史对话），在对话过程中实时读写动态生长；
• RAG 记的是“事（Global Domain Knowledge）”：全员共享的商品手册与售后政策，由运营/ETL 管道离线批量构建、在线只读检索。
❷ 为什么商品实时价格和库存不能放进 RAG 向量库，必须走 MCP Tool？
因为数据突变频率与精确度要求不同！向量化（Embedding）有延迟且余弦相似度是模糊匹配。商品卖点评测、尺码指南半年不变，适合放 pgvector 走 RAG；而库存余量、秒杀价每秒在变且要求 100% 精确，必须通过 实时业务微服务 实时查 MySQL 主库。
❸ Tool、MCP、Workflow、Multi-Agent 四个概念是什么层级关系？
它们不是四选一的竞品，而是由小到大的四个工程层级：
• Tool = 单个原子函数（如 create_order）；
• MCP = 暴露和调用 Tool 的标准化通信协议；
• Workflow (FSM) = 单 Agent 内部编排多个 Tool 执行顺序与容错的骨架；
• Multi-Agent (A2A) = 多个拥有独立 Workflow 的专业 Agent 之间的分工协作。
❹ 引入 Agent 意味着要把公司现有的 ERP / CRM / 商城微服务重写一遍吗？
绝不需要重写！Agent 不是替代存量系统，而是存量系统之上的“智能交互与编排层”。现有商城订单库、CRM、协同过滤推荐算法全部保留，只需在外部包一层薄薄的 MCP Server 适配器（调用原有 Dubbo/Feign/REST 接口），就能让老系统秒变 Agent 的手脚。
❺ 传统搜推系统（搜索+协同过滤推荐）会被导购 Agent 取代吗？
两者是完美的上下游互补关系，而非替代关系：传统搜推引擎擅长在毫秒内从百万商品池中做批量粗排召回（千人千面首页瀑布流，高并发、极低成本）；而导购 Agent 擅长在用户拿不定主意时，通过多轮对话 clarifying 复杂场景需求（如“送长辈的护膝散步鞋”），并调用传统搜推接口拿候选集做深度对比导购。
