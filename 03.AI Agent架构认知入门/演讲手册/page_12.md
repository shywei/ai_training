## Slide Objective
精讲执行层核心组件：Tool Calling 第一性原理，以及 2026 智能体互操作三大协议（MCP、A2A、AG-UI）的垂直分层定位。深度纠偏将三大协议视为“同级替代竞争关系”的概念误区，明确 MCP（下行工具上下文）、A2A（横向分布式协同）、AG-UI（上行人机流式交互）的正交分工，并掌握企业级工具治理的生产防线。

## Suggested Presentation
请大家看第 12 页：执行层组件 ① · Tool Calling 原理与三大协议垂直分层定位。
如果说前面的 Prompt 和认知层是大模型的大脑和眼睛，那么执行层就是它操控外部世界的“手和脚”。

我们首先必须在技术底层确立一个极其关键的**第一性原理**：
很多人以为大模型具备 Tool Calling 能力，是大模型“自己跑去发了 HTTP 请求或连接了 MySQL”。
**大错特错！大模型本质上永远只是一个文本与概率流形处理器！**
大模型没有任何网卡驱动，也绝不会直接发起网络 I/O。所谓 Tool Calling，是大模型根据你提前注入的函数 Schema，在生成的 Token 里输出了一个结构化的 JSON 意图（比如 `{"name": "query_stock", "args": {"sku": 1001}}`）。
是包围在模型外围的 **Agent 运行时宿主（Runtime）**，拦截到了这个 JSON，由宿主代为发起真正的远程 RPC 调用，拿到返回结果后再伪装成一条 `role: "tool"` 的消息喂回给模型上下文。
**这就是著名的“意图与执行物理分离”原则！**

那么在 2026 年，整个智能体生态是如何解决各种系统、智能体以及用户界面的通信标准的？
很多同学容易把市场上的三大协议混在一起，甚至误以为这是三个互相竞争、只能三选一的协议。
**今天我们要彻底纠偏：MCP、A2A 与 AG-UI 属于三个完全正交的垂直架构分层！**
大家看中间的三大分层：
1. **下行分层：MCP 协议（Model Context Protocol · Agent ➔ Tools）**：
   - **它的定位是“向下看”**。由 Anthropic 主导，它是 AI 世界的统一 Type-C 接口；
   - 它专门解决：Agent 如何连接底层的外部工具、文件系统、数据库与知识资源。它包含三大原语：Tools、Resources 与 Prompts；
   - **比喻：它给 Agent 配备了标准化的“扳手、探针与改锥”**；
2. **横向分层：A2A 协议（Agent-to-Agent Protocol · Agent ➔ Agent）**：
   - **它的定位是“横向看”**。由 Linux 基金会托管；
   - 它专门解决：跨部门、跨服务器、由不同框架编写的**独立自主智能体之间，如何进行分布式业务协同**！
   - A2A 协议通过 `Agent Card` 暴露自身能力名片，通过 `Task` 管理长耗时任务的分布式状态机，通过 `Artifact` 交付工作成果；
   - **比喻：它连接的是具备独立思考能力的“职业队友”**，而不是听从命令的从属工具；
3. **上行分层：AG-UI 协议（Agent-User Interaction Protocol · Agent ➔ Frontend UI）**：
   - **它的定位是“向上看”**；
   - 它专门解决：后端的 Agent 运行时如何向前端浏览器（React/Vue）或者手机 App 双向推送结构化流式事件；
   - 它推送的不仅是纯文字，还包括 `<think>` 思考流折叠步骤、工具调用的进度卡片，以及至关重要的**人工审批确认卡片（HITL Action）**！
   - **比喻：它是智能体向人类管理者汇报工作与索取授权的“可视化大屏”**。

看清了这个垂直分层架构，你就会明白：一个现代企业级 Agent 系统，**上层用 AG-UI 连用户，横向用 A2A 连兄弟 Agent，下层用 MCP 接业务系统和工具库**！三者各司其职，浑然一体。

最后看底部的**企业级工具治理五道防线**：
企业工具绝对不能裸奔！写操作必须有读写分级鉴权；必须携带 `requestId` 幂等键防重试扣款；必须配置熔断降级防止下游微服务拖垮 Agent 线程池；入参必须做正则表达式与 Schema 严格校验！

## Key Q&A / Clarifications
**Q：如果一个功能既可以通过封装为 MCP 工具调用，也可以独立做成一个 Subagent 通过 A2A 协同，架构师该怎么选？**
A：选型法则在于“目标任务是否需要复杂的自主规划与不确定性推理”。如果该功能是确定性的输入输出、毫秒级返回的原子操作（如根据 ID 查库存、根据用户查询积分），坚决封装为 **MCP 工具**，执行成本低且确定性强；如果该功能本身是一个需要翻阅多处资料、多轮权衡、涉及长生命周期状态机流转的复杂独立业务（如售后纠纷仲裁、复杂跨系统数据核销），则应该拆分为独立的 **A2A 协作智能体**。
