## Suggested Presentation
请大家看第 5 页：核心定义与形态分水岭：通用 Harness vs 垂直应用 Agent。
在进入具体的代码和系统架构之前，我们必须在今天，当场修正一个在 AI 行业流传甚广、但在技术逻辑上自相矛盾的概念：
很多人喜欢说：“Agent 是大模型作为 CPU 的确定性软件系统。”
**请大家立刻抛弃这个说法！大模型本身绝不是一个确定性 CPU！**
我们在第 01 课已经论证过：大模型的物理本质是连续条件概率流形采样，即使你把温度设为 0，底层浮点误差、推理框架的并发调度也会导致输出具有一定随机性。大模型天生是不确定性的！
因此，一个“以不确定模型为核心的系统”，怎么可能自称是确定性 CPU 呢？

**请大家牢记我们今天确立的【P0 级行业标准定义】：**
> **Agent 是以大模型为认知与决策引擎，通过上下文、记忆、工具和运行时控制机制构成的智能应用系统。系统需要用确定性工程机制约束模型的不确定性！**

这句话讲透了大模型软件工程的第一性原理：
- 大模型负责**发散、语义理解、逻辑推理与工具选择意图**（发挥它的泛化智慧）；
- 而我们架构师亲手搭建的系统——上下文装配、三层记忆、工具权限白名单、状态机工作流与不可篡改的校验规则，负责**提供确定性的工程护栏，强行收敛模型的不确定性！**

确立了这个定义之后，我们再来看当前市场上的两大产品形态分水岭：
- **左边是【通用 Harness 宿主系统（General Agent Harness）】**：
  代表是 Claude Code、OpenClaw、Cursor。它们是面向软件工程师的通用研发提效利器。它们的工具非常通用（Bash、读写文件、Grep），面对的是开放未知的电脑环境；
- **右边是【垂直应用 Agent（Domain-specific Vertical Agent）】**：
  这是我们在公司业务系统里亲手要造的核心资产（如电商智能导购、金融理赔助手、供应链调度 Agent）。
  它深植于企业的特定业务域：**严禁给它开放任意的系统 Shell！** 它的工具集是企业内部的受控微服务 API，它的记忆是用户的历史画像事实，它的状态流转严格遵循业务风控审批。

看清了这两种形态，你就明白了：我们在日常工作中，拿通用 Harness 当工具；在核心业务交付中，用企业级技术栈（Spring Boot + Spring AI）打造高可靠的垂直应用 Agent！

## Key Q&A / Clarifications
**Q：为什么说“用确定性工程机制约束模型的不确定性”是架构师最重要的心智？**
A：因为很多初学者试图在“Prompt 内部”追求绝对确定性，比如写了 50 遍“你必须绝对保证输出合法 JSON，禁止有任何别的话”，结果线上依然偶发格式错误。资深架构师从不在黑盒内求确定性，而是在黑盒外用“确定性的 JSON Schema 校验器、有限状态机、参数拦截器与自动重试机制”来约束。无论模型怎么漂移，系统在工程上始终 100% 稳定可靠。
