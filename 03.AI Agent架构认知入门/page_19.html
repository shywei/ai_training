CHAPTER 06 · 架构误区辨析与演进总结

Agent 基础认知误区辨析（五问五答）—— 打破“智能体幻觉”

❶ 误区一：“Agent 不就是大模型 API + 几个工具函数吗？”
正解：不是。“LLM + Tool”只完成了最基础的单步动作调用。真正的企业级 Agent 是一个完整的软件系统工程——包含了 Context Engineering 动态上下文组装、三层 Memory 状态延续、RAG 私域知识接地、FSM 状态机编排、HITL 人工确认以及全链路 Trace 与降级护栏。
❷ 误区二：“Agent 和传统的 RPA / 规则自动化系统是一回事吗？”
正解：本质不同。传统自动化（RPA/审批流）是100% 确定性的固定轨道，输入稍微偏离预设格式就会报错卡死；而 Agent 的核心价值在于处理模糊意图与非结构化输入，能在受控状态机边界内根据环境反馈（Observation）动态规划与自愈调整。
❸ 误区三：“只要换个参数更大的新模型，就能解决 Agent 线上所有坏案例？”
正解：极具误导性。线上 80% 的 Bad Case 并非因为模型智商不够，而是喂给模型的 Context 质量差（比如 RAG 切块把表格切碎了、Tool 描述含糊不清、缺少用户尺码画像）。好架构 + 中等模型 >> 烂上下文 + 顶级模型。
❹ 误区四：“Prompt Engineering 和 Context Engineering 有什么本质区别？”
正解：局部与全局的区别。Prompt Engineering 关注的是“怎么措辞写好那段静态指令”；而 Context Engineering（上下文工程） 是系统级运行时调度——决定在调用 LLM 的那一刻，如何从 MySQL/Redis/pgvector/MCP 中精准筛选信息、排布前缀缓存并控制 Token 预算。
❺ 误区五：“Agent 是更先进的技术，所以所有业务功能都应该改造成 Autonomous Agent 吗？”
正解：绝对不是！自主 Agent 伴随着更高的延迟（多次 LLM 往返）、更高的 Token 成本以及概率性不确定风险。对于规则完全明确、输入输出高度结构化的场景（如月底财务结算、固定表单 CRUD），传统 Java 代码或确定性 Workflow 永远更快、更省、更准；Agent 只用在真正需要理解复杂自然语言意图与动态多源信息综合决策的刀刃上。
