CHAPTER 05 · 2026 技术生态与架构决策树

架构师能力裁剪决策树：拿到业务需求后按顺序问这“五问”

千万不要一上来就把所有组件全堆上去！从问题出发而非从技术出发——对照以下五步决策树，回答“是”才引入对应组件，回答“否”坚决裁剪：
起点基线 · 纯指令与推理：单次意图理解、文本生成或 JSON 提取？ ➔ 只需 PromptManager + LlmRouter + JSON Self-Correction（无需任何外部存储或工具） 复杂度：★☆☆☆☆
Q1
需要跨轮次连贯对话或记住用户偏好吗？
例：多轮追问导购、记住老客户尺码与禁忌
✅ 是 ➔ 引入 Memory 三层记忆体系
Redis 短期窗口 + MySQL user_profile + pgvector user_memory
❌ 否（如单次翻译、纯工单分类）➔ 保持无状态 Stateless，省掉 Redis/画像表
Q2
需要依据企业私域文档/商品知识回答吗？
例：内部万款商品参数、三包退换货细则
✅ 是 ➔ 引入 Knowledge 企业级 RAG 检索
ETL 切块 + Embedding + PostgreSQL pgvector 混合检索 + Rerank
❌ 否（通识问题或规则不足 2000 字）➔ 直接写进 System Prompt 命中缓存即可
Q3
需要查实时数据或修改外部业务系统吗？
例：查 MySQL 实时库存价格、算促销、建订单
✅ 是 ➔ 引入 Tool Calling + 标准 MCP 协议
工具 ≤3 个且单应用内嵌用 @Tool；多服务复用拆独立 MCP Server
❌ 否（纯知识问答）➔ 不开 Tool 权限，杜绝模型胡乱调接口风险
Q4
涉及多步复杂规划、容错或高危写操作吗？
例：先比价再凑单最后下单扣款（需人工确认）
✅ 是 ➔ 引入 Workflow 状态机与运行时治理
AgentRuntime FSM + TaskPlanner + ConfirmationService (HITL)
❌ 否（单步只读工具查询）➔ 用简单 2~3 步 ReAct 循环即可
Q5
工具数 > 15 个或存在跨领域专业冲突吗？
例：同时涵盖售前导购、售后退换、供应链采购
✅ 是 ➔ 拆分为 Multi-Agent 多智能体协同
Supervisor-Worker / Router 分工 + A2A 协议跨智能体协同
❌ 否（单一垂直领域）➔ 坚决保持单 Agent 架构，避免多跳通信延迟与丢上下文
