CHAPTER 03 · 认知层与执行层组件拆解 · 记忆系统 (Memory)

认知层组件 ② · Memory 三层记忆体系（Redis + MySQL + pgvector）

为什么不能把用户所有历史聊天记录一股脑塞给 LLM？因为 Token 成本爆炸 + 注意力稀释。企业级 Agent 必须像人类大脑一样实施三层分层存储与按需召回：
① 短期工作缓冲层 Redis (:6379)
Working Memory · 当前会话连贯性
• 存储内容：当前 sessionId 最近 N 轮（如 10 轮）原始对话消息 + 早期轮次滚动摘要（Summary）。
• 解决痛点：听懂指代词（如“那第二双有42码吗？”、“再便宜点的呢？”）。
• 生命周期：TTL 自动过期（如 30 分钟~24 小时），读写延迟 < 2ms。
写入时机：每一轮问答结束同步追加至 Redis List，超长触发异步摘要。
② 长期结构化结论层 MySQL (user_profile)
Semantic Profile · 确定性用户画像
• 存储内容：从对话中提炼出的高价值结构化事实字段（shoe_size=42, budget_level=中高端, prefer_brand=Nike, vip_tier=Gold）。
• 解决痛点：精准属性无需每次靠向量模糊检索，直接按 user_id 主键秒级读取注入上下文。
• 生命周期：持久化保存，支持冲突覆写（如用户体重/尺码更新）。
更新机制：对话后由后台轻量模型提取标签，Upsert 更新至 MySQL。
③ 长期非结构化过程层 pgvector (user_memory)
Episodic Memory · 历史情景按需召回
• 存储内容：无法塞进固定表字段的历史经历片段（如“用户3月提过脚背高穿硬壳鞋磨脚”、“下周去川西徒步需要防泼水”）。
• 解决痛点：跨月重逢时，根据当前话题通过 Embedding 余弦相似度 + user_id 过滤 召回最相关的 Top-3 往事。
• 生命周期：长期沉淀，结合时间衰减权重排序。
检索机制：WHERE user_id = ? ORDER BY embedding <=> query_vec LIMIT 3
MemoryManager 读写双通路： 【读通路·调LLM前】合并 MySQL 画像 + pgvector 语义相关记忆 + Redis 近期对话 → 注入 Context； 【写通路·调LLM后】同步写 Redis + 异步提炼写 MySQL & pgvector。
