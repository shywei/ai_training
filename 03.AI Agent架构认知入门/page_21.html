CHAPTER 06 · 架构误区辨析与演进总结

工程现实与落地边界：反过度设计（Anti-Overengineering）与 MVP 渐进演进

架构师最容易犯的错误是“拿着锤子找钉子”，在一个日活 50 人的内部小工具上堆砌全套分布式多智能体。请牢记以下四条克制原则与四阶 MVP 演进法：
❶ 什么时候根本不该上 Agent？
当业务流程 100% 确定、无需自然语言理解、无需动态推理时（如定时同步报表、固定公式计费），直接写 Java SQL/定时任务！强行上 Agent 只会带来 10 倍延迟与幻觉风险。
❷ 什么时候不必搭建向量数据库做 RAG？
如果业务规则文档总共不到 5,000 字且极少变动，直接放进 System Prompt 并开启 Prefix Caching（前缀缓存），效果比切块向量检索更好、更准，且省去整套 ETL 维护成本！
❸ 什么时候不必拆分独立 MCP Server 微服务？
如果只有 1~3 个专属工具，且只给当前这一个 Spring Boot 应用使用，直接用 Spring AI 本地 @Tool 注解即可；只有当工具需要跨团队、跨多 Agent 宿主共享复用或独立扩缩容时，才拆成独立 MCP Server。
❹ 什么时候绝对不要拆 Multi-Agent？
单 Agent 还没调优好、评测集还没建起来之前，严禁拆多智能体！每增加一次 Agent 间通信（Handoff/A2A），就会增加一次上下文损耗与延迟翻倍。单 Agent + FSM 状态机是 80% 项目的终点。
企业新项目落地标准路径：从最小可行闭环（MVP）按需演进
STAGE 1 · 最小闭环 (Day 1~3)
Prompt + LLM + 1~2 Local Tools
先把核心意图识别、结构化 JSON 输出和最关键的 1 个只读查询工具跑通，收集第一批 50 条真实业务测试集（Golden Cases）。
验证目标：核心业务价值是否成立
STAGE 2 · 补齐认知 (Week 1~2)
+ Memory 三层记忆 + pgvector RAG
发现单轮对话记不住上下文时加 Redis/MySQL 画像；发现模型对私域商品/规则产生幻觉时接入 pgvector 混合检索与 Rerank。
验证目标：回答准确率与个性化达标
STAGE 3 · 解耦与受控 (Week 3~4)
+ MCP Server 解耦 + FSM 状态机
将通用业务工具抽离为标准 MCP Server；引入 AgentRuntime 状态机、HITL 高危下单人工确认、三级容错与全链路 Trace。
验证目标：满足生产 SLA 与安全审计
STAGE 4 · 规模化协同 (Month 2+)
+ AgentScope 2.0 + Multi-Agent 中台
当扩展到全集团跨部门场景（导购+售后+供应链）时，升级工业级运行时框架并通过 A2A 协议组建多智能体网关中台。
验证目标：企业级多业务域复用
