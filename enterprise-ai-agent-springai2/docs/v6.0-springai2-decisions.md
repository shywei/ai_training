## 2. 为什么升级 Spring AI 2.0 必须整体升级 JDK 21 + Spring Boot 4.0？

在评估技术栈升级时，许多团队试图在 JDK 17 + Spring Boot 3.4 下强行引入 Spring AI 2.0，结果遭遇严重依赖冲突。根本原因在于 Spring 官方在 2.0.x 确立的三层基线联动：

1. **虚拟线程（Virtual Threads - JEP 444）深度绑定**：
   - AI Agent 的调用特征是**高并发、长等待 I/O**（LLM 生成耗时常在 2~10 秒）。JDK 21 虚拟线程让千级并发 Agent 可以在极低内存占用下阻塞等待，彻底淘汰复杂的反应式线程池调优。
2. **Java 21 模式匹配与解构增强**：
   - Spring AI 2.0 的 `@Tool` 参数解析、Record Pattern 匹配以及 Sealed Interface 契约，大量运用了 Java 21 的语法特性。
3. **Spring Boot 4.0.0 与 Spring Framework 7.0 现代化底座**：
   - Spring Framework 7.0 针对 AOT 编译、模块化装配与原生 OpenTelemetry 链路上下文做了重构，Spring AI 2.0.2 GA 的 Starter 正式依赖于该底层规范。
4. **教学结论**：
   - 这不是“为了升级而升级”，而是现代 AI 系统底座的必然演化。我们通过独立工程 `enterprise-ai-agent-springai2` 隔离演进，既保护了原手搓工程的稳定性，又让学员学到最新工业级基线。

## 3. 核心机制对比一：CallAdvisor / StreamAdvisor 替代硬编码切面

### 手搓原版痛点 (v5.0)
在第 08 课中，安全过滤、Token 统计和耗时打点分散在 `AgentRuntime.java` 的各个执行间隙：
```java
// 手搓原版：分散显式调用，极易遗漏或破坏主逻辑
if (guardrails.checkInjection(message)) { ... }
...
String toolCall = extractToolCall(thinking);
...
answer = guardrails.sanitize(answer);
traceService.completeTrace(traceId, ...);
```

### Spring AI 2.0.2 GA 架构红利
Spring AI 2.0 确立了统一的双向拦截责任链（`CallAdvisor` 与 `StreamAdvisor`）：
```
AdvisedRequest ────────────────────────────────────────────────────────┐
   │                                                                     │
   ▼                                                                     │
[GuardrailsCallAdvisor]   (前置: Prompt注入防御、PII手机号/身份证掩码脱敏)        │
   │                                                                     │
   ▼                                                                     │
[SchemaRepairCallAdvisor] (前置/后置: 捕获参数畸变，自愈重试 Repair Prompt)       │
   │                                                                     │
   ▼                                                                     │
[ChatModel + Tools]      (底层执行: 模型推理与工具调用)                          │
   │                                                                     │
   ▼                                                                     │
[GuardrailsCallAdvisor]   (后置: 输出敏感词过滤、密钥打码、Token 与耗时统计)       │
   │                                                                     │
AdvisedResponse ◀────────────────────────────────────────────────────────┘
```
- **规范演化注意**：早期预发布版的 `CallAroundAdvisor` / `StreamAroundAdvisor` 在 2.0.2 GA 正式废弃，统一定名 `CallAdvisor` 与 `StreamAdvisor`，API 语义更加直观精炼。

## 4. 核心机制对比二：@Tool + ToolCallingAdvisor 替代正则文本解析

### 手搓原版痛点 (v5.0)
在手搓原版中，LLM 工具调用的本质是靠 Prompt 约定输出格式：
`TOOL_CALL:queryProductInfo(productId=NB001)`
然后用正则表达式硬提取：
```java
// 手搓脆弱点：LLM 一旦多输出一个换行、中文标点或缺少括号，正则全部失效！
Matcher matcher = Pattern.compile("TOOL_CALL:(\\w+)\\((.*?)\\)").matcher(thinking);
```
此外，还需要手写 `McpToolCallback` 桥接类把 MCP 的 JSON Schema 转化为 Spring AI 回调，充斥着大量的 Object 与 Map 强转。

### Spring AI 2.0.2 GA 架构红利
1. **纯声明式注解**：
   ```java
   @Tool(name = "queryProductInfo", description = "查询商品的详细规格信息")
   public Map<String, Object> queryProductInfo(@ToolParam(description = "商品ID") String productId) { ... }
   ```
2. **底层原生 Function Calling 协议**：不再依赖文本字符串正则解析，模型直接输出标准的 JSON 工具调用字段。
3. **`ToolCallingAdvisor` 自动闭环**：LLM 给出调用意图后，Spring AI 自动根据方法签名反序列化入参、反射执行方法、将结果回填至模型上下文，完全消灭手写工具循环！

## 5. 核心机制对比三：Checkpointer 模式与状态解耦

第 09 课 P07~P10 是本阶段的**首个深度深水区**。

### 三级状态存储边界辨析
| 边界层级 | 存储概念 | 本工程技术载体 | 生命周期与职责 |
|:---|:---|:---|:---|
| **第一级** | **Chat History（对话历史）** | Redis List / 会话缓存 | 短期纯文本交互记录，用于拼装 LLM 上下文，不可用于恢复运行堆栈 |
| **第二级** | **Agent State Store（状态存储）** | MySQL 用户画像表 | 会话或用户级别的全局事实（如偏好、预算），低频更新 |
| **第三级** | **Execution Checkpointer（执行快照）** | Redis (热) + PostgreSQL JSONB (冷) | **高频任务执行栈快照**：包含 Call Stack、Scratchpad、游标、未完成审批，用于断点复水与时间旅行 |

### 生产级断点复水（Rehydration）与分支衍生（Forking）
- **断点复水**：当容器发生 Pod 漂移或发布重启时，通过 `loadCheckpoint(executionId, checkpointId)` 一键将执行游标、局部临时变量工作区与步骤状态完整复原，零损耗继续执行后续步骤！
- **时光倒流分支衍生**：通过 `forkFromCheckpoint()`，基于 `parentCheckpointId` 形成因果树分支，实现决策失误时的状态回滚试探。

## 6. 终极架构反思：Spring AI 2.0 解决了什么？没解决什么？为什么需要 AgentScope？

这是第 09 课最重要的架构认知升维点：**“省的不是行数，是胶水；守住领域边界，防框架套牢。”**

### Spring AI 2.0 解决了什么？
- ✅ 统一了不同云厂商、大模型与本地模型的 API 协议接入；
- ✅ 消灭了手写 Prompt 模板拼接、MCP 桥接与正则提取工具参数的“初级胶水”；
- ✅ 提供了优雅的 `ChatClient` Fluent 链式语法和 `CallAdvisor` 拦截器切面。

### Spring AI 2.0 没解决什么？
在仔细审阅 `SpringAi2WorkflowAdapter.java` 后，我们会发现一个不可回避的现实：
1. **多步状态机依然要手写**：7 状态的跃迁逻辑、重试判断依然需要开发者在 Adapter 中写 `while` 循环和条件分支；
2. **人在回路依然要手动挂起与恢复**：Spring AI 没有原生的 `SuspendedExecution` 概念，开发者依然要自己捕获高风险动作、写入 Checkpoint、等待外部调用 `/confirm` 后手动拉起循环；
3. **缺少类型化的多通道事件流**：流式输出依然需要开发者手动创建 Reactor Sinks、手动拼装 DTO；
4. **无法原生支持多智能体（Multi-Agent）协同拓扑**：没有 Subagent 委派、没有黑板模式上下文隔离、没有 Agent 间标准通信协议（A2A）。

### 经典架构隐喻与结论
> **“Spring AI = Servlet API（现代基础设施）；AgentScope / Embabel = Spring MVC（高级应用框架）。”**

Spring AI 2.0 完美胜任底层模型通信与工具标准化的“基础设施基座”，但当企业面对复杂的退款仲裁、多轮决策、长流程分支与分布式 Multi-Agent 编排时，继续在 Spring AI 之上手搓状态机就会重蹈胶水代码膨胀的覆辙！

这正是我们在第 09 课必须引入第 2 级阶梯 **`enterprise-ai-agent-agentscope` (AgentScope Java 2.0)** 的根本原因！
