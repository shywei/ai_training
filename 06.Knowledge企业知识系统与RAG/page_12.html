CHAPTER 03 · 检索核心边界

【P0 纠正】检索过滤 vs 混合检索 — 约束边界与真正的 Hybrid Search

🚨 严正纠正：严禁将“元数据过滤”混淆为“混合检索”！
很多团队把 SQL 的 WHERE 过滤当成混合检索，这是严重的知识边界错误。两者在底层原理、打分机制与召回能力上完全不同！
❌ 元数据过滤 (Metadata Filter) 约束条件过滤
本质：SQL 的 WHERE 硬性裁剪（如 category='笔记本' AND tenant_id='T01'）。
机制：通过布尔表达式缩小候选池，不改变任何相关性打分机制，非黑即白。
局限：无法解决型号、专有名词、代码错误码在语义空间被稀释的问题。
定位：硬性范围约束，绝非混合检索！
✅ 真正混合检索完整四阶段范式 双路召回→融合→精排
① 双路召回：Dense 稠密向量（语义抽象）+ Sparse BM25（精确型号/专名）；
② 结果融合：RRF 倒数排名融合或加权评分，消除不同通道量纲差异；
③ 候选重排：Cross-Encoder Reranker 交叉编码深度打分二次精排；
④ 上下文组装：Context Assembly 证据去重与窗口防断章。
* RRF 属排名融合算法，Cross-Encoder 属相关性重排，职责独立。
定位：双路召回 + RRF 融合 + Cross-Encoder 精排体系
RRF 倒数排名融合算法（阶段 ②）： $\text{RRF\_Score}(d) = \frac{1}{60 + \text{rank}_{\text{dense}}(d)} + \frac{1}{60 + \text{rank}_{\text{bm25}}(d)}$ —— 纯依名次公平融合，不受分数量纲干扰。
💻 Demo 代码落地：检索门控与白名单过滤
// RetrievalService.java — 前置意图白名单门控
public boolean isProductRelated(String q) {
  if (q == null) return false;
  String lower = q.toLowerCase();
  for (String kw : PRODUCT_KEYWORDS) {
    if (lower.contains(kw.toLowerCase()))
      return true; // 命中白名单才调 pgvector 检索
  }
  return false;    // 闲聊直接跳过，零 Token 浪费
}

// 元数据过滤：通过 SearchRequest 约束范围
SearchRequest.query(q)
  .withTopK(3)
  .withSimilarityThreshold(0.3)
  .withFilterExpression("category == '笔记本'"); // 约束范围
🧭 企业检索演进三级跳
Stage 1（Demo）：白名单前置门控 + 单路 pgvector 稠密向量检索；
Stage 2（扩展）：+ JSONB Metadata Filtering（按租户/分类精确范围约束）；
Stage 3（生产）：真正 Hybrid Search（pgvector 向量 + PG tsvector BM25 + RRF 融合）。
铁律收口：元数据过滤是“硬筛范围”（WHERE 裁剪），混合检索是“软硬互补”（Dense + BM25 RRF 融合），两者绝不可混为一谈。
