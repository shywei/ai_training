## Slide Objective
展示企业知识的来源全景，讲清楚"知识不一定是文档"、"多种知识怎么管理"、"商品数据的 ETL 流程"。

## Suggested Presentation
很多学员一听到 RAG 就想到"把 PDF 塞进去"。这页要纠正这个认知。

看左边第一个框：知识来源不只是文档。数据库里的商品表、CRM 里的客户信息、API 接口——这些都是知识。RAG 管道的输入是**文本内容**，不管这文本是从 PDF 解析出来的，还是从 MySQL 字段拼接出来的。

商品导购场景下，商品信息本来就在 MySQL 里。我们不需要先从数据库导出成 PDF 再解析——直接从 MySQL 提取描述字段（名称、配置、亮点、适用场景），拼成文本，走 Embedding → 向量存储的流程。`products.json` 就是从 MySQL 提取的描述数据，Demo 里用 JSON 文件模拟这个过程。

看右边的商品知识流：MySQL product 表（数据源）→ 提取描述字段 → Embedding → vector_store 表（向量索引）→ 语义检索拿到商品 ID → 回 MySQL 查实时价格库存（第七课 Tool）。

这个流程体现了**数据分层**：描述信息放向量库（语义检索），实时数据放关系型库（精确查询）。两类数据的查询模式不同，不应该混在一个存储里。

看左边第二个框：多种知识怎么管理？学员会问"我们除了商品还有 FAQ、还有内部文档，怎么放？"

推荐方案：**共享一张表 + metadata 过滤**。商品、FAQ、报告都存同一张 `vector_store` 表，metadata 加 `type` 字段区分。查询时可以按类型过滤，也可以跨类型搜索。用户问"ThinkPad 的退货政策是什么"，一次检索就能同时匹配到商品知识和 FAQ。

为什么不推荐分表？分表需要多个 PgVectorStore 实例，跨类型检索要查多张表再合并，更复杂。只有数据量极大（百万级）或权限要求极严格时才考虑分表。

底部的注意事项：商品的价格和库存不放知识库。这些是实时数据——价格会变，库存实时变。放 MySQL，第七课 Tool 调用查询。这是数据分层的设计。

## Key Emphasis
学员应该理解两个关键认知：1) 知识不一定是文件，数据库数据也是知识；2) 多种知识共享一张向量表，用 metadata 区分。这两个认知对后续做项目很重要。

## Demo 与生产的差距
Demo 用 JSON 文件模拟 ETL 过程。生产中应该是：MySQL 数据变更 → 触发 ETL 管道 → 提取描述字段 → 生成 Embedding → 更新向量库。可以是定时任务，也可以是数据库变更触发。Demo 的 `products.json` 是静态的，生产中的知识应该是动态更新的。
