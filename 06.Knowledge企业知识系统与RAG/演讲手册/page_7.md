# Page 7 — 企业多元数据接入矩阵 — 向量数据库绝非万能银弹

## Slide Objective
建立企业级 AI 系统中**多源、多模态异构数据的接入矩阵**。**严正宣誓：向量数据库绝非万能银弹（Vector DB is NOT a Silver Bullet）！** 讲透结构化数据（Text-to-SQL / 函数调用）、非结构化数据（RAG / 向量检索）、复杂关系图谱数据（GraphRAG）、实时动态数据（外部 API / MCP 工具）四类资产的本质区别与最优访问路径，确立“静态知识归 RAG，实时状态归 Tool，表格事实归 SQL，复杂关系归图谱”的架构分层总原则。

## Suggested Presentation

### 一、架构警示：打破“万物皆可 Embedding”的幼稚病
在大模型和向量数据库爆火后，很多团队患上了“向量数据库万能病”：
- 把公司的订单表、库存表、财务报表直接切成文本段落，一股脑 Embedding 塞进向量库；
- 然后让用户问：“上季度销售额排名前三的商品总额是多少？”
- 结果大模型开始一本正经地胡说八道。

为什么？因为**向量数据库的核心能力是“自然语言语义模糊相似度匹配”，它根本不具备“精确聚合、数值过滤、求和与算术计算”的能力！**
在企业真实环境中，数据形态是高度异构的。架构师的第一职责，是根据数据形态选择最优接入路径，绝不能把向量库当成唯一答案。

---

### 二、企业四大主流数据形态接入矩阵

看幻灯片的 2x2 矩阵，企业数据资产清晰地划分为四大阵营：

#### 1. 结构化数据 (Structured Data) — 精确计算与聚合
- **典型形态：** 关系型数据库（MySQL / PostgreSQL）、数据仓库（ClickHouse / Hive）、ERP / CRM 核心业务表、财务对账单、商品规格属性表。
- **查询特征：** 要求 100% 精确的数值比对、范围过滤（`BETWEEN / IN`）、排序（`ORDER BY`）以及聚合计算（`SUM / AVG / GROUP BY`）。
- **避坑红线：** **严禁将表格直接拆分 Embedding！** 一旦把表格切碎成 Chunk，行与列之间的对应约束荡然无存。
- **最优访问路径：** **Text-to-SQL / 语义层（Semantic Layer） / 结构化函数调用（Function Calling）**。让大模型生成确定性的 SQL 或直接调用预定义的 API 进行精确统计。

#### 2. 非结构化数据 (Unstructured Data) — 长文档与语义问答
- **典型形态：** 企业的章程制度、产品操作使用手册、退换货与保修政策、行业分析研报、长篇 PDF、客服 FAQ 问答库。
- **查询特征：** 文本篇幅长、缺乏统一严格 Schema、用户的提问口语化（如“刚买的电脑键盘连击怎么处理”）。
- **最优访问路径：** **企业级 RAG 管道（稠密向量检索 + 稀疏词法 BM25 混合检索 + Rerank 精排）**。
- **核心工程要领：** 采用版面感知解析（Docling / MinerU）保留 Markdown/HTML 表格与标题层级，避免切片断章取义。

#### 3. 复杂关系图谱数据 (Relational Graph Data) — 多跳因果与全局拓扑
- **典型形态：** 复杂供应链上下游关系网、上市公司股权穿透与受益所有人网络、企业多层级组织权限、跨多篇文档的复杂因果脉络。
- **查询特征：** 用户问题涉及深层多跳推理（“A 公司的实际控制人控股的另一家海外公司最近有什么诉讼风险？”）。
- **普通 RAG 痛点：** 传统 RAG 将文档切碎为孤立的 Chunk，检索只能召回局部的几个碎片，无法串联全局拓扑关系，“只见树木、不见森林”。
- **最优访问路径：** **知识图谱引擎（图数据库查询如 Cypher/SPARQL）或 GraphRAG（多跳拓扑可能路线之一）**。关系图谱数据根据深层多跳深度和推理成本权衡选型，通过实体关系三元组或社区摘要算法（Community Summaries）辅助全局推理。

#### 4. 实时高频动态数据 (Real-time Dynamic Data) — 秒级实效与状态
- **典型形态：** 秒级波动的商品实时库存量、大促即时秒杀价格、顺丰快递物流轨迹、实时汇率与天气状况。
- **避坑红线：** **实时数据绝对不能写进向量库！** 价格和库存每秒都在变动，如果写入向量库，不仅更新维护成本极高，而且缓存和向量检索必然导致严重的数据延迟，引发超卖与客诉。
- **最优访问路径：** **外部业务微服务 API / MCP 工具调用（Tool Calling）**。

### 三、Demo 的读写分层映射
把视角收回到我们的导购 Agent Demo：
- **静态语义描述（RAG 侧）：** 商品的处理器型号、外观材质、屏幕亮点、适用人群等静态文本，存入 `pgvector`，供本课的 `RetrievalService` 做语义理解；
- **动态价格与库存（Tool 侧）：** 频繁变动的商品库存量与实时价格，保留在 MySQL `product_info` 表中，留给下一课（第七课 Tool Calling）让 Agent 作为外部工具实时查询。
**两者分工明确：静态知识归 RAG，实时状态归 Tool。**

## Key Emphasis
1. 向量数据库不是万能银弹：切忌把表格无脑转向量，各类型数据匹配最优访问路径。
2. 牢记四大矩阵路径：结构化走 SQL/Tool，非结构化走 RAG，多跳关系走 GraphRAG，实时动态走 API。
3. 理解 Demo 分层：静态商品特性进 pgvector，动态价格库存留 MySQL 走 Tool。

## Optional Extension
**学员问：如果用户的问题既包含模糊语义又包含精确计算，比如“帮我推荐一台写代码最舒服的笔记本，并且价格在 8000 元以下、有现货的”，怎么处理？**
答：这正是工业级 Agent 的典型工作流——**RAG 与 Tool 的协同闭环**：
1. **第一步（RAG 语义召回）：** 先通过 RAG 从 `pgvector` 知识库中检索出符合“写代码舒服”（大内存、高分屏、好键盘）的候选商品列表（如推荐 NB001 和 NB002）；
2. **第二步（Tool 精准校验）：** Agent 拿到候选商品的 ID，自动触发工具调用 `checkInventoryAndPrice(NB001, NB002)`，从 MySQL 查询实时库存与当前折扣价，过滤掉无货或超预算的款式；
3. **第三步（上下文合成）：** 结合前两步结果合成最终建议。这就是第七课和第八课要落地的完整形态！

## Classroom Interaction
现场给出三个业务场景，让学员选择最优数据接入方案：
1. “统计过去 30 天华东地区退货率最高的前 5 款商品” → **结构化查询（Text-to-SQL / 关系库）**；
2. “解答用户关于笔记本三包保修条款中‘人为损坏判定标准’的咨询” → **非结构化长文档 RAG**；
3. “查询用户的快递当前到哪一站了” → **实时业务 API / Tool Calling**。

## Take Away
数据各有其道，切莫万物向量化。表格算术走 SQL，长文泛化靠 RAG，图谱穿透解多跳，秒变状态调 API。
