## Slide Objective
展示引入向量数据库后，第五课的记忆系统如何升级——从"存标签"到"存记忆"。这是第五课的自然延伸，不是第六课的附加内容。

## Suggested Presentation
这页是第五课的延伸。第五课讲了记忆系统，但当时的长期记忆只有 MySQL 画像——结构化标签。用户说"我喜欢轻薄本"，LLM 提取成 `preferences: "轻薄本"`，存入 MySQL。这丢失了原始对话的语义细节。

"喜欢轻薄本"是标签，不是记忆。标签丢失了上下文——用户是在什么场景下说的？是对比了哪些商品后得出的结论？有没有附加条件（比如"预算8000以内"）？这些细节在结构化标签里都丢失了。

现在有了 pgvector，记忆系统可以升级了。对话原文片段被 Embedding 后存入 pgvector，下次用户问"推荐笔记本"，语义检索能找到"用户上次说想要一台写代码的笔记本，预算8000"。这比查 MySQL 的 `preferences: "轻薄本"` 精确得多——因为它保留了原始语境。

看左边的演进图。第五课的局限：长期记忆只存结构化画像，丢失语义细节。第六课的增强：对话原文片段存入 pgvector，支持语义检索。同一个 pgvector，Knowledge 和 Memory 都用。

三层存储各司其职。MySQL user_profile 存结构化画像（第五课），用于后台展示、数据分析、快速判断。pgvector user_memory 存语义记忆片段（第六课新增），用于 AI Agent 的上下文检索。Redis session 存工作缓冲区（第五课），沉淀后清空。

自动沉淀机制：Redis 的对话历史每 5 轮沉淀到 pgvector，然后清空。这样 Redis 只存"还没处理的"，pgvector 存"已经处理过的"，不会重复。这就是第五课 Session Memory 的自然进化——从"只能存当前会话"到"跨会话可检索"。

看右边的数据分层。同一个 pgvector 基础设施，Knowledge 和 Memory 都用——但存的是不同的数据。商品描述放 pgvector（语义检索），价格库存放 MySQL（实时查询）。"推荐轻薄本"是语义问题，"有没有货"是业务问题。两类问题用不同的存储解决。

## Key Emphasis
向量数据库不只服务于 Knowledge，也服务于 Memory。引入 pgvector 后，记忆系统才真正从"结构化标签"进化到"语义记忆"。这是第五课概念的自然延伸，不是第六课的附加内容。

## Demo 与生产的差距
Demo 的自动沉淀机制是同步的（在 `buildContext()` 中触发），生产中应该异步——用定时任务或消息队列，不阻塞用户请求。Demo 的记忆没有去重——多次沉淀可能产生相似记录，生产中需要合并策略。Demo 的数据分层只体现了"描述 vs 价格"，生产中还需要考虑知识权限隔离（不同部门看到不同的知识）。
