## Slide Objective
利用精炼的“只读 .jar 包”心智模型，深入辨析企业大模型落地的两大技术路线：微调（Fine-Tuning）与 RAG（检索增强生成）。纠偏“模型权重等同于可读源码”的技术误区，阐明微调是基于梯度的参数更新（学风格），而 RAG 是推理时的外部知识动态装配（学事实），树立“微调学风格，RAG 查事实”的架构选型黄金法则。

## Suggested Presentation
上一页我们确立了大模型类似一个“巨型只读二进制 .jar 包”。
现在，业务方拿着一份最新的企业《员工差旅制度》、《产品 API 文档》或者《内部考勤政策》来找你，说：“我们要让大模型掌握这些企业私有数据，该怎么落地？”

这时候，摆在你面前的通常有两条路。很多没有大模型底层工程直觉的工程师，很容易掉进巨额烧钱的误区：
有的工程师会说：“我们把这些企业文档拿去微调（Fine-Tuning），重新训练一个私有模型！”
请大家暂停一下！我们先来彻底纠偏一个概念：
**大模型权重不是 Java 源码！你不能把它像代码一样‘改两行业务逻辑重新编译’。**
大模型权重是数十亿个经过预训练优化的高维浮点数矩阵。所谓微调，本质上是通过反向传播算法更新模型内部的参数分布，或者挂载一个增量适配器（LoRA）：
- **微调改动的是概率流形**。它最擅长的是学习某种特定的说话风格、门诊病历书写规范，或者严格约束模型按固定 JSON Schema 语法输出；
- 但如果试图用微调去让模型“死记硬背”企业规章制度，代价将极其惨痛：
  1. **成本高昂且更新迟缓**：公司的退货政策下周改了一个数字，你难道再花几千上万元租 GPU 重新做一次微调对齐？
  2. **灾难性遗忘（Catastrophic Forgetting）**：神经网络是一个高维连续曲面，你强行注入新的专有事实数据，往往会冲垮它在海量预训练中形成的通用世界知识，导致逻辑推理能力断崖式下跌，俗称“把模型改傻了”；
  3. **无法溯源且仍有幻觉**：微调后模型依然以概率采样输出，你根本无法验证它吐出的政策条款到底来自哪一份权威文件。

**第二条路：RAG（检索增强生成）**。
在架构上，这相当于**基座大模型权重 100% 保持只读冻结**，我们一行动不动它！
大模型就像一位智商极高但没读过你公司制度的高考状元。
我们不在他脑子里做开颅手术（微调），而是把企业《员工差旅制度》存进外部的向量数据库或检索系统中。
当员工提问“去深圳出差每晚酒店标准是多少钱”时：
1. 系统先去知识库里毫秒级检索出最相关的条款原文；
2. 把这段权威原文作为参考资料，动态拼进 Prompt 上下文；
3. 大模型基于这段上下文进行“开卷考试”，在阅读理解后精准提取答案，并注明出处引用！

大家一对比，优劣立刻一目了然：
RAG 成本极低、文档上传秒级生效、100% 具备出处溯源防幻觉能力，天然契合企业内部数据权限隔离。

因此，请大家牢记我们架构师的八字选型黄金法则：**“微调学文风，RAG 查事实”**！
你想让模型学某种特定行业 DSL 语法、特定专业风格，去做微调；但如果你想让它回答业务规则、产品价格和企业知识，**无脑首选 RAG！**

## Key Q&A / Clarifications
**Q：长上下文窗口（Long Context，如 1M~2M Token）普及后，RAG 还有存在的必要吗？**
A：依然绝对必要！第一是成本与延迟：把 100 万字全部塞进上下文，每次推理调用的费用和首字等待延迟（TTFT）极其昂贵；第二是“大海捞针（Needle in a Haystack）”问题：即使模型支持百万上下文，当关键信息被淹没在长文本中间时，模型的注意力依然容易分散甚至忽略；第三是数据权限与安全：企业知识库有严格的部门权限隔离，RAG 可以在检索阶段天然做权限拦截，而长文本无法实现细粒度权限控制。
